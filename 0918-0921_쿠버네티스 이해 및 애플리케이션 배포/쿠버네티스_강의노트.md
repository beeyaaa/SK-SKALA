## 1. 전체 구조

Kubernetes는 여러 컴퓨터에 컨테이너를 배포하고, 사용자가 선언한 상태가 계속 유지되도록 관리하는 **컨테이너 오케스트레이션 플랫폼**이다.

```text
Kubernetes Cluster
├── Control Plane
│   ├── kube-apiserver
│   ├── etcd
│   ├── kube-scheduler
│   └── kube-controller-manager
└── Worker Node
    ├── kubelet
    ├── Container Runtime
    ├── kube-proxy
    └── Pod
        └── Container
```

| 개념 | 의미 |
|---|---|
| Cluster | Control Plane과 여러 Node를 합친 Kubernetes 전체 환경 |
| Node | Pod가 실제로 실행되는 물리 서버 또는 가상 머신 |
| Pod | Kubernetes가 배포하고 관리하는 최소 실행 단위 |
| Container | 애플리케이션 프로세스가 실행되는 격리 환경 |

Kubernetes는 컨테이너를 직접 배포하는 대신 **Pod를 배포**한다. 한 Pod에는 하나 이상의 컨테이너가 들어갈 수 있다. 같은 Pod의 컨테이너는 IP 주소와 네트워크 공간을 공유하며 `localhost`로 통신할 수 있다.

서로 독립적으로 배포하거나 확장해야 하는 애플리케이션은 서로 다른 Pod에 둔다. 항상 함께 실행되어야 하는 보조 컨테이너만 같은 Pod에 두는 것이 일반적이다.

## 2. 실습 환경과 kubeconfig

### kubeconfig

`kubeconfig`는 `kubectl`이 어떤 Cluster에 어떤 사용자로 접속할지 정의하는 설정 파일이다.

```bash
~/.kube/config
```

주요 구성:

- `clusters`: Kubernetes API Server 주소와 CA 정보
- `users`: 인증서나 토큰 등 사용자 인증 정보
- `contexts`: Cluster, User, Namespace의 조합
- `current-context`: 현재 선택된 Context

```bash
kubectl config current-context
kubectl config view --minify
```

### Namespace 변경

실습 환경의 별칭:

```bash
alias kcns='kubectl config set-context $(kubectl config current-context) --namespace'
alias k='kubectl'
```

별칭 적용과 Namespace 변경:

```bash
source ~/.zshrc
kcns class-5
kubectl config view --minify -o jsonpath='{..namespace}'; echo
```

접속 확인:

```bash
kubectl get serviceaccount
```

결과가 출력되면 kubeconfig 인증과 API Server 통신이 가능한 상태다.

### API Server 요청 흐름

```text
사용자
  ↓ kubectl
kube-apiserver
  ↓ Authentication
  ↓ Authorization
  ↓ Admission Control
etcd 및 Controller
```

## 3. 컨테이너 이미지와 Registry

### 이미지 생성과 배포 흐름

```text
소스 코드 + Dockerfile
        ↓ docker build
Container Image
        ↓ docker push
Container Registry
        ↓ Kubernetes가 pull
Pod 안에서 Container 실행
```

### Dockerfile

```dockerfile
FROM eclipse-temurin:21-jre
WORKDIR /app
EXPOSE 8080
ADD ./target/*.jar app.jar
CMD ["sh", "-c", "exec java $JAVA_OPTS -jar app.jar"]
```

| 명령 | 의미 |
|---|---|
| `FROM` | 기반 이미지 지정 |
| `WORKDIR` | 컨테이너 내부 작업 디렉터리 지정 |
| `COPY`, `ADD` | 파일을 이미지에 포함 |
| `EXPOSE` | 애플리케이션 사용 포트 설명 |
| `ENV` | 환경변수 설정 |
| `CMD`, `ENTRYPOINT` | 컨테이너 시작 시 실행할 명령 |

`EXPOSE`만으로 포트가 외부에 공개되지는 않는다. 로컬에서는 `docker run -p`, Kubernetes에서는 Service나 Ingress가 필요하다.

### Registry 이미지 이름

```text
<registry>/<project>/<repository>:<tag>
```

```text
skala-registry.example.com/class-5/sk172-webserver:1.0
```

- Registry: 이미지 서버
- Project: Harbor의 논리적 프로젝트
- Repository: 이미지 이름
- Tag: 이미지 버전

### 안전한 로그인

```bash
printf '%s' "$DOCKER_REGISTRY_PASSWORD" |
docker login "$DOCKER_REGISTRY" \
  -u "$DOCKER_REGISTRY_USER" \
  --password-stdin
```

웹 로그인 계정과 Docker CLI용 Robot 계정은 다를 수 있다.

### 이미지 빌드와 Push

로컬에 저장하는 단일 플랫폼 빌드:

```bash
docker buildx build \
  -t <사용자>-webserver:1.0 \
  --platform linux/amd64 \
  --load \
  .
```

멀티 플랫폼 이미지를 Registry에 바로 Push:

```bash
docker buildx build \
  --tag <registry>/<project>/<사용자>-webserver:1.0 \
  --platform linux/amd64,linux/arm64 \
  --push \
  .
```

기존 이미지에 Registry 태그를 붙여 Push:

```bash
docker tag <사용자>-webserver:1.0 \
  <registry>/<project>/<사용자>-webserver:1.0
docker push <registry>/<project>/<사용자>-webserver:1.0
```

로컬 실행:

```bash
docker run --rm -it --name webserver \
  -p 8888:8080 <사용자>-webserver:1.0
```

`8888:8080`은 호스트의 8888 포트를 컨테이너의 8080 포트에 연결한다는 뜻이다.

## 4. Kubernetes와 선언적 관리

### Kubernetes가 해결하는 문제

- 컨테이너 장애 시 자동 복구
- 여러 Node에 적절한 배치
- 트래픽 증가에 따른 복제본 확장
- 애플리케이션 업데이트와 Rollback
- 동적으로 바뀌는 Pod IP 관리
- 설정과 Storage 분리
- 상태 확인과 모니터링

### 선언적 방식

명령적 방식은 실행 절차를 지시한다.

```text
서버 A에서 컨테이너 세 개를 실행한다.
```

선언적 방식은 원하는 최종 상태를 정의한다.

```text
이 애플리케이션의 Pod가 항상 세 개 실행되어야 한다.
```

Controller는 현재 상태를 계속 관찰하고 원하는 상태와 다르면 조정한다. 이를 **Reconciliation Loop**라고 한다.

```text
Desired State(Spec)
        ↕ 비교와 조정
Current State(Status)
```

### 주요 Resource

| Resource | 역할 |
|---|---|
| Pod | 컨테이너 실행 |
| Deployment | Stateless Pod의 배포와 업데이트 관리 |
| ReplicaSet | 지정된 수의 Pod 복제본 유지 |
| Service | Pod 집합에 고정된 네트워크 Endpoint 제공 |
| ConfigMap | 일반 설정 저장 |
| Secret | 민감한 설정 저장 |
| Namespace | Cluster 내부 리소스의 논리적 분리 |
| PersistentVolume | 외부 Storage 자원 표현 |
| PersistentVolumeClaim | Storage 사용 요청 |
| Ingress | HTTP/HTTPS 요청을 Service로 Routing |

## 5. Manifest

Manifest는 Kubernetes Resource의 원하는 상태를 YAML 또는 JSON으로 선언한 문서다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: example-pod
  namespace: example
  labels:
    app: webserver
spec:
  containers:
    - name: webserver
      image: example/webserver:1.0
```

| 필드 | 의미 |
|---|---|
| `apiVersion` | Resource가 속한 API 버전 |
| `kind` | Resource 종류 |
| `metadata` | 이름, Namespace, Label, Annotation |
| `spec` | 사용자가 선언하는 원하는 상태 |
| `status` | Kubernetes가 기록하는 현재 상태 |

`status`는 일반적으로 사용자가 직접 작성하지 않는다.

- Resource: Kubernetes API가 제공하는 유형. 예: Pod
- Object: 실제 생성된 인스턴스. 예: `sk172-webserver` Pod

```bash
kubectl apply -f resource.yaml
kubectl delete -f resource.yaml
```

## 7. Pod

Pod는 Kubernetes에서 배포·실행되는 최소 단위다.

### 특징

1. Kubernetes Scheduling의 최소 단위다.
2. 같은 Pod의 컨테이너는 네트워크 Namespace와 Pod IP를 공유한다.
3. 필요하면 Volume을 공유할 수 있다.
4. Pod는 교체 가능한 일시적 Resource로 다룬다.

```text
Node
└── Pod
    ├── Application Container
    └── Sidecar Container
```

Sidecar는 로그 수집이나 Proxy처럼 주 애플리케이션을 보조한다. 독립적으로 확장해야 하는 서비스는 같은 Pod에 넣지 않는다.

### Pod Network

각 Pod는 Cluster 내부 고유 IP를 받는다. Pod가 재생성되면 IP가 바뀔 수 있으므로 클라이언트는 Pod IP에 직접 의존하지 않고 Service를 사용한다.

### Pod Phase

| Phase | 의미 |
|---|---|
| Pending | Scheduling 또는 이미지 다운로드 대기 |
| Running | Node에 배치되어 컨테이너 실행 중 |
| Succeeded | 모든 컨테이너가 정상 종료 |
| Failed | 하나 이상의 컨테이너가 실패로 종료 |
| Unknown | Node 통신 문제로 상태 확인 불가 |

### 배포와 점검

```bash
gen-yaml.sh
kubectl apply -f webserver-pod.yaml
kubectl get pod
kubectl describe pod <pod-name>
kubectl logs <pod-name>
```

Port Forwarding:

```bash
kubectl port-forward pod/<pod-name> 8888:8080
```

Port Forwarding은 개발·점검용 임시 연결이며 운영용 외부 노출 방식이 아니다.

## 8. Deployment와 ReplicaSet

Deployment는 Stateless 애플리케이션의 Pod 배포, 복제, 업데이트, Rollback을 관리한다.

```text
Deployment
└── ReplicaSet
    ├── Pod
    ├── Pod
    └── Pod
```

Deployment가 ReplicaSet을 만들고 ReplicaSet이 지정된 수의 Pod를 유지한다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: webserver
spec:
  replicas: 2
  selector:
    matchLabels:
      app: webserver
  template:
    metadata:
      labels:
        app: webserver
    spec:
      containers:
        - name: webserver
          image: example/webserver:1.0
```

`spec.selector.matchLabels`와 `spec.template.metadata.labels`는 일치해야 한다.

```bash
kubectl scale deployment webserver --replicas=3
kubectl rollout status deployment/webserver
kubectl rollout history deployment/webserver
kubectl rollout undo deployment/webserver
```

이미지를 변경하면 Deployment가 새 ReplicaSet과 Pod를 만들고, 새 Pod가 준비되면 이전 Pod를 줄이는 Rolling Update를 수행한다.

| 값 | 의미 |
|---|---|
| DESIRED | 원하는 Pod 개수 |
| CURRENT | 현재 생성된 Pod 개수 |
| READY | 요청 처리 준비가 된 Pod 개수 |

## 9. Service와 DNS

Pod는 교체될 때 IP가 바뀐다. Service는 Label Selector로 Pod 집합을 선택하고, 변하지 않는 Cluster IP와 DNS 이름을 제공한다.

```text
Client Pod
   ↓ Service DNS 또는 Cluster IP
Service
   ↓ Label Selector
Pod A / Pod B / Pod C
```

```yaml
apiVersion: v1
kind: Service
metadata:
  name: webserver
spec:
  selector:
    app: webserver
  ports:
    - port: 80
      targetPort: 8080
```

- `selector`: 연결할 Pod Label
- `port`: Service가 제공하는 Port
- `targetPort`: 컨테이너 애플리케이션 Port

Service와 연결된 Pod IP·Port 정보는 EndpointSlice에 기록된다.

```bash
kubectl get service
kubectl get endpoints
kubectl get endpointslice
kubectl get pod --show-labels
```

Endpoint가 비어 있으면 Service Selector와 Pod Label 불일치를 먼저 확인한다.

CoreDNS는 Service 이름을 Cluster IP로 변환한다.

```text
같은 Namespace: http://webserver
다른 Namespace: http://webserver.<namespace>.svc.cluster.local
```

| Service 유형 | 용도 |
|---|---|
| ClusterIP | Cluster 내부 접근. 기본값 |
| NodePort | 각 Node의 Port로 외부 노출 |
| LoadBalancer | Cloud Load Balancer로 외부 노출 |
| ExternalName | 외부 DNS 이름 연결 |

## 10. Namespace

Namespace는 Cluster 내부 Resource를 팀, 프로젝트, 환경별로 논리적으로 분리하는 공간이다.

주요 목적:

- 이름 충돌 방지
- RBAC 권한 범위 설정
- ResourceQuota와 LimitRange 적용
- 팀·환경별 Resource 분리

Namespace는 기본적으로 완전한 네트워크 격리를 제공하지 않는다. 네트워크 격리에는 NetworkPolicy가 필요하다.

Namespace-scoped Resource:

- Pod, Deployment, Service
- ConfigMap, Secret
- PersistentVolumeClaim

Cluster-scoped Resource:

- Node, Namespace
- PersistentVolume, StorageClass
- ClusterRole

```bash
kubectl get namespace
kubectl get all -n class-5
```

## 11. ConfigMap과 외부 설정

ConfigMap은 애플리케이션 설정을 이미지에서 분리해 저장한다.

예시:

- Spring `application.yaml`
- API 주소
- 로그 레벨
- 일반 환경변수

비밀번호와 Token 같은 민감정보는 ConfigMap이 아니라 Secret을 사용한다.

파일에서 생성:

```bash
kubectl create configmap app-config \
  --from-file=application.yaml
```

환경변수로 주입:

```yaml
envFrom:
  - configMapRef:
      name: app-config
```

Volume으로 Mount:

```yaml
volumes:
  - name: config
    configMap:
      name: app-config
containers:
  - name: app
    volumeMounts:
      - name: config
        mountPath: /app/config
```

환경변수로 주입된 값은 일반적으로 Pod 재시작 후 변경 사항이 반영된다. Volume Mount는 파일로 제공되지만 애플리케이션이 변경된 파일을 다시 읽는지는 별개의 문제다.

## 12. Volume, PV, PVC, StorageClass

컨테이너의 Writable Layer 데이터는 컨테이너 교체 시 사라질 수 있다. 데이터 유지나 공유에는 Volume을 사용한다.

| 개념 | 의미 |
|---|---|
| Volume | Pod가 사용하는 저장 공간 추상화 |
| PersistentVolume(PV) | Cluster에 제공된 실제 Storage 자원 표현 |
| PersistentVolumeClaim(PVC) | 사용자가 필요한 Storage 조건을 요청하는 Resource |
| StorageClass | 동적 Storage 생성을 위한 Provisioner와 정책 |
| CSI | Kubernetes와 외부 Storage를 연결하는 표준 Interface |

```text
관리자 또는 Provisioner가 Storage 제공
               ↓
PersistentVolume
               ↑ Binding
PersistentVolumeClaim
               ↓
Pod가 PVC를 Volume으로 Mount
```

PVC 예시:

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: app-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi
```

Pod에서 사용:

```yaml
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: app-data
containers:
  - name: app
    volumeMounts:
      - name: data
        mountPath: /app/data
```

| Access Mode | 의미 |
|---|---|
| ReadWriteOnce(RWO) | 하나의 Node에서 Read/Write Mount |
| ReadOnlyMany(ROX) | 여러 Node에서 Read-Only Mount |
| ReadWriteMany(RWX) | 여러 Node에서 Read/Write Mount |
| ReadWriteOncePod(RWOP) | 하나의 Pod에서만 Read/Write Mount |

- Static Provisioning: 관리자가 PV와 실제 Storage를 미리 생성
- Dynamic Provisioning: PVC 생성 시 StorageClass와 CSI Driver가 Storage와 PV를 자동 생성

Block Storage의 대표 예는 AWS EBS, File Storage의 대표 예는 AWS EFS다.

## 13. Ingress

Ingress는 외부 HTTP/HTTPS 요청을 내부 Service로 전달하는 API Resource다. Ingress Resource는 규칙을 선언하고 실제 트래픽은 **Ingress Controller**가 처리한다.

```text
외부 Client
    ↓ HTTP/HTTPS
Ingress Controller
    ↓ Ingress Rule
Service
    ↓ Selector
Pod
```

| 구분 | Service | Ingress |
|---|---|---|
| 주요 계층 | 주로 L4 | L7 HTTP/HTTPS |
| Routing 기준 | IP와 Port | Host와 Path |
| 연결 대상 | Pod | Service |

```yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: app-ingress
spec:
  ingressClassName: public-nginx
  rules:
    - host: app.example.com
      http:
        paths:
          - path: /
            pathType: Prefix
            backend:
              service:
                name: frontend
                port:
                  number: 80
```

HTTPS는 인증서와 개인키를 TLS Secret으로 등록한 뒤 Ingress에서 참조한다.

Rewrite Target은 외부 Path와 Backend가 기대하는 Path가 다를 때 사용한다.

```text
외부: /sk172/api/users
내부: /api/users
```

연결 문제 확인 순서:

```text
DNS → Ingress Controller → Host/Path Rule → Service → EndpointSlice → Pod
```

## 14. 무중단 배포

### Rolling Update

새 버전 Pod를 점진적으로 생성하고 이전 버전 Pod를 점진적으로 제거한다. Deployment의 기본 업데이트 전략이다.

- 장점: 추가 환경이 적고 기본 기능으로 구현 가능
- 주의: 배포 중 두 버전이 동시에 요청을 처리할 수 있음

### Blue/Green Deployment

현재 버전을 Blue, 새 버전을 Green으로 분리해 동시에 배포한 뒤 Service나 Ingress의 연결 대상을 전환한다.

```text
Ingress
  ├── Blue Service → Version 1 Pods
  └── Green Service → Version 2 Pods
```

- 장점: 빠른 전환과 Rollback
- 단점: 두 버전의 Resource를 동시에 유지해야 함
- 주의: Database Schema 변경은 양쪽 버전의 호환성을 고려해야 함

## 15. Pod 생명주기와 Probe

Kubernetes는 Probe를 이용해 컨테이너 상태를 판단한다.

| Probe | 확인 대상 | 실패 시 동작 |
|---|---|---|
| Startup Probe | 애플리케이션 시작 완료 여부 | 다른 Probe 시작 지연 |
| Liveness Probe | 프로세스가 정상적으로 살아 있는지 | 컨테이너 재시작 |
| Readiness Probe | 현재 요청을 받을 준비가 됐는지 | Service Endpoint에서 제외 |

Readiness 실패는 컨테이너를 재시작하지 않고 트래픽만 차단한다.

Handler 방식:

- HTTP GET
- TCP Socket
- Exec Command
- gRPC Health Check

```yaml
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
```

| 필드 | 의미 |
|---|---|
| `initialDelaySeconds` | 첫 검사 전 대기 시간 |
| `periodSeconds` | 검사 주기 |
| `timeoutSeconds` | 검사 제한 시간 |
| `failureThreshold` | 실패 판정까지 연속 실패 횟수 |
| `successThreshold` | 성공 판정까지 연속 성공 횟수 |

Probe 경로나 초기 지연 시간을 잘못 설정하면 정상 애플리케이션도 반복 재시작될 수 있다.

## 16. Prometheus와 Grafana

### Prometheus

Prometheus는 시계열 Metric을 수집·저장하고 PromQL로 조회하는 모니터링 시스템이다.

- `/metrics` Endpoint를 주기적으로 호출하는 Pull 방식
- Metric Name, Label, Timestamp, Value 구조
- PromQL을 이용한 조회와 집계
- Alertmanager와 연계 가능

```text
http_server_requests_seconds_count{method="GET",status="200"} 1520
```

Counter는 누적값이므로 초당 증가율은 `rate()`로 계산한다.

```promql
rate(http_server_requests_seconds_count[5m])
```

### Grafana

Grafana는 Prometheus 등의 Metric을 Dashboard로 시각화한다.

| 개념 | 의미 |
|---|---|
| Data Source | Prometheus 등 원본 데이터 시스템 |
| Dashboard | 여러 Panel을 모은 화면 |
| Panel | 그래프, 표, 숫자 등 개별 시각화 |
| Variable | 조회 조건을 동적으로 바꾸는 변수 |

실습 흐름:

1. 애플리케이션에 요청 발생
2. `/metrics`에서 Metric 제공
3. Prometheus에서 Metric 조회
4. Grafana Dashboard Import
5. 부하 발생 후 그래프 변화 관찰

## 17. Kubernetes 시스템 컴포넌트

### Control Plane

#### kube-apiserver

Kubernetes API의 Frontend다. 모든 요청의 진입점이며 인증, 인가, Admission Control, Validation을 수행한다.

```text
Request → Authentication → Authorization → Admission → Validation → etcd
```

#### etcd

Cluster의 상태와 설정을 저장하는 분산 Key-Value Store다. Backup과 접근 통제가 중요하다.

#### kube-scheduler

Node가 정해지지 않은 Pod를 감지하고 CPU·Memory, Affinity, Taint/Toleration, Volume 조건 등을 고려해 Node를 선택한다.

#### kube-controller-manager

Deployment, ReplicaSet, Node 등의 Controller를 실행한다. Controller는 원하는 상태와 현재 상태의 차이를 조정한다.

### Worker Node

#### kubelet

각 Node에서 실행되는 Agent다. 할당된 PodSpec을 확인하고 Container Runtime을 통해 컨테이너를 실행하며 Probe와 Pod 상태를 관리한다.

#### Container Runtime

실제 컨테이너를 실행한다. Kubernetes는 CRI(Container Runtime Interface)를 통해 containerd, CRI-O 같은 Runtime과 통신한다.

#### kube-proxy

Service Network 규칙을 관리하고 Service 트래픽을 Backend Pod로 전달한다.

#### CNI Plugin

CNI(Container Network Interface)는 Pod Network 구성 표준이다. Pod IP 할당, Node 간 Pod 통신, NetworkPolicy 등을 구현한다. 강의 환경에서는 Calico를 다룬다.

### Pod 생성 흐름

```text
1. kubectl apply
2. kube-apiserver가 요청 인증·인가·검증
3. 원하는 상태를 etcd에 저장
4. Controller가 필요한 Pod 생성
5. Scheduler가 Node 선택
6. 선택된 Node의 kubelet이 PodSpec 감지
7. Container Runtime이 Image Pull 및 Container 실행
8. CNI가 Pod Network 구성
9. kubelet이 상태를 API Server에 보고
```
