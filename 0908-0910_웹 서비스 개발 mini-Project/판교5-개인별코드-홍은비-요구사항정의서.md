## 1. 서비스 개요

### 1.1 기획 배경

국내 은행은 여신심사 **지원 업무**에 AI를 도입하고 있다. 하나은행은 기업 재무제표와 산업 동향 등을 분석해 심사의견 초안을 생성하는 시스템을 전 영업점에 도입했으며, 초안 작성 시간을 평균 30분 이상에서 약 10초로 줄이고 연간 약 2만7000시간을 절감할 것으로 제시했다. 신한은행도 기업정보와 여신 신청 내용을 분석하고 12개 주요 산업의 특성을 반영하는 여신심사지원 Agent를 도입했다. 국내 18개 은행장을 대상으로 한 설문에서 12개 응답사 중 50%가 AI·디지털 기술의 우선 활용 분야로 여신심사·평가 고도화를 선택했다.

그러나 공개된 주요 사례는 은행 직원의 기업 분석과 심사의견 작성 등 **서류가 접수된 이후의 내부 업무 지원**에 집중되어 있다. 한국수출입은행은 2026년 7월 기업 제출자료의 반복 검증과 서류심사를 자동화하는 시스템 구축에 착수했지만, 이 역시 AI 결과를 보조자료로 사용하고 최종 판단은 담당 직원이 수행하는 구조다.

기업대출을 신청하는 중소기업 담당자는 사업자등록증, 납세증명서, 재무제표 등 여러 서류의 누락·유효기간·기업정보 일치 여부를 직접 확인해야 한다. 오류가 접수 후 발견되면 기업의 보완·재제출과 은행의 재검토가 함께 발생한다. 이는 과제 설계를 위한 문제 가설이며 실제 개발 전 사용자 인터뷰로 검증해야 한다.

DocSure는 OCR 엔진이나 대출심사 AI가 아니라, 외부 OCR 결과를 이용해 **기업 고객이 접수 전에 필수서류 누락, 유효기간과 서류 간 기업정보 불일치를 스스로 확인·보완**하도록 돕고 은행 담당자의 문서 검토 이력을 연결하는 서비스다.

### 1.2 문제 정의

1. 기업 고객은 여러 제출서류 가운데 무엇이 누락되었고 어떤 값이 불일치하는지 접수 전에 알기 어렵다.
2. 서류별 발급 기준과 유효기간이 달라 만료된 문서를 제출하기 쉽다.
3. 은행 담당자는 여러 문서의 기업명과 사업자등록번호를 눈으로 대조해야 한다.
4. 보완 요청과 재제출이 반복되면 최신 문서와 이전 문서의 구분이 어려워진다.
5. OCR 결과, 고객이 정정한 값, 은행 담당자의 검토 결과를 추적하기 어렵다.

위 문제는 과제 설계를 위한 업무 가설이며, 실제 개발 전 기업 재무 담당자와 은행 기업금융 실무자 인터뷰로 검증한다.

### 1.3 목표 사용자

- 기업대출 서류를 준비·제출하는 중소기업 재무·총무 담당자
- 접수된 기업대출 서류를 확인하는 은행 기업금융 담당자

### 1.4 핵심 가치

- 기업 고객이 접수 전에 누락·만료·불일치를 스스로 발견하고 보완한다.
- 은행 담당자가 원본, OCR 추출값, 고객 정정값과 교차검증 결과를 한 화면에서 확인한다.
- 최초 제출부터 보완 제출, 문서 확인 완료까지 버전과 처리 이력을 보존한다.
- AI는 문서 검수를 보조하며 대출 승인이나 신용 판단을 수행하지 않는다.

### 1.5 핵심 흐름

기업 고객 담당자가 로그인하여 기업대출 신청 건의 필수서류 3종을 업로드한다. 외부 OCR이 주요 정보를 추출하면 시스템이 필수서류 누락, 납세증명서 유효기간, 서류 간 기업명·사업자등록번호, 재무제표 사업연도를 검증한다. 기업 고객은 오류 위치와 해결 방법을 확인해 값을 정정하거나 문서를 다시 업로드한 뒤 제출한다. 은행 담당자는 원본과 검증 결과를 비교해 **서류 확인 완료** 또는 **보완 요청**을 처리한다.

### 1.6 MVP 범위

- 적용 업무: 중소기업의 기업대출 접수 전 제출서류 확인
- 필수 문서: 사업자등록증, 납세증명서, 표준재무제표증명 또는 재무제표
- 지원 파일: JPG, PNG, PDF / 파일당 최대 10MB
- 추출 필드
  - 사업자등록증: 상호·법인명, 사업자등록번호, 대표자명, 개업일
  - 납세증명서: 납세자명, 사업자등록번호, 발급일, 유효기간
  - 재무제표: 법인명, 사업자등록번호, 사업연도, 매출액, 자산총계
- 검증 규칙: 필수서류 누락, 납세증명서 유효기간 만료, 기업명 불일치, 사업자등록번호 불일치, 요구 사업연도 불일치, OCR 저신뢰도
- 기업 고객 기능: 로그인, 제출 현황 조회, 서류 업로드, OCR 결과 확인·정정, 검증 결과 확인, 최종 제출, 보완 재제출
- 은행 담당자 기능: 로그인, 검토 목록 조회, 원본·추출값·정정값 비교, 서류 확인 완료, 보완 요청

### 1.7 선행조건

- 기업은 은행의 기존 채널에서 기업대출 상담 또는 신청을 완료했다.
- 은행은 DocSure에 기업 고객 계정과 서류 제출 건을 사전 생성한다.
- 신청 건에는 요구 재무제표 사업연도와 필수 문서 유형이 설정되어 있다.
- 과제용 프로토타입에서는 사전에 생성한 기업 고객·은행 담당자 계정과 신청 건을 사용한다.

### 1.8 용어 정의

| 용어 | 정의 |
|---|---|
| 서류 패키지 | 한 기업대출 신청 건에 필요한 사업자등록증, 납세증명서, 재무제표의 묶음 |
| OCR 원본값 | 외부 OCR 서비스가 문서에서 최초 추출한 값 |
| 정정값 | OCR 오인식을 확인한 기업 고객이 원본을 근거로 고친 값 |
| 교차검증 | 서로 다른 문서의 기업명·사업자등록번호와 신청 조건의 사업연도를 비교하는 처리 |
| 차단 오류 | 해결하기 전에는 서류 패키지를 최종 제출할 수 없는 오류 |
| 경고 | 제출 전에 사용자의 원본 확인이 필요하지만 자동으로 제출을 차단하지 않는 항목 |
| 서류 확인 완료 | 은행 담당자가 제출서류의 형식 검토를 마친 상태이며 대출 승인·신용 판단을 의미하지 않음 |

### 1.9 이번에 하지 않는 것

- 공개 회원가입과 기업 실명확인
- OCR 모델 직접 학습·튜닝
- 대출 승인, 신용평가, 한도·금리 산정 또는 자동 심사
- 3종 이외의 문서 지원
- 문서 위변조 판별과 진위확인 기관 연동
- 실제 은행 SSO, 코어뱅킹, 기업 ERP 연동
- 상품별 검증 규칙을 편집하는 관리자 화면
- 문자·이메일 알림
- 모바일 네이티브 애플리케이션

### 1.10 기존 금융 OCR과의 차이

| 구분 | 기존 금융 OCR의 일반적 범위 | DocSure의 설계 범위 |
|---|---|---|
| 주요 목적 | 문서 분류·필드 추출과 내부 입력 자동화 | 기업대출 서류 패키지의 접수 전 오류 예방 |
| 검증 단위 | 개별 문서 중심 | 필수서류 전체와 문서 간 값의 교차검증 |
| 기업 고객 경험 | 업로드 후 처리 결과를 기다림 | 오류 위치·원인·해결 행동 확인 후 자가 보완 |
| 담당자 경험 | 추출값을 문서별로 검수 | 서류 패키지와 이전·최신 버전을 한 화면에서 비교 |
| AI의 역할 | 인식·추출 또는 내부 자동화 | 검수 보조만 수행하며 대출 판단은 하지 않음 |
| 성공 기준 | 인식률과 처리 속도 | 접수 전 오류 감소, 반복 보완 감소, 이력 추적 |

## 2. 시스템 액터 정의

| Actor 구분 | 주요 역할·행동 | 상세 설명 |
|---|---|---|
| 기업 고객 담당자 | 로그인, 신청 건 조회, 필수서류 업로드, OCR 결과 확인·정정, 최종 제출, 보완 재제출 | 은행이 사전 등록한 계정으로 로그인한다. 소속 기업의 신청 건과 문서만 조회한다. OCR 오인식은 허용된 범위에서 정정하고, 서류 요건 오류는 새 문서로 보완한다. |
| 은행 기업금융 담당자 | 로그인, 검토 목록 조회, 원본·추출값·정정값·검증 결과 비교, 서류 확인 완료, 보완 요청 | 은행이 발급한 직원 계정으로 로그인한다. 시스템 검증 결과를 참고하되 직접 원본을 확인하여 문서 접수 가능 여부를 결정한다. 대출 승인 여부는 이 서비스에서 처리하지 않는다. |

외부 OCR 서비스는 사람이 아니므로 시스템 액터에 포함하지 않고 API 명세의 외부 연동 대상으로 정의한다.

### 4.1 신청 상태 정의

| 상태 | 의미 |
|---|---|
| DRAFT | 기업 고객이 서류를 준비하거나 검증 결과를 확인 중인 상태 |
| REVIEW_PENDING | 기업 고객이 제출하여 은행 담당자 검토를 기다리는 상태 |
| REVISION_REQUESTED | 은행 담당자가 보완을 요청한 상태 |
| RESUBMITTED | 기업 고객이 보완 문서를 다시 제출한 상태 |
| DOCUMENTS_APPROVED | 은행 담당자가 서류 확인을 완료한 상태. 대출 승인 상태가 아님 |

### 4.2 문서 처리 상태 정의

| 상태 | 의미 |
|---|---|
| UPLOADED | 원본 파일 업로드 완료 |
| PROCESSING | 외부 OCR 분석 진행 중 |
| COMPLETED | OCR 결과 저장과 문서 검증 완료 |
| FAILED | 외부 OCR 분석 실패 |

### 4.3 검증 오류 유형

| 오류 유형 | 설명 | 심각도 | 기본 처리 방식 |
|---|---|---|---|
| MISSING_DOCUMENT | 필수 문서가 제출되지 않음 | 차단 | 누락 문서 업로드 |
| MISSING_FIELD | 필수 값을 추출하지 못함 | 차단 | 원본 확인 후 정정 또는 재업로드 |

## 7. 인수 조건

### REQ-FUNC-001 역할 기반 로그인

- AC-01: 아이디 또는 비밀번호가 없으면 로그인 요청을 보낼 수 없다.
- AC-02: 인증에 성공한 기업 고객은 `SCR-CUST-001`로 이동한다.
- AC-03: 인증에 성공한 은행 담당자는 `SCR-REV-001`로 이동한다.
- AC-04: 인증에 실패하면 "아이디 또는 비밀번호를 확인하세요."를 표시한다.

### REQ-FUNC-003 제출서류 패키지 업로드

- AC-01: JPG, PNG, PDF 외 파일은 업로드할 수 없다.
- AC-02: 10MB를 초과한 파일은 업로드할 수 없다.
- AC-03: 문서 유형과 원본 파일 정보, 유형별 버전 번호를 저장한다.
- AC-04: 보완 재제출 파일은 이전 버전을 삭제하거나 덮어쓰지 않는다.

### REQ-FUNC-005 추출값·검증 결과 조회

- AC-01: 필수 문서 3종의 제출 여부를 한 화면에서 확인할 수 있다.
- AC-02: 기업명·사업자등록번호의 문서별 값을 나란히 표시한다.
- AC-03: 오류마다 대상 문서·필드, 원인과 해결 행동을 표시한다.
- AC-04: 저신뢰도 필드는 신뢰도와 원본 위치를 함께 표시한다.

### REQ-FUNC-006 OCR 추출값 정정

- AC-01: OCR 원본값과 기업 고객 정정값을 모두 조회할 수 있다.
- AC-02: 정정자와 정정 시각을 저장한다.
- AC-03: 정정 후 영향을 받는 교차검증 결과를 다시 계산한다.
- AC-04: 제출 완료된 문서 버전은 정정할 수 없다.

### REQ-FUNC-007 패키지 최종 제출

- AC-01: 차단 오류가 남아 있으면 최종 제출할 수 없다.
- AC-02: 저신뢰도 경고는 원본 확인 체크를 완료해야 한다.
- AC-03: 제출 성공 시 상태가 `REVIEW_PENDING`으로 변경된다.
- AC-04: 제출 버튼을 반복해서 눌러도 같은 버전이 중복 접수되지 않는다.

### REQ-FUNC-010 서류 확인 완료 처리

- AC-01: 은행 담당자만 처리할 수 있다.
- AC-02: 처리 전 ‘대출 승인과 무관함’을 포함한 확인 모달을 표시한다.
- AC-03: 성공 시 `DOCUMENTS_APPROVED` 상태와 담당자 검토 기록을 함께 저장한다.
- AC-04: 이미 처리된 신청을 다시 처리하면 충돌 오류를 표시한다.

### REQ-FUNC-011 보완 요청 및 재제출

- AC-01: 은행 담당자는 대상 문서와 보완 사유를 하나 이상 선택해야 한다.
- AC-02: 기업 고객은 문서별 보완 사유와 처리 상태를 확인할 수 있다.
- AC-03: 재제출 문서는 같은 유형의 이전 문서보다 큰 버전 번호를 갖는다.
- AC-04: 은행 담당자는 직전 버전과 최신 버전의 변경 내용을 비교할 수 있다.

## 8. 공통 예외 처리 및 정책

| 상태 | 발생 조건 | 화면 처리 | HTTP 상태 |
|---|---|---|---:|
| 정상 조회 | 요청 성공 | 조회 결과 표시 | 200 |
| 정상 생성·처리 | 업로드·제출·검토 성공 | 성공 메시지와 변경 상태 표시 | 201 또는 200 |
| 잘못된 입력 | 필수값 누락, 형식·용량 오류 | 필드 또는 업로드 영역에 구체적인 오류 표시 | 400 |
| 인증 실패 | 로그인 실패, 세션 만료 | 공통 인증 오류 또는 로그인 화면 이동 | 401 |
| 접근 권한 없음 | 다른 기업의 문서 조회, 기업 고객의 검토 API 호출 | 권한 없음 안내 | 403 |

| 지원하지 않는 형식 | JPG, PNG, PDF 외 파일 | 지원 형식 안내 | 415 |
| 처리 불가 | OCR 미완료, 해결되지 않은 차단 오류 | 해결할 오류 목록 표시 | 422 |
| 서버 오류 | 내부 처리 실패 | "잠시 후 다시 시도하세요."와 재시도 제공 | 500 |
| 외부 OCR 오류 | 외부 서비스 실패·타임아웃 | 원본을 보존하고 분석 재시도 제공 | 502 또는 504 |
| 빈 화면 | 신청 또는 검토 건이 없음 | 빈 화면 설명과 가능한 다음 행동 표시 | 해당 없음 |
| 로딩 중 | API 요청 처리 중 | 로딩 표시와 중복 클릭 방지 | 해당 없음 |
| 네트워크 오류 | 사용자 네트워크 연결 끊김 | "네트워크를 확인하세요."와 재시도 제공 | 해당 없음 |

## 9. 데이터 설계 시 고려사항

- `users`: 기업 고객과 은행 담당자를 `role`로 구분하고 소속 조직 정보를 저장한다.
- `loan_applications`: 기업별 서류 제출 건, 요구 사업연도와 현재 상태를 저장한다.
- `document_types`: MVP 필수 문서 3종의 코드와 표시명을 저장한다.
- `submitted_documents`: 신청 건, 문서 유형, 원본 파일 메타데이터, 처리 상태, OCR 재시도 횟수와 유형별 버전을 저장한다.
- `extracted_fields`: 문서별 OCR 원본값, 신뢰도와 기업 고객 정정값을 분리 저장한다.
- `validation_issues`: 검증 규칙, 대상 문서·필드, 심각도, 안내 문구와 해결 상태를 저장한다.
- `reviews`: 은행 담당자, 결정, 대상 문서, 보완 사유와 처리 시각을 저장한다.
- 화면과 API에서 사용하지 않는 미래 기능용 테이블은 미리 만들지 않는다.
