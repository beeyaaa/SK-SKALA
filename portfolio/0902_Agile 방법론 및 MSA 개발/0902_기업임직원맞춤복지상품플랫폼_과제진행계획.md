# 기업 임직원 맞춤 복지상품 플랫폼 - 과제 진행계획

> 주제: 기업 임직원 맞춤 복지상품 플랫폼  
> 서비스 가칭: BenefitPick  
> 구현 원칙: 제공된 MSA 백엔드는 수정하지 않고, 프론트엔드 화면과 API 연동을 복지상품 도메인에 맞게 변경한다.

# 2. 프로젝트 주제 확정

## 프로젝트명

**기업 임직원 맞춤 복지상품 플랫폼**

서비스명:

> BenefitPick

## 한 줄 설명

> 기업 임직원이 다양한 복지상품 중 자신에게 필요한 상품을 쉽게 찾고, 이용 이력과 선호 카테고리를 기반으로 맞춤 추천받아 복지포인트로 신청할 수 있는 B2B2C 플랫폼

## 비즈니스 구조

```text
우리 서비스
    ↓ B2B
기업·HR 담당자
    ↓ 사내 복지서비스 제공
임직원
    ↑
복지 제휴사 상품 공급
```

현재 백엔드에는 HR 관리자 기능이 없으므로 다음과 같이 역할을 구분한다.

- HR 담당자: 구매·운영 이해관계자
- 임직원: 핵심 사용자
- 복지 제휴사: 공급자

# 3. 이해관계자와 Pain Point 정리

교수님 말씀대로 기능을 먼저 정하지 않고 이해관계자의 문제부터 확정한다.

| 이해관계자 | 역할 | Pain Point | 원하는 가치 |
|---|---|---|---|
| 임직원 | 핵심 사용자 | 복지상품이 많아 자신에게 필요한 상품을 찾기 어려움 | 필요한 복지상품을 빠르게 발견하고 신청 |
| HR 복지담당자 | 구매·운영자 | 복지예산을 사용하지만 상품 이용률이 낮음 | 복지제도 접근성과 이용률 향상 |
| 복지 제휴사 | 공급자 | 관심 있는 임직원에게 상품을 노출하기 어려움 | 상품 노출과 이용자 수 증가 |
| 경영진 | 의사결정자 | 복지예산이 직원 만족으로 이어지는지 판단하기 어려움 | 복지예산 활용도 향상 |

## 핵심 Pain Point

모든 문제를 동시에 해결하려고 하지 않고 다음 한 가지를 핵심 문제로 잡는다.

> 임직원은 회사가 제공하는 복지상품이 많아도 자신에게 적합한 상품을 찾기 어렵고, 일일이 비교해야 해서 혜택을 사용하지 못하고 놓친다.

## 핵심 가치

> 복지상품 탐색 시간을 줄이고 임직원의 복지 혜택 이용률을 높인다.

# 4. AI 솔루션 정의

현재 백엔드 추천 서비스는 실제 생성형 AI가 아니라 **규칙 기반 추천 모델**이다.

따라서 다음과 같이 정의한다.

> 임직원의 기존 복지상품 이용 이력을 분석하여 가장 많이 이용한 카테고리를 찾고, 해당 카테고리에서 아직 이용하지 않은 인기 복지상품을 추천한다.

## 추천 규칙

### 이용 이력이 없는 임직원

```text
전체 상품
→ 누적 이용자 수 기준 정렬
→ 인기 상품 최대 5개 추천
```

### 이용 이력이 있는 임직원

```text
ACTIVE 상태 이용 이력 조회
→ 가장 많이 이용한 카테고리 계산
→ 같은 카테고리의 미이용 상품 조회
→ 누적 이용자 수 기준 정렬
→ 최대 5개 추천
```

## User Story

> As a **기업 임직원**,  
> I want **내 복지 이용 이력과 선호 카테고리를 기반으로 복지상품을 추천받고 싶다**,  
> So that **많은 복지상품을 일일이 비교하는 시간을 줄이고 회사에서 제공하는 혜택을 놓치지 않고 이용할 수 있다.**

## 과장하면 안 되는 표현

다음 기능은 현재 백엔드에 없으므로 작성하지 않는다.

- AI가 건강상태를 분석한다.
- 생애주기와 가족정보를 분석한다.
- AI가 자연어로 추천 이유를 생성한다.
- 개인별 복지예산을 분석한다.
- 직원 만족도를 예측한다.

정확한 표현은 다음과 같다.

> 이용 이력·최빈 카테고리·인기도를 활용한 규칙 기반 맞춤 추천 MVP

# 5. 도메인 매핑표 작성

교수님이 설명한 대로 이 표를 먼저 작성하면 화면과 사용할 API가 자연스럽게 정해진다.

| 교육 플랫폼 | 복지상품 플랫폼 | 백엔드 유지값 |
|---|---|---|
| 학생 | 임직원 | `STUDENT` |
| 강사 | 복지 제휴사 | `INSTRUCTOR` |
| 강의 | 복지상품 | `Course` |
| 강의 등록 | 복지상품 등록 | `POST /api/courses` |
| 강의 조회 | 복지상품 조회 | `GET /api/courses` |
| 수강신청 | 복지상품 신청 | `Enrollment` |
| 결제 | 복지포인트 사용 | `Payment` |
| 수강 대기 | 포인트 처리 중 | `PENDING` |
| 수강 활성화 | 이용 가능 | `ACTIVE` |
| 수강 취소 | 이용 취소 | `CANCELLED` |
| 수강생 수 | 누적 이용자 수 | `enrollmentCount` |
| 추천 강의 | 맞춤 복지상품 | `Recommend` |
| 내 수강 목록 | 내 복지상품 | My Enrollments |

화면에 보이는 용어만 바꾸고 내부 API 이름과 상태값은 그대로 유지한다.

# 7. 상품 정책 결정

현재 백엔드 결제 요청은 실제 상품 가격과 관계없이 `99,000`으로 고정되어 있다.

따라서 모든 상품을 다음 정책으로 통일한다.

> 모든 상품은 기업이 제공하는 99,000P 정액 복지 이용권이다.

## 상품 예시

- 종합건강검진 이용권
- 심리상담 3회권
- 피트니스 월 이용권
- 문화생활 패키지
- 재무상담 이용권
- 가족 돌봄 지원권
- 국내 휴양시설 이용권

## 화면 표현 변경

| 기존 화면 | 변경 화면 |
|---|---|
| ₩99,000 | 99,000P |
| 결제하고 수강하기 | 복지포인트로 신청하기 |
| 결제 처리 중 | 포인트 처리 중 |
| 수강 중 | 이용 가능 |
| 평생 소장 | 이용권 발급 |
| 수료증 발급 | 모바일 이용권 제공 |

# 9. Sprint 1 진행 방법

## Sprint 1의 의미

Sprint 1은 단순히 더 긴급한 기능을 모으는 단계가 아니다.

> 사용자가 처음부터 끝까지 실제로 사용할 수 있는 가장 얇은 완성 흐름을 만드는 단계다.

## Sprint 1 Goal

> 임직원이 로그인하여 복지상품을 조회하고 하나의 상품을 신청한 뒤 내 복지상품에서 신청 결과를 확인할 수 있게 한다.

## Sprint 1 핵심 시나리오

```text
임직원 로그인
→ 복지상품 목록 조회
→ 카테고리 필터
→ 상품 상세 조회
→ 99,000P 사용
→ 상품 신청
→ 내 복지상품에서 상태 확인
```

## Sprint 1에서 수정할 화면

- 랜딩 화면
- 헤더·메뉴
- 로그인 화면의 역할 표현
- 복지상품 목록
- 복지상품 카드
- 복지상품 상세
- 복지상품 등록
- 내 복지상품 목록

## Sprint 1에서 연결하는 핵심 서비스

- User Service
- Course Service
- Enrollment Service

Payment, Kafka, Recommend는 백엔드에서 원래대로 동작하게 두고 적극적으로 변경하지 않는다.

## Sprint 1 Task 예시

| Task | 담당 | 산출물 |
|---|---|---|
| 서비스명·로고·소개 변경 | 프론트엔드 | 랜딩 화면 |
| 역할명 변환 | 프론트엔드 | 임직원·제휴사 UI |
| 카테고리 매핑 | 프론트엔드 | 복지 카테고리 필터 |
| 상품 목록 API 연결 | 프론트엔드 | 복지상품 목록 |
| 상품 상세 API 연결 | 프론트엔드 | 상세 화면 |
| 신청 API 연결 | 프론트엔드 | 신청 결과 |
| 내 신청 목록 연결 | 프론트엔드 | 내 복지상품 |
| API 확인 | 통합 담당 | Swagger 캡처 |
| E2E 테스트 | 팀 전체 | 데모·결과 기록 |

## Sprint 1 완료 기준

- [ ] 교육 플랫폼 이름과 주요 문구가 복지 플랫폼으로 변경됨
- [ ] 임직원·제휴사 역할이 화면에서 구분됨
- [ ] 실제 API에서 복지상품 목록을 가져옴
- [ ] 상품 상세가 실제 API 데이터로 출력됨
- [ ] 임직원이 상품을 신청할 수 있음
- [ ] 신청 결과가 내 복지상품에 나타남
- [ ] `PENDING` 또는 `ACTIVE` 상태가 화면에 표시됨
- [ ] Swagger와 화면 데이터가 일치함
- [ ] 핵심 E2E 시나리오를 시연할 수 있음

# 11. Sprint 2 진행 방법

## Sprint 2 Goal

> Sprint 1 피드백을 반영하고 복지포인트 처리, 이용 상태, 맞춤 추천 및 제휴사 화면을 완성한다.

## Sprint 2 범위

- 인기 복지상품 추천
- 이용 이력 기반 맞춤 추천
- 추천 카테고리 변환
- 추천 이유 문구
- 포인트 처리 상태 표시
- 이용권 활성화 결과 확인
- 제휴사 마이페이지
- 제휴사 등록 상품 목록
- 누적 이용자 수
- 전체 E2E 통합 테스트

## Sprint 2 핵심 시나리오

```text
복지상품 신청
→ Payment Service가 포인트 처리
→ payment.completed 이벤트
→ Enrollment 상태 ACTIVE
→ 누적 이용자 수 증가
→ enrollment.completed 이벤트
→ Recommend Service가 이용 이력 조회
→ 같은 복지 카테고리 상품 추천
```

## 추천 화면 문구

신규 사용자:

> 임직원들이 가장 많이 선택한 인기 복지상품입니다.

이용 이력이 있는 사용자:

> 건강관리 상품을 이용한 고객님을 위한 맞춤 추천입니다.

백엔드에서 내려주는 원문 메시지를 그대로 출력하지 않고 `basedOnCategory` 값을 프론트에서 복지 카테고리로 변환해 표시한다.

## Sprint 2 완료 기준

- [ ] 인기 추천이 정상 출력됨
- [ ] 이용 이력 기반 추천이 출력됨
- [ ] 이미 이용한 상품은 추천에서 제외됨
- [ ] 추천 카테고리가 복지 용어로 표시됨
- [ ] `PENDING`에서 `ACTIVE`로 상태가 바뀌는 것을 확인함
- [ ] 제휴사가 등록 상품과 이용자 수를 확인할 수 있음
- [ ] Kafka Producer·Consumer 로그를 확인함
- [ ] Sprint 1 기능에 문제가 없음
- [ ] 최종 E2E 데모를 진행함

# 12. API 확인 방법

프론트 코드를 변경하기 전에 Swagger에서 다음 API를 직접 실행한다.

| 기능 | API | 확인할 필드 |
|---|---|---|
| 내 정보 | `GET /api/users/me` | `id`, `name`, `role` |
| 상품 목록 | `GET /api/courses` | `title`, `category`, `price`, `enrollmentCount` |
| 상품 상세 | `GET /api/courses/{id}` | 상세 필드 |
| 상품 등록 | `POST /api/courses` | `title`, `description`, `category`, `price` |
| 상품 신청 | `POST /api/enrollments` | `courseId`, `status` |
| 내 상품 | `GET /api/enrollments/my` | `course`, `status` |
| 추천 | `GET /api/recommend/{userId}` | `recommendedCourses`, `basedOnCategory` |

각 API에 대해 다음 내용을 기록한다.

- Request
- Response
