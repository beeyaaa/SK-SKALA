# 「오늘 뭐 입지?」 개발 과정 및 시행착오

## 1. 프로젝트 시작

처음에는 Vue 문법을 익히기 위해 날씨 데이터를 활용한 개별 Hands-on을 진행했다.

- `v-for`를 이용한 도시 카드 반복 출력
- `v-if`를 이용한 기온별 문구 표시
- `:value`, `@input`을 이용한 한글 검색
- `ref`, `computed`를 이용한 반응형 상태 관리
- `watch`, `watchEffect`를 이용한 상태 변화 감시
- 컴포넌트와 Vue Router를 이용한 화면 분리

초기에는 각 기능이 별도의 실습 예제로만 존재했기 때문에 전체적으로 하나의 서비스처럼 연결되지는 않은 상태였다.

---

## 2. 서비스 방향에 대한 고민

단순히 도시별 날씨 카드만 보여주는 서비스는 기능과 목적이 약하다고 느꼈다. 날씨를 확인한 사용자가 실제로 다음에 궁금해할 만한 내용을 고민한 결과, 날씨에 맞는 옷차림을 추천하는 **「오늘 뭐 입지?」** 서비스로 확장하기로 했다.

기존 Hands-on 코드는 학습 결과를 확인할 수 있도록 날씨 대시보드에 유지하고, 새 서비스는 별도의 `views-clothes` 구조로 분리했다.

- 기존 Hands-on 구현 결과 보존
- 배운 내용을 종합한 새로운 서비스 개발

## 3. 화면 구성 과정

### 3.1 일반적인 날씨 카드에서 지도형 UI로 변경

처음에는 도시별 날씨를 카드 목록으로 표시했다. 그러나 도시의 위치 관계가 보이지 않고 일반적인 날씨 애플리케이션과 차별점이 부족했다.

이를 개선하기 위해 대한민국 지도 위에 주요 도시의 기온과 날씨를 표시하는 방식으로 변경했다.

- 주요 도시를 실제 위치에 가깝게 배치
- 울릉도와 독도를 별도 위치에 표시
- 도시 마커 클릭 시 옷차림 추천 팝업 표시
- 지도 바깥이나 닫기 버튼 클릭 시 팝업 종료

### 3.2 상세 패널과 팝업 사이의 고민

처음에는 화면 오른쪽에 상세 패널을 배치하는 방법도 고려했다. 그러나 도시를 선택하지 않았을 때 큰 빈 공간이 남아 화면 균형이 좋지 않았다.

최종적으로 평상시에는 지도를 넓게 보여주고, 필요한 순간에만 정보를 표시할 수 있는 팝업 방식을 선택했다. 더 자세한 정보는 동적 경로를 이용한 별도 상세 페이지에서 제공했다.

```text
지도 마커 클릭
→ 간단한 옷차림 팝업
→ 상세 날씨 보기
→ /clothes/weather/:cityId 이동
```

## 4. 검색 기능 확장

지도에는 정해진 주요 도시만 표시되기 때문에 다른 지역을 조회할 수 없다는 한계가 있었다.

이를 해결하기 위해 상단에 돋보기 버튼을 두고, 버튼을 누르면 검색창이 나타나도록 구성했다.

- 검색어와 일치하는 지도 마커 필터링
- 검색 결과가 없으면 안내 문구 표시
- OpenWeather Geocoding API를 이용한 외부 도시 검색
- 지도에 없는 검색 도시를 임시 마커로 표시

검색창을 항상 노출하면 상단 영역이 복잡해지기 때문에 온도 단위 변경 버튼 옆에 돋보기 아이콘을 배치했다.

---

## 5. 현재 기온에서 하루 전체 분석으로 확장

초기에는 현재 기온 한 개만 기준으로 옷차림을 추천했다. 하지만 낮에는 덥고 아침과 저녁에는 쌀쌀한 날처럼 하루 중 기온 변화가 큰 경우 적절한 추천을 제공하기 어려웠다.

따라서 시간대별 예보를 다음과 같이 분석하도록 확장했다.

- 아침 시간대와 가장 가까운 예보 선택
- 낮 시간대와 가장 가까운 예보 선택
- 저녁 시간대와 가장 가까운 예보 선택
- 세 시간대의 최저·최고 기온과 일교차 계산
- 강수확률 분석
- 하루 전체를 고려한 종합 추천 문장 생성

예를 들면 다음과 같은 형태로 추천한다.

> 낮에는 따뜻하지만 아침과 저녁에는 기온이 내려가요.  
> 반팔 위에 벗기 쉬운 얇은 재킷을 추천해요.  
> 최고 강수확률이 70%이므로 우산도 준비하세요.

기온 구간별 추천 기준도 세분화하여 반팔, 가디건, 재킷, 코트, 패딩 등으로 결과가 달라지도록 구현했다.

## 6. 외부 API 선택 과정

### 6.1 옷차림 이미지 API 검토

처음에는 Pinterest의 패션 이미지를 이용해 추천 옷차림 예시를 보여주려고 했다. 하지만 Pinterest API는 일반적인 검색 결과를 자유롭게 가져오기 어렵고, 개인 보드를 연결하면 사용자가 제한되는 문제가 있었다.

Unsplash와 Pexels도 검토했지만 날씨에 정확히 대응하는 코디 이미지를 안정적으로 제공하기 어렵다고 판단했다.

결과적으로 이미지 기능을 억지로 추가하기보다 날씨 데이터 분석과 옷차림 추천이라는 서비스의 핵심 기능을 강화하는 방향을 선택했다.

### 6.2 최종 연결 API

- OpenWeather Current Weather API: 현재 기온·습도·풍속·날씨
- OpenWeather Forecast API: 시간대별 기온·강수확률
- OpenWeather Geocoding API: 지도에 없는 도시 검색
- OpenWeather Air Pollution API: PM2.5·PM10 대기질
- 기상청 API Hub: 폭염·한파·호우·대설·태풍·강풍 특보

## 7. 대기질과 기상특보의 옷차림 반영

미세먼지와 기상특보를 단순히 화면에 표시하는 것에서 끝내지 않고 실제 준비물과 추천 문구에 반영했다.

- 미세먼지가 나쁘면 `보건용 마스크` 추가
- 비 올 확률이 높으면 `우산` 추가
- 일교차가 크면 `얇은 겉옷` 추가
- 폭염특보가 있으면 물·모자·통풍이 잘되는 옷 추천
- 한파특보가 있으면 방한용품 추천

기상특보가 있을 때는 일반적인 날씨 정보보다 먼저 확인할 수 있도록 **Weather Safety Mode** 영역을 상세 화면 상단에 배치했다.

## 8. Pinia를 이용한 상태 관리

처음에는 각 컴포넌트 안에서 데이터를 관리했지만, 지도·검색·상세 페이지에서 동일한 날씨 데이터를 공유해야 했다.

이를 위해 Pinia Store를 적용하여 다음 상태를 중앙에서 관리했다.

- 전체 도시 날씨
- 선택된 도시
- 검색어와 날씨 상태 필터
- 온도 단위
- 실시간 날씨
- 시간대별 예보
- 대기질과 기상특보
- 로딩 및 오류 상태

덕분에 지도에서 선택한 도시 정보를 상세 화면에 별도로 전달하지 않아도 동일한 Store에서 사용할 수 있게 되었다.

# 개발 과정에서 겪은 시행착오

## 1. 배운 Vue 문법을 하나의 서비스로 연결하기 어려웠음

초기에는 `v-for`, `v-if`, `computed`, `watch` 등의 문법을 각각 실습했지만, 이를 실제 서비스의 어느 부분에 사용해야 하는지 판단하기 어려웠다.

단순히 과제 조건을 충족하기 위해 문법을 추가하면 불필요한 코드가 될 수 있기 때문에 각 문법이 실제 기능을 담당하도록 구성했다.

- `v-for`: 지도 위 도시 마커와 시간대별 예보 반복 출력
- `v-if`: 로딩·오류·검색 결과·기상특보 조건부 표시
- `computed`: 검색 결과, 옷차림 추천, 하루 기온 분석
- `watch`: 선택 도시와 필터 변경 감시
- `watchEffect`: 검색어 변경 추적

이 과정을 통해 Vue 문법은 단순한 작성 형식이 아니라 상태와 화면을 연결하기 위한 도구라는 점을 이해했다.

## 2. `v-model`과 `:value`, `@input` 선택

일반적으로 검색창에는 `v-model`을 사용하면 양방향 바인딩을 간단하게 구현할 수 있다. 하지만 Hands-on 요구사항에서는 한글 입력 처리를 확인하기 위해 `:value`와 `@input`을 사용하도록 제시되어 있었다.

따라서 편의성을 위해 바로 `v-model`로 변경하지 않고 다음과 같이 구현했다.

- `:value`: 현재 검색어를 입력 요소에 전달
- `@input`: 사용자가 입력한 값을 반응형 상태에 저장
- `computed`: 검색어가 포함된 도시만 필터링

또한 현재 검색은 기본 문자열 포함 방식이므로 `서`, `수`처럼 완성된 음절은 검색되지만 `ㅅ`과 같은 초성만으로는 검색되지 않는다. 초성 검색을 지원하려면 별도의 초성 분리 로직이 필요하지만 현재 과제 범위에서는 일반적인 포함 검색을 유지했다.

## 3. 지도와 도시 마커의 위치가 어긋나는 문제

초기에는 도시 마커의 위치를 직접 퍼센트 좌표로 입력했다. 그러나 화면 크기가 바뀌거나 지도 비율을 조정하면 마커와 지도 위치가 어긋나는 문제가 발생했다.

이를 해결하기 위해 도시의 위도·경도를 지도 내부 좌표로 변환하는 계산 로직을 만들고, 지도와 마커가 동일한 프레임을 기준으로 배치되도록 수정했다.

울릉도와 독도는 실제 지도 비율로 배치하면 화면에서 잘리거나 지나치게 멀리 표시되어 별도의 섬 이미지와 고정 좌표를 이용해 표시했다.

## 4. 팝업 클릭 이벤트가 지도까지 전달되는 문제

팝업 내부 버튼을 클릭했을 때 지도 클릭 이벤트도 함께 실행되어 팝업이 닫히는 이벤트 버블링 문제가 있었다.

이를 해결하기 위해 팝업과 도시 마커의 클릭 이벤트에 `.stop` 수식어를 적용했다. 지도 빈 곳을 클릭했을 때만 팝업이 닫히도록 이벤트 범위를 분리했다.

## 5. 시간대별 추천 데이터 선택 문제

OpenWeather 예보 데이터는 정확히 08시, 13시, 19시에 제공되지 않을 수 있었으며, 단순히 앞에서부터 데이터를 선택하면 서로 다른 날짜의 예보가 한 추천에 섞일 수 있었다.

이를 해결하기 위해 다음 기준을 적용했다.

- 같은 날짜의 예보만 사용
- 아침·낮·저녁 목표 시간에 가장 가까운 예보 선택
- 세 시간대 데이터가 모두 존재할 때만 하루 종합 추천 생성
- 데이터가 부족하면 해당 추천 계산을 생략

이를 통해 서로 다른 날짜의 데이터가 섞이는 문제와 불완전한 추천 생성을 방지했다.

## 6. 추천 문장이 부자연스럽게 표시되는 문제

종합 추천 문장을 조건에 따라 이어 붙이면서 문장 중간에서 줄바꿈되거나 마침표가 빠지는 문제가 있었다.

이를 해결하기 위해 다음 정보를 각각 완성된 문장으로 생성하도록 분리했다.

- 하루 기온 변화 요약
- 추천 옷차림
- 강수확률 안내

화면에서도 문장 단위로 표시하여 사용자가 자연스럽게 읽을 수 있도록 정리했다. 이 과정에서 줄바꿈은 CSS만의 문제가 아니라 데이터를 어떤 단위의 문자열로 구성하는지도 중요하다는 점을 확인했다.

## 7. API Key와 환경변수 관리

처음에는 API Key를 어디에 저장하고 어떻게 Vue 코드에서 사용하는지 익숙하지 않았다. 코드에 직접 작성하면 GitHub에 Key가 노출될 수 있기 때문에 `.env.local`로 분리했다.

```ini
VITE_OPENWEATHER_API_KEY=발급받은_키
VITE_KMA_API_KEY=발급받은_키
```

공개 저장소에는 실제 값이 없는 `.env.example`만 포함하고 `.env.local`은 `.gitignore`로 제외했다. 또한 Vite에서 브라우저가 사용할 환경변수 이름은 `VITE_`로 시작해야 한다는 점을 확인했다.

## 8. 기상청 API 연결의 어려움

OpenWeather API는 JSON 응답을 제공해 비교적 쉽게 처리할 수 있었지만, 기상청 API Hub는 신청한 API와 실제 호출 주소를 맞추는 과정이 어려웠다.

구현 과정에서 다음 내용을 확인하고 수정했다.

- 비슷한 이름의 특보 API 중 신청한 엔드포인트 확인
- 인증키 전달 방식 확인
- 텍스트 형식의 응답 파싱
- EUC-KR 응답 인코딩 처리
- 전체 데이터에서 현재 발효 중인 특보만 필터링
- 특보 지역 코드와 서비스 도시 연결

이를 통해 API 문서에서 이름만 확인하는 것이 아니라 요청 변수, 응답 형식, 인코딩까지 정확히 확인해야 한다는 점을 배웠다.

## 9. CORS 정책으로 기상청 API 요청이 차단되는 문제

Vue 애플리케이션에서 기상청 API로 직접 요청하면 브라우저의 CORS 정책으로 요청이 차단될 수 있었다.

이를 해결하기 위해 Vite Proxy를 사용했다.

```text
Vue 애플리케이션
→ /kma-api 요청
→ Vite 개발 서버 Proxy
→ 기상청 API Hub
```

프론트엔드에서는 동일 출처인 Vite 서버에 요청하고, Vite가 외부 기상청 API로 전달하도록 구성했다. 실제 배포 환경에서는 별도의 백엔드 또는 서버리스 프록시가 필요하다는 점도 확인했다.

## 10. API 실패 시 화면이 비어 보이는 문제 방지

실시간 API만 기준으로 화면을 구성하면 API Key 미설정, 네트워크 오류, 호출 횟수 제한, 데이터 누락 등의 상황에서 서비스가 비어 보일 수 있었다.

따라서 Mock Data를 기본값으로 유지하고 실시간 요청에 성공한 경우에만 데이터를 갱신하도록 설계했다.

- 로딩: `ElSkeleton`
- 오류: `ElAlert`
- 데이터 출처: 실시간 또는 임시 데이터
- 갱신 결과: `ElMessage`

API를 연동할 때는 성공했을 때뿐 아니라 실패했을 때의 사용자 경험도 함께 설계해야 한다는 점을 배웠다.

## 11. Element Plus와 기존 디자인의 충돌

Hands-on 7을 위해 Element Plus를 적용했지만 모든 버튼과 카드를 라이브러리 컴포넌트로 교체하면 기존 디자인의 개성이 사라지는 문제가 있었다.

따라서 기존 지도·팝업·카드·버튼 디자인은 유지하고 공통 상태 표현에만 제한적으로 사용했다.

- `ElSkeleton`: API 로딩 상태
- `ElAlert`: API 오류
- `ElTag`: 대기질 등급과 기상특보
- `ElMessage`: 날씨 갱신 결과

Element Plus의 기본 파란색도 기존 서비스와 어울리지 않아 올리브·오프화이트 색상으로 테마를 조정했다.

기상특보는 처음에 `폭염`과 `주의보`를 각각 별도의 Tag로 표시했지만 하나의 의미가 분리되어 어색해 보였다. 이후 `폭염 주의보`를 단일 Tag로 합쳐 정보 구조를 개선했다.

## 12. 패키지 설치 후 기존 개발 서버에서 오류가 발생함

Element Plus를 설치한 뒤 이미 실행 중이던 Vite 개발 서버가 새 패키지를 즉시 인식하지 못해 모듈을 찾을 수 없다는 오류가 발생했다.

코드와 프로덕션 빌드는 정상적이었으며, 개발 서버를 종료한 뒤 다시 실행하여 해결했다.

```bash
# 기존 서버 종료
Control + C

# 개발 서버 재실행
npm run dev
```

새로운 패키지를 설치하거나 Vite 설정을 변경한 경우 개발 서버를 재시작해야 할 수 있다는 점을 확인했다.

# 시행착오를 통해 알게 된 점

- 과제에서 배운 문법을 실제 기능에 자연스럽게 연결해야 한다.
- 외부 API의 개수보다 서비스 목적과 데이터 품질이 중요하다.
- API의 성공뿐 아니라 로딩, 실패, 데이터 누락 상황도 설계해야 한다.
- 여러 화면에서 사용하는 상태는 Store로 중앙화하면 관리하기 쉽다.
- 외부 UI 라이브러리는 필요한 부분에만 사용해 기존 디자인과 조화를 맞출 수 있다.
- 기능 구현 후 사용자가 정보를 읽는 순서와 화면의 정보 구조를 함께 검토해야 한다.
