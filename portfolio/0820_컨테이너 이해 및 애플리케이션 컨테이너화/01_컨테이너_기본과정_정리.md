# 0. 워밍업 — 프로그램과 프로세스

> 📍 p8~18 | **컨테이너를 이해하는 첫걸음은 "저장된 코드 ≠ 실행 중인 코드"를 구분하는 것**

## 0-1. 카카오톡을 열면 무슨 일이 벌어지나 (p9)

- 앱 아이콘을 누르면 → 저장되어 있던 **'코드'**가 컴퓨터의 **메모리 위에서 '실행'**되기 시작
- **저장된 상태의 코드 ≠ 실행되고 있는 상태**
- 이 둘의 차이를 이해하는 것이 컨테이너를 이해하는 첫걸음

## 0-2. 네 가지 기본 개념 (p10~14)

| 개념 | 🎵 비유로 말하면 | 📖 정확히 말하면 |
|---|---|---|
| **프로그램 (Program)** | 악보 — 종이에 적혀있지만 아직 연주되진 않는 상태 | 컴퓨터에게 시킬 일을 미리 적어둔 파일로, **저장 장치(디스크)** 안에 가만히 있는 상태 |
| **프로세스 (Process)** | 연주자가 악보를 보고 **실제로 연주 중** | 프로그램이 실행되어 **메모리와 CPU를 사용하며** 실제로 동작하고 있는 상태 |
| **운영체제 (OS)** | 오케스트라의 **지휘자** | 하드웨어(CPU·메모리·디스크)와 프로그램 사이에서 자원을 나눠주고 정리 |
| **서버 (Server)** | 24시간 문을 여는 **편의점** | 인터넷에 연결된 채 항상 켜져 있으면서, 다른 컴퓨터의 요청을 받아 응답하는 컴퓨터 |

> ✅ **우리가 흔히 '앱을 켠다'고 말하는 순간이 바로, 프로그램이 프로세스가 되는 순간입니다.** (p12)

> 💡 Windows, macOS, 그리고 오늘 배울 **Linux**가 모두 운영체제입니다.
> 우리가 오늘 만들 컨테이너도, 결국 이 **서버 위에서 실행**됩니다.

# 1. Linux OS 기초

> 📍 p19~49 | **컨테이너와 대화하기 위해 터미널과 친해지기**

## 1-1. 왜 서버는 Linux를 쓸까 (p20)

- 전 세계 서버의 대부분이 Linux 위에서 실행 중 → **가볍고, 안정적이고, 무료**
- **결정적으로, 오늘 배울 '컨테이너'는 사실 Linux의 기술을 빌려 만들어진 것**
- → 컨테이너를 이해하려면 Linux의 기본 동작 방식을 알아야 함

## 1-2. 터미널 (p21~22)

| | |
|---|---|
| 🖱️ **비유로 말하면** | 마우스로 그림을 그리는 대신, 컴퓨터에게 **글자로 직접 말을 거는 대화창** |
| 📖 **정확히 말하면** | 마우스 클릭 없이, 글자로 된 명령어를 입력해 컴퓨터를 조작하는 화면 |

**마우스 클릭 vs 터미널 명령어** — 둘 다 '컴퓨터에게 시키는 방법'

| 🖱️ 마우스로 클릭하기 | ⌨️ 터미널에 타이핑하기 |
|---|---|
| 눈에 보이는 아이콘을 클릭 | 글자로 된 명령어를 입력 |
| 직관적이고 배우기 쉬움 | 처음엔 낯설지만 **빠르고 정확함** |
| 같은 작업을 반복하려면 매번 클릭 | 같은 명령어를 저장해두면 **재사용 가능** |
| 정확히 같은 결과를 재현하기 어려움 | **서버 컴퓨터를 다룰 때는 사실상 필수** |

## 1-3. 리눅스의 파일 정리 방식 — 나무 이야기 (p23)

Windows의 '내 PC, C드라이브' 대신, 리눅스는 **뿌리(root) 하나에서 시작**합니다.

```plain text
/ (루트) ─── 나무의 뿌리, 모든 것이 여기서 시작
├── /home ─── 나뭇가지 하나, 나만의 개인 폴더
├── /etc  ─── 또 다른 가지, 설정 파일들이 모인 곳
└── ...
```

## 1-4. 명령어 하나씩 (p24~37)

### 📍 위치와 이동

| 명령어 | 줄임말 | 비유 | 예시 |
|---|---|---|---|
| `pwd` | **P**rint **W**orking **D**irectory | "저 지금 어디 있어요?" | `pwd` → `/home/student` |
| `ls` | **l**i**s**t | "이 방 안에 뭐가 있어요?" | `ls -al` (숨겨진 파일까지 자세히) |
| `cd` | **C**hange **D**irectory | "다른 방으로 이동하실게요" | `cd Documents` / `cd ..` (상위 폴더) |

### 📁 파일 만들고 다루기

| 명령어 | 줄임말 | 비유 | 예시 |
|---|---|---|---|
| `mkdir` | **m**a**k**e **dir**ectory | 새 서랍을 만드는 것 | `mkdir project` |
| `touch` | — | 서랍 안에 **빈 종이 한 장** 넣어두기 | `touch app.py` |
| `cp` | **c**o**p**y | 서류를 복사기에 넣는 것 | `cp a.txt b.txt` |
| `mv` | **m**o**v**e | 다른 서랍으로 옮기거나 **새 이름표**를 붙이기 | `mv a.txt archive/` |
| `rm` | **r**e**m**ove | 종이를 **파쇄기**에 넣는 것 | `rm -r 폴더명` |

> ⚠️ **`rm`은 휴지통을 거치지 않고 완전히 사라집니다.**
> `rm -r 폴더명` 을 실행하기 전, 정말 지울 폴더가 맞는지 **꼭 한번 더** 확인하세요.

### 📄 내용 보기

| 명령어 | 비유 | 설명 | 예시 |
|---|---|---|---|
| `cat` | 편지를 처음부터 끝까지 다 읽기 | 파일 **전체** 내용을 화면에 출력 | `cat app.log` |
| `tail` | 편지의 **마지막 몇 줄만** 훑어보기 | 파일 뒷부분만 출력. **최근 로그 확인**에 자주 사용 | `tail -n 20 app.log` |
| `grep` | 긴 책에서 원하는 단어가 있는 **페이지만** 찾아주기 | 파일이나 결과 안에서 문자열 검색 | `cat app.log \| grep ERROR` |

### 🔑 권한 — 열쇠 이야기 (p36~37)

모든 파일에는 '누가 열어볼 수 있고, 누가 고칠 수 있는지' 정해진 **열쇠 규칙**이 있습니다.

```plain text
       소유자    같은 그룹   그 외 모두
       ┌────┐   ┌────┐   ┌────┐
       │ rwx │   │ r-x │   │ r-- │
       └────┘   └────┘   └────┘
   r = 읽기(read)  w = 쓰기(write)  x = 실행(execute)
```

- 이 열쇠는 **소유자 / 같은 그룹 / 그 외 모든 사람** 세 그룹에 각각 따로 적용
- 스크립트 파일을 실행하려면 **'실행 권한(x)'이라는 열쇠**가 필요

| 명령어 | 줄임말 | 비유 | 예시 |
|---|---|---|---|
| `chmod` | **ch**ange **mod**e | 문에 **새 자물쇠**를 달아 누가 들어올 수 있는지 바꾸기 | `chmod +x deploy.sh` |

### ⚙️ 프로세스 (p38)

- 컴퓨터 안에는 지금 이 순간에도 여러 프로그램이 동시에 '일'하는 중
- `ps -ef` — 지금 일하고 있는 **모든 프로세스의 명단**
- `kill` — 너무 오래 일하거나 문제가 생긴 프로세스를 멈추기

> ✅ 이 개념은 잠시 후 **'컨테이너 = 프로세스'**를 이해할 때 다시 등장합니다.

## 1-5. 쉘 스크립트 — 할 일 목록 자동화 (p39~42)

명령어를 매번 하나씩 입력하기 귀찮다면, **순서대로 적어서 한 번에 실행**합니다. 확장자는 `.sh`.
**변수 · 조건문 · 반복문**, 이 세 가지만 알아도 충분합니다.

```bash
#!/bin/bash

# ① 변수 — 자주 바뀌는 값에 이름표 붙이기
APP_NAME="my-app"
echo "안녕하세요, $APP_NAME 입니다"

# ② 조건문 — "만약 우산이 있으면 밖에 나간다"와 같은 논리
if [ -f "app.py" ]; then
    echo "app.py 파일이 있어요"
else
    echo "app.py 파일이 없어요"
fi

# ③ 반복문 — "1번부터 3번까지 순서대로 인사하기"
for i in 1 2 3; do
  echo "$i 번째 인사입니다"
done
```

> ⚠️ **대괄호 `[ ]` 양옆에는 꼭 띄어쓰기를 해주세요 — 가장 흔한 실수입니다.**

## 1-6. [실습] 나만의 폴더 만들어보기 (p43)

## 1-7. 명령어 한 장 총정리 (p46)

| 명령어 | 한 줄 뜻 |
|---|---|
| `pwd` / `ls` / `cd` | 위치 확인 / 목록 보기 / 이동 |

| `cp` / `mv` / `rm` | 복사 / 이동·이름 변경 / 삭제 |
| `cat` / `tail` / `grep` | 전체 읽기 / 끝부분 읽기 / 검색 |
| `ps` / `kill` | 프로세스 확인 / 종료 |

# 2. 컨테이너 기본

> 📍 p50~101 | **비유로 먼저 이해하고, 그 다음에 손으로 직접 만들어봅니다**

## 2-1. 생각해보기 — 이사할 때 이야기 (p51)

이사를 가는 세 가지 방법을 상상해봅시다.

```plain text
① 트럭 하나에 살림살이를 그냥 다 쏟아붓고 옮긴다    →  Bare-metal
   (뒤죽박죽, 깨지기 쉬움)

② 방마다 큰 박스 하나씩 통째로 옮긴다             →  VM
   (안전하지만 박스가 무겁고 큼)

③ 물건마다 딱 맞는 작은 상자에 잘 포장해서 옮긴다   →  Container
   (가볍고, 어디서든 바로 풀어 쓸 수 있음)
```

## 2-2. 옛날 방식 — Bare-metal (p52~57)

> 컴퓨터 한 대에 프로그램을 **그냥 직접 설치해서 쓰는 방식**

**【 It means… 】** Bare-metal은 운영체제(OS)를 바로 설치해 사용하던 **물리 서버**.
"철판 위에(OS를 얹어)" 바로 Application을 사용 — 데이터 센터의 여러 Rack, 그 Rack 안에 작은 단위의 서버 여러 개가 동작.

### 문제점 3가지 (p57)

| 문제점 1 — 한 서버에 여러 앱 어려움 | 문제점 2 — 환경 설정이 지옥 | 문제점 3 — 장애 시 서버 자체가 죽음 |
|---|---|---|
| 한 서버에 Django+Python 앱과 Spring+Java 앱을 동시에 올리면? | 앱 하나 배포 시 → 라이브러리 설치 → OS 설정 변경 → 방화벽 수정 → 사용자가 직접 모든 설정 체크 | 물리 서버 전원·디스크·RAM 문제 → **바로 전체 서비스 중단** |
| → 라이브러리 버전 충돌 | **20대 서버 = 20번 반복** | 복구 시간 보통 **수 시간 ~ 수십 시간** |
| → 자바와 파이썬이 CPU·메모리를 서로 잡아먹음 | | 24시간 서비스 가능… but |
| → 하나가 죽으면 서버 전체가 불안정 | | |
| 💣 **달걀 한 바구니 흔들기** | 💣 **"환경 세팅이 개발자의 시간을 잡아먹는 괴물"** | 💣 **"서버 1대가 죽으면 회사가 죽는다."** |

## 2-3. 그 다음 방식 — VM (p58~62)

> 한 건물(컴퓨터)을 여러 개의 **독립된 원룸(가상 컴퓨터)**으로 나누는 방식

```plain text
┌─────────────────────────────────────┐
│  VM 1     │  VM 2     │  VM 3       │
│ ┌───────┐ │ ┌───────┐ │ ┌───────┐   │
│ │  App  │ │ │  App  │ │ │  App  │   │
│ │  Lib  │ │ │  Lib  │ │ │  Lib  │   │
│ │Guest OS│ │ │Guest OS│ │ │Guest OS│  │ ← 원룸마다 부엌·화장실을 통째로 새로 지음
│ └───────┘ │ └───────┘ │ └───────┘   │
├─────────────────────────────────────┤
│           Hypervisor                │ ← VM 관리 프로그램
├─────────────────────────────────────┤
│           Hardware                  │
└─────────────────────────────────────┘
```

**【 VM이란? 】**
- 하드웨어 위에 **Hypervisor**(VM 관리 프로그램) 설치
- 그 위에 가상의 컴퓨터(**Guest OS**) 여러 개 생성
- 각 VM은 독립된 컴퓨터처럼 행동 — 자체 OS / 자체 라이브러리 / 자체 파일 시스템

- ✅ 각 원룸은 완전히 독립되어 있어 옆방에 영향을 주지 않음
- ⚠️ 하지만 **원룸마다 부엌, 화장실을 통째로 새로 짓는 것**과 같아서 무겁고, 짓는 데 시간이 오래 걸림

## 2-4. 지금 방식 — Container (p63~69)

> 건물의 **공용 주방(운영체제)은 같이 쓰되, 도시락(컨테이너)만 따로**

```plain text
┌─────────────────────────────────────┐
│ ┌──────┐  ┌──────┐  ┌──────┐        │
│ │ App  │  │ App  │  │ App  │        │ ← 도시락 하나하나는
│ │ Lib  │  │ Lib  │  │ Lib  │        │   서로 섞이지 않게 잘 포장
│ └──────┘  └──────┘  └──────┘        │
├─────────────────────────────────────┤
│      Container Engine (Docker)      │
├─────────────────────────────────────┤
│         Host OS  ← 커널 공유         │ ← 건물 전체를 다시 안 지어도 됨
├─────────────────────────────────────┤
│           Hardware                  │
└─────────────────────────────────────┘
```

**【 컨테이너란? 】**
- **OS 커널을 공유**하면서
- 앱 실행에 필요한 **라이브러리, 설정만 묶어서 패키징**한 것 (= Docker 이미지)
- VM = 무거운 집 전체 / **Container = 필요시 빌려 쓰는 게스트하우스**

> ⚠️ **컨테이너가 많아질수록 오히려 운영이 어려워집니다.** (p69)
> → 이것이 다음 과정 **쿠버네티스**가 필요한 이유입니다.

## 2-5. 세 가지 방식, 한눈에 비교 (p70)

| Bare-metal | VM → Container |
|---|---|
| 한 방에 다 같이 (**격리 없음**) | **VM**: 건물을 통째로 나눔 (무거움) |
| 충돌 위험이 큼 | **Container**: 도시락만 따로 (가벼움) |
| 설치·설정에 시간이 오래 걸림 | 지금은 대부분 Container를 사용 |

## 2-6. 컨테이너 (p71)

| | |
|---|---|
| 🍱 **비유로 말하면** | 잘 포장된 **도시락**. 어디로 가져가든 뚜껑만 열면 바로 먹을 수 있습니다. |
| 📖 **정확히 말하면** | 프로그램이 실행되는 데 필요한 **모든 것(코드, 라이브러리, 설정)을 하나로 포장**해, 어떤 컴퓨터에서든 똑같이 실행되게 만든 상자 |

> ✅ 그래서 **"내 컴퓨터에서는 되는데요?"** 라는 문제가 컨테이너를 쓰면 크게 줄어듭니다.

## 2-7. ⭐ 이미지 vs 컨테이너 (p72)

| | |
|---|---|
| 🐟 **비유로 말하면** | **붕어빵 틀과 붕어빵의 관계.** 틀(이미지)은 하나지만, 그 틀로 붕어빵(컨테이너)을 여러 개 구워낼 수 있습니다. |
| 📖 **정확히 말하면** | **이미지**는 '실행되기 전, 저장된 설계도', **컨테이너**는 '그 이미지로 실제 실행되고 있는 것' |

| 이미지 (Image) | 컨테이너 (Container) |
|---|---|
| 붕어빵 **틀** | 실제로 구워진 **붕어빵** |
| **저장**되어 있는 상태 | **실행**되고 있는 상태 |
| 하나로 여러 컨테이너 생성 가능 | 같은 이미지로 여러 개 생성 가능 |

> ✅ **아까 배운 프로그램(이미지) vs 프로세스(컨테이너)와 정확히 같은 관계!**

```plain text
  프로그램  :  프로세스   =   이미지  :  컨테이너
  (저장됨)    (실행 중)      (저장됨)   (실행 중)
```

| | |
|---|---|
| 🏭 **비유로 말하면** | 붕어빵 틀을 만들고, 굽고, 포장까지 도와주는 **만능 기계** |
| 📖 **정확히 말하면** | 컨테이너를 쉽게 **만들고, 실행하고, 관리**할 수 있게 도와주는 프로그램(도구) |

## 2-9. ⭐ Dockerfile 6대 명령어 (p79~84)

레시피를 순서대로 적는다고 생각하면 됩니다.

| 명령어 | 🍳 비유로 말하면 | 📖 정확히 말하면 | 예시 |
|---|---|---|---|
| **`FROM`** | "이 요리는 밥을 베이스로 시작할게요" | 어떤 **베이스 이미지**로 시작할지 정함. **항상 첫 줄** | `FROM python:3.10-slim` |
| **`WORKDIR`** | "오늘 요리는 이 도마 위에서 하실게요" | 앞으로의 작업이 이루어질 **작업 디렉토리** 지정 | `WORKDIR /app` |
| **`COPY`** | 내 냉장고 재료를 도마 위로 옮겨오기 | 내 컴퓨터의 파일을 **이미지 안으로 복사** | `COPY app.py .` |
| **`RUN`** | "재료를 씻고 다듬어주세요" | **이미지를 만드는 시점(빌드 타임)**에 실행. 주로 라이브러리 설치 | `RUN pip install flask` |
| **`EXPOSE`** | "손님은 정문으로 들어오실게요" | 이 컨테이너가 **몇 번 문(포트)으로 손님을 받을지 적어두는 안내문** | `EXPOSE 5000` |
| **`CMD`** | "완성된 요리를 손님상에 내어드릴게요" | **컨테이너가 시작될 때(런타임)** 자동 실행할 명령어. 주로 마지막 줄 | `CMD ["python", "app.py"]` |

> 💡 **`RUN`과 `CMD`의 차이가 핵심입니다.**
> `RUN` = **이미지를 만들 때** 한 번 실행 (재료 손질) / `CMD` = **컨테이너를 켤 때마다** 실행 (요리 내어드리기)

## 2-10. [실습] 첫 이미지 만들고 실행하기 (p85~92)

```bash
# 1) 기존 컨테이너 삭제
docker rm -f my-container

# 2) app.py 작성
cat << 'EOF' > app.py
from flask import Flask

app = Flask(__name__)

@app.route('/')
def hello():
    message = "Docker yarrrrrrrr!!!!!"
    print(message, flush=True)
    return f"<h1>{message}</h1>"

if __name__ == '__main__':
    app.run(host='0.0.0.0', port=5000)
EOF

# 3) Dockerfile 작성
cat << 'EOF' > Dockerfile
FROM python:3.10-slim
WORKDIR /app
RUN pip install flask
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
EOF

# 4) 캐시 없이 깨끗하게 재빌드
docker build --no-cache -t my-app:1.0 .
docker images                          # 목록에 있는지 확인

# 5) 컨테이너 실행
docker run -d -p 8080:5000 --name my-container my-app:1.0
docker ps                              # 실행 중인지 확인
#  → 브라우저에서 http://localhost:8080

# 6) 정리
docker stop my-container
docker rm my-container
```

> 💡 **Dockerfile의 한 줄 = 빌드의 한 단계.** `docker build` 로그에 지나가는 메시지가 바로 그 단계들입니다.
> `-t my-app:1.0` 은 이미지에 **이름표(태그)**를 붙이는 옵션입니다.

## 2-11. ⭐ docker run 주요 옵션 (p93~97)

| 옵션 | 줄임말 | 🎯 비유로 말하면 | 📖 정확히 말하면 |
|---|---|---|---|
| **`-d`** | **d**etached | 가게 문은 열어두되, 사장님은 뒤에서 조용히 일하기 | 터미널을 계속 붙잡지 않고 **백그라운드**로 계속 실행 |
| **`-p`** | **p**ort | 건물 정문(내 컴퓨터 포트)과 가게 안쪽 문(컨테이너 포트)을 잇는 **통로** | `-p 5000:5000` = 내 컴퓨터 5000번 문을 컨테이너 5000번 문과 연결 |
| **`--name`** | — | 번호표 대신 **예쁜 이름표** 달아주기 | 복잡한 ID 대신 이름으로 컨테이너를 다룰 수 있음 |
| **`--network`** | — | 같은 **아파트 단지**에 입주하면 동·호수(이름)만 불러도 찾아감 | 아무 설정 없이는 컨테이너끼리 이름으로 통신 **불가**. 같은 네트워크에 연결해야 가능 |
| **`-e`** | **e**nvironment | "이 앱아, DB는 board-db라는 곳에 있어"라고 **쪽지** 남기기 | 컨테이너 안에 **환경변수**를 심어줌. 앱 코드가 이 쪽지를 읽어 접속 주소를 결정 |

```bash
docker network create board-net
docker run --name board-db  --network board-net -d postgres:17
docker run --name board-was --network board-net -e DB_HOST=board-db -d board-was:1.0
```

## 2-12. 자주 쓰는 Docker 명령어 모음 (p98)

| 명령어 | 내용 |
|---|---|
| `docker ps` | 지금 **실행 중인** 컨테이너 목록 보기 |
| `docker ps -a` | **멈춘 것까지 포함**한 전체 목록 보기 |
| `docker exec -it <이름> sh` | 컨테이너 **안으로 들어가 셸 실행** ※ 원문 설명 오류 → [검증 노트](#️-원문-용어-검증-노트) 참고 |
| `docker logs <이름>` | 컨테이너가 남긴 기록(로그) 보기 |
| `docker stop <이름>` | 컨테이너 멈추기 |
| `docker rm <이름>` | **멈춘** 컨테이너 삭제 |

| | |
|---|---|

## 3-1. 네트워크와 포트 (p103~104)

| 개념 | 🛣️ 비유로 말하면 | 📖 정확히 말하면 |
|---|---|---|
| **네트워크 (Network)** | 컴퓨터와 컴퓨터를 잇는 **도로** | 여러 컴퓨터(또는 컨테이너)가 서로 데이터를 주고받을 수 있게 연결된 통로 |
| **포트 (Port)** | 아파트의 **호수**(101호, 102호) — 같은 건물이라도 몇 호로 찾아가느냐가 다름 | 한 컴퓨터 안에서 여러 프로그램을 구분하기 위한 번호. 웹사이트는 보통 **80번** |

## 3-2. [실습] 포트 번호 바꿔서 실행해보기 (p105)

```bash
docker run -d -p 8080:5000 my-app:1.0
```
| 접속 주소 | 결과 |
|---|---|
| `http://localhost:8080` | ✅ 열림 |
| `http://localhost:5000` | ❌ 안 열림 |

> ⭐ **`-p 호스트포트:컨테이너포트`** — 내가 접속할 문 번호를 정하는 건 **앞쪽(호스트) 숫자**입니다.

## 3-3. 컨테이너끼리는 어떻게 대화할까 (p106)

- 컨테이너는 **기본적으로 서로 격리**되어 있음
- 같은 **'네트워크'**에 연결하면 대화 가능 → **컨테이너 이름만으로 서로를 찾을 수 있음**
- WAS 컨테이너에서 `db` 라는 **이름만으로** DB 컨테이너에 연결
- 오늘 종합실습에서 이 방식을 직접 사용

## 3-4. 스토리지가 왜 필요할까 — 기억상실 문제 (p108)

> ⚠️ **컨테이너를 지우면, 그 안에 저장했던 데이터도 함께 사라집니다.**

- 마치 도시락을 다 먹고 버리면, 안에 있던 음식도 같이 사라지는 것
- 회원가입 데이터처럼 **계속 남아있어야 하는 정보**에는 치명적
- 이 문제를 해결하는 것이 바로 **'볼륨'**

## 3-5. 볼륨 (p109~110)

| | |
|---|---|
| 🏬 **비유로 말하면** | 도시락과 **별개로 마련된 창고**. 도시락(컨테이너)을 버려도 창고(볼륨)의 물건은 그대로 |
| 📖 **정확히 말하면** | 컨테이너 **바깥**에 데이터를 저장해두는 공간. 컨테이너가 삭제돼도 볼륨의 데이터는 남음 |

### Bind Mount vs Named Volume

| Bind Mount | Named Volume |
|---|---|
| 내 컴퓨터의 **특정 폴더를 그대로 연결** | **Docker가 알아서 관리**하는 창고 |
| 코드를 수정하면 **바로 반영**됨 | DB처럼 **계속 남아야 할 데이터**에 적합 |
| **개발할 때** 특히 편리함 | 어느 컴퓨터로 옮겨도 잘 동작함 |

## 3-6. [실습] 볼륨 만들어보기 (p111)

```bash
docker volume create my-data                          # ① 볼륨 생성
docker volume ls                                      # ② 만들어졌는지 확인
docker run -d -v my-data:/data alpine sleep 1000      # ③ 볼륨을 연결해 실행
docker volume inspect my-data                         # ④ 상세 정보 확인
```

## 🧩 Quiz (p113~114)

**Q. 컨테이너를 삭제해도 데이터가 남아있게 하려면 무엇을 써야 할까요?**
→ **볼륨(Volume)** ✅ — 볼륨은 컨테이너 바깥의 창고이므로, 컨테이너가 사라져도 데이터는 그대로 남습니다.

## ✅ 네트워크 · 스토리지, 이것만은 기억하세요 (p115)

| | |
|---|---|
| 포트는 한 컴퓨터 안에서 프로그램을 구분하는 번호 | `-p 호스트포트:컨테이너포트` 로 외부와 연결 |
| 같은 네트워크의 컨테이너는 **이름으로 서로 통신** 가능 | 컨테이너를 지우면 안의 데이터도 함께 사라진다 |
| **볼륨을 쓰면 컨테이너가 사라져도 데이터는 남는다** | |

## 4-3. 이미지 태그 (p119)

| | |

| 🏷️ **비유로 말하면** | 붕어빵 틀에 붙이는 이름표 — "팥 붕어빵 v1", "슈크림 붕어빵 v2" |

## 4-4. 이미지는 여러 층으로 쌓여있다 — 레이어 (p120)

**Dockerfile의 한 줄, 한 줄이 이미지의 한 '층(레이어)'**이 됩니다.

```plain text
┌──────────────────────────┐
│ CMD ["python","app.py"]  │  ← 레이어 6
├──────────────────────────┤
│ EXPOSE 5000              │  ← 레이어 5
├──────────────────────────┤
│ COPY . .                 │  ← 레이어 4  ★ 코드 수정 시 여기부터만 다시
├──────────────────────────┤
│ RUN pip install flask    │  ← 레이어 3  (캐시 재사용)
├──────────────────────────┤
│ WORKDIR /app             │  ← 레이어 2  (캐시 재사용)
├──────────────────────────┤
│ FROM python:3.10-slim    │  ← 레이어 1  (캐시 재사용)
└──────────────────────────┘
```

- 마치 **케이크가 여러 층으로 쌓여있는 것**과 같음
- 코드 한 줄만 바뀌어도 **전체를 처음부터 다시 만들 필요 없이, 바뀐 층만** 새로 만들면 됨
- 이 원리는 **Day 2 / 심화자료**에서 더 자세히 다룸

## 5-1. 시작 전 환경 재확인 (p132)

## 5-2. 코드 리뷰란 무엇인가 (p133~134)

> 코드 리뷰는 — **서로의 코드를 보며 함께 이야기하는 것**

- **"이 부분은 왜 이렇게 작성했어요?"** 라고 물어보는 것부터 시작
- **정답을 맞히는 시험이 아니라**, 서로 다른 접근을 보고 배우는 시간
- 실무에서도 코드 리뷰는 실력을 가장 빠르게 키우는 방법 중 하나
- 진행 방식: 두 명이 서로 동료가 되어 각자 작성하고 서로의 코드를 리뷰. **정답을 바로 알려주는 대신, 체크리스트로 스스로 점검**

## 5-3. 3-tier 구조 (p136)

| Web | WAS | DB |
|---|---|---|
| 정적 화면(HTML) 역할 | 요청 처리하는 프로그램 | 게시글 데이터를 실제로 저장 |
| **nginx**로 서비스 | Web과 DB 사이 연결 | **PostgreSQL** 사용 |

## 5-4. 진행 순서 로드맵 (p137)

```plain text
STEP 1     STEP 2      STEP 3      STEP 4      STEP 5      STEP 6
폴더 준비 → Web 이미지 → WAS 이미지 → DB 실행  →  연결     → 확인
web, was   화면용       서버용      PostgreSQL  세 컨테이너를 브라우저로

          작성·빌드     작성·빌드    실행         연결
```

## 5-5. Step 0~1 — 환경 정리와 폴더 준비 (p138~139)

# [Step 1] 프로젝트 폴더 준비

board/
├── web/    ← 화면 (nginx)

## 5-6. Step 2 — Web(화면) Dockerfile (p140)

```dockerfile
# web/Dockerfile
FROM nginx:alpine
COPY index.html /usr/share/nginx/html/index.html
EXPOSE 80
```
> 💡 nginx는 **화면을 보여주는 데 특화된 가벼운 웹서버** 이미지입니다.

## 5-7. Step 3 — WAS(서버) Dockerfile (p141)

```dockerfile
# was/Dockerfile
FROM python:3.10-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
EXPOSE 5000
CMD ["python", "app.py"]
```

```text
# was/requirements.txt
flask
psycopg2-binary
```

> 💡 **`COPY requirements.txt` → `RUN pip install` → `COPY . .` 순서가 중요합니다.**
> 코드만 바뀌었을 때 `pip install` 레이어를 캐시로 재사용할 수 있기 때문입니다. (4-4 레이어 참고)

## 5-8. Step 4 — DB 컨테이너 실행 (p142)

```bash
docker network create board-net

docker run --name board-db --network board-net \
  -e POSTGRES_PASSWORD=mypassword \
  -e POSTGRES_DB=board \
  -d postgres:17

docker ps
```

## 5-9. Step 5 — 세 컨테이너를 네트워크로 연결 (p143)

```bash
docker build -t board-was:1.0 ./was
docker run --name board-was --network board-net \
  -e DB_HOST=board-db -p 5001:5000 -d board-was:1.0

docker build -t board-web:1.0 ./web
docker run --name board-web --network board-net \
  -p 8080:80 -d board-web:1.0
```

> ⭐ **`DB_HOST=board-db`** — **컨테이너 이름을 그대로 주소로 쓸 수 있는 것**이 네트워크의 힘입니다.

```plain text
                board-net (Docker 네트워크)
  ┌───────────────────────────────────────────────────┐
  │  board-web        board-was          board-db     │
  │  nginx:alpine  →  Flask         →    postgres:17  │
  │  :80              :5000               :5432       │
  └───┬─────────────────┬─────────────────────────────┘
      │                 │
  호스트 :8080      호스트 :5001
```

## 5-10. Step 6 — 브라우저로 실행 확인 (p144)

```bash
docker ps                    # 세 컨테이너 모두 Up 상태인지
#   → 브라우저 http://localhost:8080 (Web)
#   → 화면에서 글쓰기를 시도해, WAS를 거쳐 DB에 저장되는지 확인
docker logs board-was        # DB 연결 로그 확인
#   * Serving Flask app 'app'
#   * Running on http://172.18.0.3:5000
#   [DB 연결 성공] board-db:5432 접속 완료
```

## 5-11. 코드 리뷰 체크리스트 (p150)

- [ ] Dockerfile의 `FROM`에 적절한 **베이스 이미지**를 사용했는가
- [ ] **불필요한 파일까지 `COPY`**하지는 않았는가
- [ ] `EXPOSE` 포트와 실제 `-p` 옵션의 포트가 맞는가
- [ ] **환경 변수(`DB_HOST` 등) 이름이 코드와 일치**하는가
- [ ] **컨테이너 이름이 서로 겹치지** 않는가

| **컨테이너를 지우면 이미지도 지워지나요?** | • 불가<br>• 이미지(틀)와 컨테이너(붕어빵)는 **별개**<br>• **`docker rmi`**로 따로 지워야 함 |

## 5-14. 트러블슈팅 가이드 (p154)

| 증상 | 점검 순서 |
|---|---|
| **WAS가 DB에 연결 못 함** | ① 같은 `--network`인지 ② `DB_HOST` 값이 컨테이너 이름과 같은지 |
| **Web에서 화면이 안 보임** | ① `docker ps`로 `board-web`이 Up인지 ② `-p` 포트 확인 |
| **글쓰기가 저장되지 않음** | `docker logs board-was` 로 에러 메시지 확인 |

# 7. 컨테이너 구조

> 📍 p168~179 | **컨테이너가 사실은 무엇으로 이루어져 있는지 깊이 들어갑니다**

## 7-1. 컨테이너는 사실 무엇일까 (p169)

> ⭐ **컨테이너는 사실 특별한 종류의 '프로세스'입니다.**

- 컨테이너는 **가상의 컴퓨터가 아니라**, 우리 컴퓨터(호스트) 안에서 살짝 **'눈가림'된 프로세스**
- 그래서 컨테이너는 VM처럼 무겁지 않고, **순식간에 실행**될 수 있음

## 7-2. Namespace와 cgroups (p170~171)

| 기술 | 🧱 비유로 말하면 | 📖 정확히 말하면 |
|---|---|---|
| **Namespace** | 칸막이가 있는 **독서실**. 같은 방에 있어도 서로 다른 사람은 안 보이게 **시야**를 막아둔 것 | 컨테이너마다 프로세스·네트워크 등을 **서로 안 보이게 나눠주는** 리눅스 기술. 이 덕분에 컨테이너는 서로 독립된 것처럼 보임 |
| **cgroups** | 각자에게 정해진 **용돈**만큼만 쓸 수 있게 하는 것 | 컨테이너마다 CPU·메모리를 얼마나 쓸 수 있는지 **제한**하는 리눅스 기술. 한 컨테이너가 자원을 독차지하지 못하게 막음 |

> 💡 외우는 법: **Namespace는 '시야', cgroups는 '용돈'을 나눠준다.**
> (cgroups = **c**ontrol **groups**)

## 7-3. [실습] 컨테이너도 결국 프로세스 (p172)

```bash
docker run -d --name demo nginx

# ① 컨테이너 안에서 확인 (Namespace 덕분에 자기 혼자만 보임)
docker exec demo cat /proc/1/status | head -2
#   Name:   nginx
#   State:  S (sleeping)
#   → 컨테이너 안에서는 PID 1이 nginx 자신! (호스트에서는 PID 1이 아님)

# ② 호스트(내 컴퓨터)에서 컨테이너의 실제 프로세스를 확인
docker top demo
#   UID   PID   PPID  C  STIME  TTY  TIME      CMD
#   root  4821  4802  0  15:03  ?    00:00:00  nginx: master process
#   101   4867  4821  0  15:03  ?    00:00:00  nginx: worker process
#   → 호스트 관점에서는 평범한 프로세스 번호(PID)를 가지고 있음
```

> ⭐ 컨테이너 안(**PID 1**)과 호스트에서 보는 번호(**PID 4821**)가 서로 다름
> = **Namespace가 "번호표"를 새로 매겨준 것**

## 7-4. 컨테이너 네트워크, 다시 한번 (p173)

- 어제 만든 `board-net`도 사실 Docker가 만들어준 **'작은 도로망'**
- Docker는 기본적으로 컨테이너를 위한 **가상 도로(bridge network)**를 자동으로 준비
- 같은 도로 위에 있는 컨테이너끼리는 **이름을 주소처럼** 사용

## 7-5. 컨테이너 플랫폼 (p174~175)

Docker는 컨테이너 기술 그 자체라기보다는, **쉽게 쓰도록 도와주는 '도구 모음'**입니다.
실제로 컨테이너를 실행하는 **더 낮은 수준의 엔진들**이 Docker 내부에서 동작 중입니다.

| 이름 | 설명 |
|---|---|
| **Docker** | 가장 널리 쓰이는 표준 도구 (지금 배우는 중) |
| **containerd** | Docker 내부에서도 실제로 일하는 엔진 ※ 원문 표기 `containered` → [검증 노트](#️-원문-용어-검증-노트) |
| **Podman** | Docker와 비슷하지만 **데몬(daemon) 없이** 동작 |
| **CRI-O** | **쿠버네티스 전용**으로 만들어진 경량 엔진 |

> 💡 지금은 **"Docker 말고도 다른 도구가 있구나"** 정도만 알아도 충분합니다.

## 🧩 Quiz (p177~178)

**Q. 컨테이너마다 CPU·메모리 사용량을 제한하는 기술은?**
→ **cgroups** ✅ — cgroups는 자원 사용량에 **상한선**을 두는 기술. Namespace는 '시야'를, cgroups는 '용돈'을 나눠준다고 기억하세요.

## ✅ 컨테이너 구조, 이것만은 기억하세요 (p179)

| | |
|---|---|
| 컨테이너는 가상 컴퓨터가 아니라 **특별한 프로세스** | **Namespace**는 서로 안 보이게 나눠주는 칸막이 |
| **cgroups**는 자원 사용량을 제한 | Docker 외에도 **containerd, Podman** 같은 도구 |

# 8. Registry와 Docker Compose

> 📍 p180~209 | **이미지를 창고에 보관하고, 여러 컨테이너를 한 번에 지휘하는 법**

## 8-1. Registry (p181~182)

| | |
|---|---|
| 🏬 **비유로 말하면** | 이미지를 보관하는 **창고**. 내가 만든 붕어빵 틀을 다른 사람도 꺼내 쓸 수 있게 맡겨두는 곳 |
| 📖 **정확히 말하면** | 만든 이미지를 **저장하고 공유**할 수 있는 저장소. 다른 컴퓨터에서도 이 창고에서 이미지를 꺼내 쓸 수 있음 |

**Docker Hub** — 가장 유명한 공개 창고
- 어제 사용한 `nginx`, `postgres`, `python` 이미지도 모두 여기서 가져온 것
- 회사에서는 외부에 공개하고 싶지 않은 이미지를 위해 **자체 비공개 창고(Private Registry)**를 두기도 함

## 8-2. tag → push → pull (p183~186)

> ⭐ **`docker login` → `docker tag` → `docker push`** — 이 순서를 기억하세요. **로그인 없이는 창고 문이 열리지 않습니다.**

```bash
$ docker tag board-was:1.0 skalateny/board-was:1.0
$ docker images
REPOSITORY            TAG   IMAGE ID       CREATED          SIZE
skalateny/board-was   1.0   a1b2c3d4e5f6   10 minutes ago   180MB
board-was             1.0   a1b2c3d4e5f6   10 minutes ago   180MB
board-web             1.0   f6e5d4c3b2a1   12 minutes ago   45MB

$ docker push skalateny/board-was:1.0
```
> 💡 `<Docker Hub 아이디>` 자리에는 본인이 **실제 회원가입한 아이디**를 넣어야 push가 정상 동작합니다.
> 💡 태그가 같은 IMAGE ID를 공유하는 것에 주목 — **태그는 이름표일 뿐, 이미지 본체는 하나**입니다.

**pull** — `docker pull`로 창고에서 이미지를 꺼내옴
- 다른 컴퓨터에서도 같은 이미지를 pull 받으면 **완전히 똑같은 프로그램**을 실행 가능
- 사실 어제 쓴 `docker run postgres:17`도, 처음 실행할 때 **자동으로 pull이 먼저 일어난 것**

## 8-3. 문제 제기 — 여러 컨테이너를 한 번에? (p187)

- 어제는 Web, WAS, DB를 켤 때 `docker run`을 **세 번이나 따로** 입력
- 컨테이너가 늘어나면, 매번 순서대로 옵션을 다 기억해서 입력하기 **너무 번거로움**
- → 이 문제를 해결하는 도구가 **Docker Compose**

## 8-4. Docker Compose (p188~189)

| | |
|---|---|
| 🎼 **비유로 말하면** | **오케스트라 지휘자.** 여러 연주자(컨테이너)에게 각자의 악보를 미리 나눠주고, **지휘봉 한 번**으로 다 함께 연주를 시작하게 함 |
| 📖 **정확히 말하면** | 여러 컨테이너를 **하나의 파일**에 미리 적어두고, **명령어 한 번**으로 한꺼번에 실행·종료할 수 있게 해주는 도구 |

**Compose가 해주는 일 세 가지**
1. 여러 컨테이너를 **파일 하나로** 정리해서 관리
2. 컨테이너 간 **네트워크를 자동으로 생성** (`docker network create` 안 해도 됨)
3. **`up`** 명령어 하나로 전부 켜고, **`down`** 하나로 전부 끔

## 8-5. docker-compose.yml 첫인상 (p190)

> 낯설어 보이지만, 사실 **어제 쓴 `docker run` 옵션들을 파일로 옮겨 적은 것뿐**입니다.

```yaml
services:
  was:
    build: ./was
    ports:
      - "5000:5000"
    environment:
      - DB_HOST=db
  db:
    image: postgres:17
    environment:
      - POSTGRES_PASSWORD=1234
```

## 8-6. ⭐ Compose 문법 — docker run 옵션과 1:1 대응 (p191~197)

| Compose 항목 | 대응하는 `docker run` | 설명 |
|---|---|---|
| **`services`** | — | 지휘자의 악보에서 **"오늘 연주할 사람들" 목록**. 실행할 컨테이너들을 적는 가장 큰 영역 |
| **`ports`** | `-p` | 호스트 포트와 컨테이너 포트를 연결. **`"5000:5000"` 처럼 따옴표로 감싸 적음** |
| **`environment`** | `-e` | 컨테이너 안에서 사용할 환경 변수. DB 주소나 비밀번호 등 |
| **`depends_on`** | — | "이 요리는 저 요리가 끝난 다음에 시작하세요"라고 **순서**를 정하는 것 |
| **`volumes`** | `-v` | 데이터를 보존할 볼륨 연결. **파일 맨 아래에 볼륨 이름을 한 번 더 선언**해야 함 |
| **`build`** | `docker build` | "레시피 보고 **직접 만들기**" — Dockerfile로 이미지를 만들 때 (우리가 만든 web·was) |
| **`image`** | — | "이미 만들어진 것 **사오기**" — 이미 존재하는 이미지를 그대로 쓸 때 (공식 db) |

## 8-7. Compose 명령어 (p196, p199)

**켜고 끄기**

| 명령어 | 의미 |
|---|---|
| `docker compose up -d` | 파일에 적힌 **모든 컨테이너를 한 번에 실행** |
| `docker compose down` | 모든 컨테이너를 한 번에 **종료·삭제** |

**확인하기**

| 명령어 | 의미 |
|---|---|
| `docker compose ps` | 지금 실행 중인 **서비스 목록** 확인 |
| `docker compose logs -f <서비스명>` | 특정 서비스의 로그를 **실시간**으로 확인 |
| `docker compose build` | Dockerfile을 **다시 읽어 이미지 재생성** |

## 8-8. Compose 파일, 자주 하는 실수 (p198)

| 실수 | 고치는 법 |
|---|---|
| **들여쓰기에 탭 사용** | **스페이스만** 사용하도록 통일 |
| **콜론(`:`) 뒤에 공백 빠뜨림** | `key: value` 처럼 콜론 뒤 **한 칸 띄우기** |
| **따옴표 짝이 안 맞음** | `"8080:80"` 처럼 여는 따옴표와 닫는 따옴표 확인 |

> ⚠️ **YAML 파일은 들여쓰기가 아주 중요합니다 — 탭 대신 스페이스를 사용하세요.**

## 8-9. 1일차 방식 vs 2일차 방식 (p200)

| 1일차 — `docker run` | 2일차 — Docker Compose |
|---|---|
| 명령어를 여러 번 따로 입력 | **파일 하나에 전부 선언** |
| 네트워크를 직접 만들어야 함 | **네트워크가 자동으로 생성됨** |
| 컨테이너가 늘어나면 관리가 복잡해짐 | **`up`/`down` 명령 하나로 전체 관리** |

## 8-10. [실습] 첫 Compose 파일 (p201~205)

```bash
$ mkdir compose-practice && cd compose-practice
$ cat << 'EOF' > docker-compose.yml
services:
  web:
    image: nginx
    ports:
      - "8090:80"
EOF

$ docker compose up -d
[+] Running 2/2
 ✔ Network compose-practice_default   Created  0.1s
 ✔ Container compose-practice-web-1   Started  0.4s

$ docker compose ps
NAME                     IMAGE   SERVICE  STATUS         PORTS
compose-practice-web-1   nginx   web      Up 4 seconds   0.0.0.0:8090->80/tcp

#  → 브라우저 http://localhost:8090 에서 "Welcome to nginx!" 가 뜨면 성공

$ docker compose down
[+] Running 2/2
 ✔ Container compose-practice-web-1   Removed  0.3s
 ✔ Network compose-practice_default   Removed  0.1s
```

> 💡 `docker compose ps` 출력에서 컨테이너 이름 앞에 **폴더명이 자동으로 붙습니다** (`폴더명-web-1` 형태).
> 💡 `down`을 실행하면 컨테이너뿐 아니라 **`up`이 자동으로 만든 네트워크까지** 정리됩니다.
> → **"Compose가 네트워크까지 알아서 만들고 치워준다"**

## 🧩 Quiz (p207~208)

**Q. 여러 컨테이너를 한 번에 실행하는 Compose 명령어는?**
→ **`docker compose up -d`** ✅ — 파일에 적힌 모든 서비스를 한 번에 백그라운드로 실행

## ✅ Docker Compose, 이것만은 기억하세요 (p209)

| | |
|---|---|
| Registry는 이미지를 보관하는 **창고** | **tag → push → pull** 순서로 이미지를 공유 |
| Compose는 여러 컨테이너를 한 파일로 관리하는 **지휘자** | `services`, `ports`, `environment`, `depends_on`, `volumes`가 **핵심 문법** |
| **`up`/`down`으로 전체를 켜고 끌 수 있다** | |

# 9. 종합 실습 2 — Compose로 3-tier 재완성

> 📍 p210~240 | **손으로 직접 연결했던 3-tier 미니 게시판을 Compose로 훨씬 쉽게 완성**
> 1일차 Dockerfile은 **그대로 재사용**하고, `docker-compose.yml`만 새로 작성합니다.

## 9-1. 시작 전 환경 재확인 (p211)

- [ ] 어제 만든 `board` 폴더가 그대로 남아있는가
- [ ] `docker ps -a` 로 켜져 있는 이전 컨테이너를 정리했는가
- [ ] `docker compose version` 이 정상적으로 출력되는가

## 9-2. 목표 (p214)

| 1일차 | 2일차 |
|---|---|
| `docker run`을 **세 번** | `docker-compose.yml` **파일 하나** |
| `docker network create`도 따로 실행 | `docker compose up` **한 줄** |

## 9-3. 코드 리뷰, 이렇게 질문해보세요 (p212)

> 무엇을 물어야 할지 모르겠다면 아래 질문을 그대로 사용해도 좋습니다.

| 상황 | 질문 예시 |
|---|---|
| 서비스 이름이 낯설 때 | "이 서비스 이름은 왜 이렇게 지었어요?" |
| `environment` 값이 다를 때 | "이 값은 어디서 가지고 온 거에요?" |
| 구조가 다르게 짜여 있을 때 | "이 방식으로 하면 어떤 점이 더 편해요?" |

## 9-4. Step 1 — 어제 폴더 재사용 (p217~218)

```bash
$ cd board
$ ls -al
drwxr-xr-x  4 user  staff  128  8월 19 09:00 was
drwxr-xr-x  4 user  staff  128  8월 19 09:00 web

$ docker ps -a
#  (어제 컨테이너가 남아있다면 여기 표시됨 → docker rm -f 로 정리)
```

## 9-5. Step 2~4 — 서비스 하나씩 정의 (p219~221)

**① Web 서비스** — 어제 작성한 `web/Dockerfile`을 그대로 `build`에 연결
```yaml
services:
  web:
    build: ./web
    ports:
      - "8080:80"
    depends_on:
      - was
```

**② WAS 서비스** — 어제 `-e`로 직접 넣었던 환경 변수를 `environment`로 옮김
```yaml
  was:
    build: ./was
    ports:
      - "5001:5000"
    environment:
      - DB_HOST=db
    depends_on:
      - db
```
> ⭐ **`DB_HOST=db`** — `db`는 아래에서 정의할 **서비스 이름과 정확히 같아야** 합니다.

**③ DB 서비스** — 공식 postgres 이미지와, 데이터를 지킬 볼륨
```yaml
  db:
    image: postgres:17
    environment:
      - POSTGRES_PASSWORD=1234
      - POSTGRES_DB=board
    volumes:
      - board-data:/var/lib/postgresql/data

volumes:
  board-data:
```
> 💡 PostgreSQL의 데이터 저장 경로는 **`/var/lib/postgresql/data`** 입니다.

## 9-6. Step 5 — 전체 합치기 (p222)

```yaml
services:
  web:
    build: ./web
    ports: ["8080:80"]
    depends_on: [was]

  was:
    build: ./was
    ports: ["5001:5000"]
    environment:
      - DB_HOST=db
    depends_on: [db]

  db:
    image: postgres:17
    environment:
      - POSTGRES_PASSWORD=1234
      - POSTGRES_DB=board
    volumes: ["board-data:/var/lib/postgresql/data"]

volumes:
  board-data:
```

> ⚠️ 원문 p222에서는 was의 ports가 `"5000:5000"`으로 되어 있으나, p220과 예상화면(p227)은 **`5001:5000`** 기준입니다. → [검증 노트](#️-원문-용어-검증-노트)

## 9-7. Step 6~8 — 실행하고 확인 (p223~229)

```bash
$ docker compose build
[+] Building 4.8s (16/16) FINISHED
 => [web 1/2] FROM docker.io/library/nginx:alpine
 => [was 3/4] RUN pip install --no-cache-dir -r requirements.txt

$ docker compose up -d
[+] Running 4/4
 ✔ Network board_default   Created
 ✔ Container board-db-1    Started      ← db
 ✔ Container board-was-1   Started      ← was
 ✔ Container board-web-1   Started      ← web  (depends_on 순서대로)

$ docker compose ps
NAME          IMAGE         SERVICE  STATUS         PORTS
board-db-1    postgres:17   db       Up 10 seconds  5432/tcp
board-was-1   board-was     was      Up 10 seconds  0.0.0.0:5001->5000/tcp
board-web-1   board-web     web      Up 10 seconds  0.0.0.0:8080->80/tcp

$ docker compose logs -f was

board-was-1  | [DB 연결 성공] db:5432 접속 완료

$ docker compose logs -f db

```

**최종 확인 — 볼륨이 진짜 데이터를 지키는지**
```bash
#  브라우저 http://localhost:8080 → 글쓰기 테스트 → 목록에 반영 확인
$ docker compose down       # 컨테이너·네트워크 전부 삭제
$ docker compose up -d      # 다시 실행
#  브라우저 새로고침 → 조금 전 작성한 글이 그대로 남아있음
#  → volumes(board-data) 덕분에 컨테이너를 지웠다 다시 만들어도 데이터가 유지됨 ✅
```

> ⚠️ **`depends_on`은 "순서"만 보장하지, "준비 완료"는 보장하지 않습니다.** (p226, p233)
> → 이걸 해결하는 것이 심화자료의 **healthcheck**입니다.

## 9-8. 코드 리뷰 체크리스트 (p230)

- [ ] `services` 아래 **들여쓰기가 일관되게** 되어 있는가
- [ ] 각 서비스의 `build` 경로 또는 `image` 이름이 정확한가
- [ ] `depends_on` 순서가 **실제 의존 관계**와 맞는가
- [ ] `environment`의 `DB_HOST` 값이 **`db` 서비스 이름과 일치**하는가
- [ ] `volumes`가 **최상위와 서비스 내부 양쪽**에 모두 선언되어 있는가

| | — 브라우저 화면 |

## 9-10. 자주 발생하는 오류 (p233~234)

**(1) 연결 문제**

| 증상 | 점검 사항 |
|---|---|
| **WAS 로그에 DB 연결 실패** | `DB_HOST`를 `localhost`로 적지 않았는지 확인 (**서비스 이름 `db`여야 함**) |
| **DB가 준비되기 전에 WAS가 먼저 시도** | `depends_on`은 **순서만 보장**. 완전히 준비될 때까지 기다려주진 않음 |

**(2) 문법 문제**

| 증상 | 점검 사항 |
|---|---|
| **파일을 읽지 못한다는 오류** | 들여쓰기에 **탭이 섞여있지 않은지** 확인 (스페이스만 사용) |
| **코드를 고쳤는데 반영이 안 됨** | **`docker compose build` 후 `up`** 해야 새 이미지가 반영됨 |
| **포트 충돌 오류** | 8080, 5000번을 다른 프로그램이 이미 쓰고 있지 않은지 확인 |

# ★ 시험/면접 대비 핵심 문답

| # | 질문 | 답 |
|---|---|---|
| 1 | 프로그램과 프로세스의 차이는? | 프로그램 = **디스크에 저장된** 코드 / 프로세스 = **메모리·CPU를 쓰며 실행 중**인 상태 |
| 2 | 이미지와 컨테이너의 차이는? | 이미지 = 저장된 **설계도(붕어빵 틀)** / 컨테이너 = 그 이미지로 **실행 중인 것(붕어빵)**. 하나의 이미지로 여러 컨테이너 생성 가능 |
| 3 | 컨테이너가 VM보다 가벼운 이유는? | VM은 **Guest OS를 통째로** 올리지만, 컨테이너는 **호스트 커널을 공유**하고 앱과 라이브러리만 패키징하기 때문. 실체는 **Namespace·cgroups로 격리된 프로세스** |
| 4 | Dockerfile 6대 명령어는? | `FROM`(베이스) / `WORKDIR`(작업 폴더) / `COPY`(파일 복사) / `RUN`(**빌드 시** 실행) / `EXPOSE`(포트 안내) / `CMD`(**실행 시** 실행) |
| 5 | `RUN`과 `CMD`의 차이는? | `RUN`은 **이미지 빌드 시점**에 한 번 실행되어 레이어로 남음 / `CMD`는 **컨테이너 시작 시점**에 실행됨 |
| 6 | `-p 8080:5000`의 의미는? | **호스트 8080번 → 컨테이너 5000번**. 내가 브라우저로 접속하는 건 **앞쪽 숫자(8080)** |
| 7 | 컨테이너끼리 이름으로 통신하려면? | **같은 Docker 네트워크**에 연결. 그러면 컨테이너 이름이 그대로 호스트명(주소)이 됨 |
| 8 | `DB_HOST`에 `localhost`를 쓰면 안 되는 이유는? | 컨테이너 안에서 `localhost`는 **그 컨테이너 자기 자신**을 의미하기 때문. 상대 컨테이너의 **이름**을 써야 함 |
| 9 | 컨테이너를 지워도 데이터를 남기려면? | **볼륨(Volume)** 사용. 볼륨은 컨테이너 바깥의 저장 공간 |
| 10 | Bind Mount와 Named Volume의 차이는? | Bind Mount = **내 폴더를 직접 연결**(개발 중 실시간 반영) / Named Volume = **Docker가 관리**(DB 등 영속 데이터) |
| 11 | Namespace와 cgroups의 차이는? | Namespace = **'시야'** 격리(PID·Network·Mount 등) / cgroups = **'용돈'** 제한(CPU·메모리 상한) |
| 12 | Registry에 이미지를 올리는 순서는? | **`docker login` → `docker tag` → `docker push`** |
| 13 | Docker Compose가 해주는 일 3가지는? | ① 여러 컨테이너를 **파일 하나로 관리** ② **네트워크 자동 생성** ③ **`up`/`down`으로 전체 제어** |
| 14 | Compose의 `build`와 `image` 차이는? | `build` = Dockerfile로 **직접 만들기** / `image` = 이미 있는 이미지 **가져다 쓰기** |
| 15 | `depends_on`의 한계는? | **시작 순서만 보장**하고, 해당 서비스가 **실제로 요청을 받을 준비가 됐는지는 보장하지 않음** → `healthcheck` + `condition: service_healthy` 필요 |
| 16 | 컨테이너를 지우면 이미지도 지워지나? | 아니오. **별개**이며 `docker rmi`로 따로 삭제 |
| 17 | 코드를 고쳤는데 Compose에 반영이 안 되면? | **`docker compose build` 후 `up`**. `up`만으로는 기존 이미지를 재사용함 |

| 4 | p175 컨테이너 플랫폼 | **containered** | **containerd** | "컨테이너드"로 읽는 저수준 런타임. 심화자료 p25에는 `containerd`로 올바르게 표기됨 |
| 5 | p175 Podman 설명 | "관리자 프로그램 없이 동작" | **데몬(daemon) 없이 동작 = 데몬리스(daemonless)** | Docker Daemon에 대응하는 개념. Appendix p246에서 '데몬'을 이미 정의하고 있으므로 그 용어를 쓰는 게 일관됨 |
