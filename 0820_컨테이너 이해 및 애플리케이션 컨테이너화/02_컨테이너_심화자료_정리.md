# 1. Dockerfile · 이미지 심화

> 📍 p3~16 | **빌드를 더 빠르게, 이미지를 더 작고 안전하게 만드는 기법들**

## 1-1. Multi-stage Build, 한 걸음 더 (p4~5)

기본 과정에서 배운 **2단계(build → 운영)** 구조를 더 세분화할 수 있습니다.

- 스테이지를 **3개 이상**으로 나눠 **의존성 설치 / 테스트 / 최종 빌드**를 분리
- 각 스테이지에 이름을 붙여(`AS build`, `AS test`) 다른 스테이지에서 **선택적으로 참조**
- **`docker build --target`** 옵션으로 특정 스테이지까지만 빌드해 **디버깅** 가능

```dockerfile
FROM python:3.10 AS deps
WORKDIR /app
COPY requirements.txt .
RUN pip install --user -r requirements.txt

FROM deps AS test
COPY . .
RUN pytest

FROM python:3.10-slim AS final
COPY --from=deps /root/.local /root/.local
COPY . .
CMD ["python", "app.py"]
```

```bash
docker build --target test .    # 테스트 단계까지만 검증
```

```plain text
  deps (python:3.10)  ──▶  test (deps 기반)  ──▶  final (python:3.10-slim)
  의존성 설치               pytest 실행           런타임만 남은 가벼운 이미지
       └────────── COPY --from=deps ─────────────────┘
```

## 1-2. BuildKit (p6)

Docker의 **차세대 빌드 엔진**으로, 지금은 **기본으로 활성화**되어 있습니다.

- 여러 레이어를 **병렬로 빌드**해 속도 향상
- 빌드 캐시를 더 정교하게 관리하고, **필요 없는 스테이지는 아예 Skip**
- 구버전은 `DOCKER_BUILDKIT=1` 환경 변수로 활성화 / **최신 Docker는 기본값**

## 1-3. 캐시 마운트 — 라이브러리 캐시 재사용 (p7)

BuildKit의 **`--mount=type=cache`**로, pip/npm 캐시를 **레이어 밖에 별도로** 보관할 수 있습니다.

```dockerfile
# syntax=docker/dockerfile:1
FROM python:3.10-slim
WORKDIR /app
COPY requirements.txt .
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt
```

> ⭐ 일반 레이어 캐시와 달리, 이 캐시는 **이미지 레이어에 남지 않으면서도 빌드마다 재사용**됩니다.
> → 이미지는 작아지고, 빌드는 빨라집니다.

## 1-4. .dockerignore, 한 걸음 더 (p8)

| 기본 | 심화 |
|---|---|
| `node_modules`, `.git` 제외 | **`.env`, `*.pem`, `*.key` 같은 민감 파일도 반드시 제외** |
| `*.log` 제외 | 테스트 코드·문서(`docs/`, `tests/`)도 **운영 이미지에서는 제외 고려** |
| 불필요한 파일 COPY 방지 | 패턴은 **`.gitignore`와 유사한 문법** 사용 가능 |

## 1-5. Distroless 이미지 (p9)

| | |
|---|---|
| 🛏️ **비유로 말하면** | **가구 하나 없이 침대만 있는 방** — 필요한 것만 딱 있고, 불필요한 게 없습니다 |
| 📖 **정확히 말하면** | 쉘(bash 등)이나 **패키지 매니저조차 없는** 최소한의 이미지. **공격자가 침투해도 활용할 도구 자체가 없어** 보안에 유리 |

> 💡 `gcr.io/distroless/python3` 처럼 **구글이 공식 배포**하는 이미지들이 있습니다.

## 1-6. 이미지 취약점, 왜 스캔해야 할까 (p10~11)

- 베이스 이미지 안에는 **우리가 모르는 오래된 라이브러리**가 있을 수 있음
- 이미지를 그대로 배포하면, **그 취약점도 함께 배포**됨
- **Trivy, Grype** 같은 오픈소스 스캐너로 알려진 취약점(**CVE**)을 미리 확인
- **CI/CD 파이프라인에 스캔 단계**를 넣으면, 취약한 이미지가 배포되기 전에 **자동 필터링**

### [자율실습] Trivy로 이미지 스캔하기

```bash
brew install trivy              # ① 설치 (또는 공식 문서의 설치 방법)
trivy image my-was:1.0          # ② 스캔
#   → 출력되는 CVE 목록에서 심각도(CRITICAL, HIGH) 확인
#   → 베이스 이미지를 더 최신 버전으로 바꾸면 취약점이 줄어드는지 비교
```

> ⭐ **베이스 이미지를 최신으로 유지하는 것만으로도 상당수의 취약점을 예방**할 수 있습니다.

## 1-7. 멀티 아키텍처 빌드 (p12~14)

### 왜 필요한가

- 인텔(**AMD64**) 서버 외에 **Apple Silicon**, ARM 기반 서버(**AWS Graviton** 등)가 늘어남
- Mac(ARM)에서 빌드한 이미지가 **인텔 서버에서 안 돌아가는 경우**도 있음
- **하나의 이미지 태그 아래에 여러 아키텍처용 이미지를 함께 묶어두는 것**이 '멀티 아키텍처 이미지'

### docker buildx

| | |
|---|---|
| 🧵 **비유로 말하면** | 한 벌의 옷을 **여러 사이즈로 동시에** 만들어주는 재봉틀 |
| 📖 **정확히 말하면** | Docker의 확장 빌드 도구. 여러 CPU 아키텍처(AMD64, ARM64 등)를 위한 이미지를 **한 번에 빌드하고 묶어서 업로드** |

```bash
# 빌더 인스턴스 생성 (최초 1회)
docker buildx create --use

# AMD64, ARM64 두 아키텍처를 동시에 빌드 후 push
docker buildx build --platform linux/amd64,linux/arm64 \
  -t <registry>/my-was:1.0 --push .
```

> ⚠️ `--push` 없이 로컬에만 두고 싶다면 `--load`를 쓰되, **이 경우 단일 플랫폼만 가능**합니다.

## 1-8. 이미지 최적화 체크리스트 (p15)

| 점검 항목 | 왜 중요한가 |
|---|---|
| **경량 베이스 이미지 사용** | 이미지 크기, **공격 표면** 감소 |
| **Multi-stage build 적용** | **빌드 도구가 운영 이미지에 남지 않음** |
| **`.dockerignore` 정비** | **민감 파일 유출 방지**, 빌드 속도 향상 |
| **취약점 스캔 습관화** | 알려진 **CVE를 배포 전에 차단** |
| **태그 버전 명시** | **롤백**과 배포 이력 관리 용이 |

## ✅ 1장 정리 (p16)

| | |
|---|---|
| Multi-stage build는 **3단계 이상**으로도 세분화 가능 | **BuildKit과 캐시 마운트**로 빌드 속도 향상 |
| **Distroless** 이미지는 공격 표면을 최소화 | **Trivy** 같은 도구로 알려진 취약점을 스캔 가능 |
| **buildx**로 여러 CPU 아키텍처용 이미지를 한 번에 빌드 | |

# 2. 컨테이너 내부 동작 원리

> 📍 p17~27 | **실제 커널 명령어로 컨테이너의 원리를 직접 체험**

## 2-1. ⭐ Namespace 종류, 자세히 보기 (p18)

> 기본 과정에서는 '칸막이'로 뭉뚱그려 배웠다면, 이번엔 **종류별로** 나눠봅니다.

| Namespace 종류 | 격리 대상 |
|---|---|
| **PID** | 프로세스 번호 체계 |
| **Network** | 네트워크 인터페이스, IP, 포트 |
| **Mount** | 파일 시스템 마운트 지점 |
| **UTS** | 호스트 이름 (hostname) |
| **IPC** | 프로세스 간 통신 (공유 메모리 등) |
| **User** | 사용자·그룹 ID (UID/GID) |

> 💡 기본 과정의 `docker top` 실습에서 본 **"컨테이너 안 PID 1 ≠ 호스트 PID 4821"**이 바로 **PID Namespace**의 효과입니다.

## 2-2. [자율실습] unshare로 나만의 Namespace 만들기 (p19)

**Docker 없이도, 리눅스 명령어만으로** 격리된 공간을 만들 수 있습니다.

```bash
# 새로운 PID, Mount, UTS Namespace를 가진 쉘 실행
sudo unshare --pid --mount --uts --fork bash

# 새 쉘 안에서 호스트 이름을 바꿔본다
hostname my-namespace
hostname
#   → my-namespace

# 다른 터미널(원래 쉘)에서 hostname을 확인하면 그대로임을 확인
```

> ⭐ **Docker가 내부적으로 사용하는 것과 같은 원리 — Docker는 이 과정을 자동화해준 것**입니다.

## 2-3. [자율실습] nsenter로 컨테이너 내부 들여다보기 (p20)

`docker exec`이 실제로는 무엇을 하는지, **더 낮은 레벨에서** 확인합니다.

```bash
# ① 실행 중인 컨테이너의 (호스트 기준) PID 확인
docker inspect --format '{{.State.Pid}}' my-was
#   → 12345 (예시)

# ② 해당 프로세스의 namespace로 직접 진입
sudo nsenter --target 12345 --pid --mount --net bash
```

> ⭐ **`docker exec`은 `nsenter`와 비슷한 원리로 동작** — 실행 중 컨테이너의 namespace로 진입하는 것입니다.

## 2-4. cgroups v2, 조금 더 깊이 (p21)

실제 **파일 시스템 레벨**에서 확인할 수 있습니다.

- 리눅스는 **`/sys/fs/cgroup`** 아래에 **가상의 파일**로 자원 제한을 표현
- **cgroups v2**에서는 이 계층 구조가 **통합**되어, **하나의 트리**로 CPU·메모리·I/O를 함께 관리

## 2-5. [자율실습] 메모리 제한을 걸고 일부러 OOM 유발 (p22)

제한을 넘어서면 실제로 무슨 일이 일어나는지 눈으로 점검합니다.

```bash
# ① 20MB 제한을 걸고 대용량 배열 생성 시도
docker run --memory=20m --name oom-test python:3.10-slim python -c "a=[0]*10**8"

# ② 컨테이너 상태 확인 → Exited (137)
docker ps -a

# ③ OOM으로 종료됐는지 확인
docker inspect oom-test --format '{{.State.OOMKilled}}'
#   → true

# ④ --memory 값을 넉넉하게 늘려 다시 실행해 정상 동작을 비교
```

> ⭐ **종료 코드 137은 커널이 강제로 프로세스를 죽였다는 신호** — **SIGKILL(9), 즉 128 + 9 = 137**입니다.

## 2-6. OverlayFS (p23~24)

| | |
|---|---|
| 🎞️ **비유로 말하면** | 여러 장의 **투명 필름을 겹쳐서** 하나의 그림처럼 보이게 하는 것 |
| 📖 **정확히 말하면** | 이미지의 여러 레이어를 **하나로 겹쳐 보여주는** 리눅스 파일시스템. 실제로는 여러 층이지만, **컨테이너 입장에서는 하나의 파일시스템** |

```bash
docker inspect my-was --format '{{json .GraphDriver}}' | python3 -m json.tool
```
```json
{
  "Data": {
    "LowerDir":  "/var/lib/docker/overlay2/.../diff:...",
    "MergedDir": "/var/lib/docker/overlay2/.../merged",
    "UpperDir":  "/var/lib/docker/overlay2/.../diff"
  }
}
```

| 구성 | 의미 |
|---|---|
| **LowerDir** | **읽기 전용** 레이어들 (이미지에서 온 층) |
| **UpperDir** | **현재 컨테이너가 쓴 변경분** |
| **MergedDir** | **합쳐진 최종 모습** (컨테이너가 보는 파일시스템) |

```plain text
   MergedDir  ← 컨테이너가 보는 화면 (하나처럼 보임)
      ▲
   ┌──┴──────────────┐
   │  UpperDir       │  ← 컨테이너가 쓴 변경분 (쓰기 가능)
   ├─────────────────┤
   │  LowerDir (n)   │  ┐
   │  LowerDir (2)   │  ├ 이미지 레이어 (읽기 전용)
   │  LowerDir (1)   │  ┘
   └─────────────────┘
```

> 💡 기본 과정 p120 **"Dockerfile 한 줄 = 한 레이어"**가 실제 파일시스템에서 이렇게 구현되어 있습니다.
> 컨테이너를 지우면 **UpperDir만 사라지는 것** — 그래서 데이터가 날아가고, 볼륨이 필요한 것입니다.

## 2-7. containerd와 runc의 관계 (p25)

| containerd | runc |
|---|---|
| 이미지 pull, 컨테이너 **생명주기 관리** | 실제로 **Namespace·cgroups를 만들어** 프로세스를 격리 실행 |
| Docker Daemon이 **내부적으로 사용** | **OCI 표준을 구현한 저수준 실행기** |
| **Kubernetes의 기본 런타임** | containerd가 이 runc를 **호출해** 컨테이너를 실행 |

```plain text
  docker CLI  →  Docker Daemon  →  containerd  →  runc  →  [Namespace + cgroups]
                                                              = 컨테이너
```

## 2-8. OCI 표준 (p26)

**Open Container Initiative** — 컨테이너 생태계가 **서로 호환되기 위한 약속**

- **Image Spec**(이미지 포맷)과 **Runtime Spec**(실행 방식), 두 가지를 표준화
- 덕분에 **Docker로 만든 이미지를 Podman이나 Kubernetes에서도 그대로 실행** 가능

## ✅ 2장 정리 (p27)

| | |
|---|---|
| Namespace는 PID, Network, Mount 등 **6가지 이상**으로 세분화 | **`unshare`, `nsenter`**로 Docker 없이도 격리 원리를 확인 가능 |
| cgroups는 **`/sys/fs/cgroup`** 파일 시스템으로 표현 | 메모리 제한 초과 시 **OOM Killer가 강제 종료 (exit 137)** |
| **OverlayFS**는 여러 레이어를 하나로 합쳐 보여주는 파일시스템 | **containerd가 runc를 호출**해 실제 컨테이너를 실행 |

# 3. 운영 관점 — 보안 · 리소스

> 📍 p28~39 | **실 환경에서의 보안과 자원 관리 이야기**

## 3-1. 컨테이너 보안, 기본 원칙 (p29)

> ⚠️ **컨테이너는 격리되어 있지만, 완벽히 안전한 것은 아닙니다.**

| 원칙 | 내용 |
|---|---|
| **최소 권한 원칙** | 필요한 권한만 부여 |
| **최소 이미지 원칙** | 불필요한 도구가 없을수록 **공격 표면 감소** |
| **최신 유지 원칙** | 베이스 이미지와 라이브러리를 **주기적으로 업데이트** |

## 3-2. 루트리스 컨테이너 (p30~31)

| | |
|---|---|
| 🔑 **비유로 말하면** | 손님에게 **집 전체 열쇠 대신, 손님방 열쇠만** 주는 것 |
| 📖 **정확히 말하면** | 컨테이너 안의 프로세스가 **관리자(root) 권한 없이** 실행되도록 하는 방식. **컨테이너가 뚫려도 피해 범위를 최소화** |

### [자율실습] --user 옵션으로 비루트 사용자 실행

```bash
docker run --user 1000:1000 -it python:3.10-slim whoami
#   ② 컨테이너 안에서 id 명령으로 UID/GID가 1000인지 확인
```

```dockerfile
# ③ Dockerfile 마지막에 한 줄 추가하면 기본 사용자로 지정됨
USER appuser
```

> 💡 이렇게 해두면 **매번 `--user`를 안 써도 기본으로 적용**됩니다.

## 3-3. 읽기 전용 파일 시스템 (p32~33)

컨테이너 내부 파일이 **실행 중에 변경되지 못하게** 막을 수 있습니다.

- **`--read-only`** 옵션을 주면 루트 파일시스템이 읽기 전용
- 로그나 임시 파일처럼 **쓰기가 꼭 필요한 경로**는 **`--tmpfs`**나 볼륨으로 별도 허용

```bash
docker run --read-only -it ubuntu bash
#   touch test.txt   → 쓰기가 거부되는지 확인

docker run --read-only --tmpfs /tmp -it ubuntu bash
#   /tmp 에는 쓰기가 가능한지 확인
```

## 3-4. ⭐ Secrets 관리 — 환경 변수의 한계 (p34~35)

> ⚠️ **우리가 지금까지 써온 환경 변수(`-e`)는 사실 완전히 안전하지 않습니다.**

- **`docker inspect` 명령으로 환경 변수 값이 그대로 노출**될 수 있음
- 비밀번호, API 키 같은 민감한 값은 **별도의 Secrets 관리 도구**로 다루는 것이 안전

| 환경 변수 (`-e`) | Secrets (Compose/Swarm) |
|---|---|
| **`docker inspect`로 그대로 노출됨** | **암호화되어 저장** |
| 설정은 간단하지만 **보안에 취약** | **필요한 컨테이너에만** 전달 |
| 간단한 실습, **개발 환경**에 적합 | **파일 형태로** 컨테이너 내부에 마운트 |
| | **운영 환경에 더 적합** |

> 💡 기본 과정에서 `-e POSTGRES_PASSWORD=1234`로 배웠던 방식은 **학습용**입니다. 실 서비스에서는 Secrets로 바꿔야 합니다.

## 3-5. 리소스 제한, 실전처럼 다루기 (p36~37)

기본 과정에서 배운 `--memory`, `--cpus`를 **운영 관점**에서 다시 점검합니다.

- 제한을 **너무 낮게** 걸면 → 서비스가 자주 죽음
- 제한을 **너무 높게(또는 안)** 걸면 → 한 컨테이너가 **서버 전체를 다운**시킬 수 있음
- 실제 운영에서는 **모니터링 데이터를 보고 적정 값을 찾아가는 것**이 일반적

### [자율실습] docker stats로 실시간 리소스 확인

```bash
docker stats
#   ① CPU·메모리 사용량을 실시간으로 확인
#   ② 부하를 발생시키는 간단한 스크립트를 컨테이너 안에서 실행
#   ③ --cpus 값을 바꿔가며 CPU 사용률 상한이 실제로 적용되는지 관찰
```

## 3-6. 로깅 드라이버 (p38)

| 드라이버 | 특징 |
|---|---|
| **`json-file`** (기본값) | 컨테이너별 JSON 파일로 로그 저장 |
| **`local`** | `json-file`보다 **압축·성능이 개선된** 기본 대안 |

|---|---|

# 4. Docker Compose 심화

> 📍 p40~51 | **기본 과정에서 배운 Compose를, 실무에서 쓰는 방식까지 확장**

## 4-1. 여러 Compose 파일을 합칠 수 있다 (p41~43)

`docker-compose.yml` 하나에 모든 걸 다 적을 필요는 없습니다.

- **기본 설정**(`docker-compose.yml`) + **환경별 추가 설정**(override 파일)
- 개발 환경에서는 소스코드를 **bind mount**하고, 운영 환경에서는 **빌드된 이미지만** 쓰는 식으로 분리

### docker-compose.override.yml

| | |
|---|---|
| 🧂 **비유로 말하면** | 기본 레시피 위에, **오늘만 추가하는 특별 양념** |
| 📖 **정확히 말하면** | 같은 폴더에 이 이름의 파일이 있으면, `docker compose`는 기본 파일과 **자동으로 합쳐서** 읽음 (주로 **로컬 개발 전용** 설정에 활용) |

```yaml
# docker-compose.override.yml
services:
  was:
    volumes:
      - ./was:/app
    environment:
      - FLASK_DEBUG=1
```

```bash
# docker-compose.yml은 그대로 두고,
# docker compose up 만 실행해도 두 파일이 자동으로 합쳐집니다
docker compose up -d
```

> 💡 기본 과정 3장에서 배운 **Bind Mount(개발 중 실시간 반영)**를 실무에서 쓰는 정석 방식이 바로 이것입니다.

## 4-2. Profiles — 선택적으로 서비스 실행 (p44~45)

모든 서비스를 **항상 다 켜고 싶지 않을 때**가 있습니다.

- 예: 평소엔 필요 없지만, **가끔 관리자 도구(Adminer 등)만** 켜고 싶은 경우
- 서비스에 **`profiles`**를 지정해두면, **특정 profile을 지정했을 때만** 실행됨

```yaml
services:
  was:
    build: ./was
  db:
    image: postgres:17
  adminer:
    image: adminer
    profiles: ["debug"]
```

```bash
docker compose up -d                    # 평소 실행: was, db만 켜짐
docker compose --profile debug up -d    # adminer까지 켜고 싶을 때
```

## 4-3. ⭐ Healthcheck — depends_on의 한계를 해결 (p46~47)

> ⚠️ **컨테이너가 '떠 있다'고 해서 '정상 동작 중'이라는 보장은 없습니다.**

- `healthcheck`는 **주기적으로 컨테이너 내부에 간단한 명령을 실행**해 진짜 살아있는지 확인
- `depends_on`과 함께 쓰면, **'진짜로 준비된' 서비스가 뜬 뒤에야** 다음 서비스가 시작되도록 만들 수 있음

```yaml
services:
  db:
    image: postgres:17
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  was:
    build: ./was
    depends_on:
      db:
        condition: service_healthy
```

> ⭐ 이렇게 하면 was는 db가 단순히 **'떠 있는' 상태가 아니라, 진짜 '접속 가능한' 상태**일 때 시작합니다.

```plain text
【 기본 과정 】  depends_on: [db]
   db 컨테이너 Started  →  즉시 was 시작  →  ❌ DB가 아직 초기화 중이라 연결 실패

【 심화 】  depends_on: { db: { condition: service_healthy } }
   db Started  →  pg_isready 통과할 때까지 대기  →  ✅ was 시작
```

> 📎 이것이 기본 과정 p226·p233에서 남겨두었던 **"depends_on은 순서만 보장한다"** 문제의 정답입니다.

## 4-4. Restart Policy 종류 (p48)

| 정책 | 동작 |
|---|---|
| **`no`** (기본값) | 재시작하지 않음 |
| **`on-failure`** | **오류로 종료됐을 때만** 재시작 |
| **`always`** | **어떤 이유로든** 항상 재시작 |
| **`unless-stopped`** | **사용자가 직접 멈추지 않는 한** 항상 재시작 |

> ⭐ **운영 환경에서는 보통 `unless-stopped` 또는 `always`를 많이 사용**합니다.

## 4-5. .env 파일로 환경별 설정 분리 (p49~50)

비밀번호나 포트 번호처럼 **환경마다 달라지는 값을 코드 밖으로 분리**합니다.

- `.env` 파일에 `KEY=VALUE` 형식으로 적어두면, **Compose가 자동으로 읽어들임**
- `docker-compose.yml` 안에서는 **`${변수명}`** 형태로 참조

```bash
# .env
POSTGRES_PASSWORD=1234
WAS_PORT=5000
```

```yaml
# docker-compose.yml
    ports:
      - "${WAS_PORT}:5000"
```

```bash
docker compose config     # ③ 실제 값이 잘 치환되는지 미리 확인
docker compose up -d      # ④ 정상 동작 확인
```

> ⚠️ **`.env` 파일은 반드시 `.gitignore`에 추가**해 저장소에 올라가지 않게 할 것.
> (1-4의 `.dockerignore`에서도 `.env`를 제외하라고 했던 것과 같은 맥락입니다.)

## ✅ 4장 정리 (p51)

| | |
|---|---|
| **override 파일**로 환경별 설정을 기본 파일과 분리 | **profiles**로 특정 상황에만 필요한 서비스를 선택적 실행 |
| **healthcheck**로 서비스가 '진짜 준비됐는지'까지 확인 | **restart policy**로 장애 시 자동 복구 방식을 설정 |
| **`.env` 파일**로 민감한 값과 환경별 설정을 코드에서 분리 | |

# ★ 기본 과정 ↔ 심화 대응표

> 기본 과정에서 배운 것이 심화에서 **어떻게 확장되는지** 한눈에 봅니다.

| 기본 과정 | 심화 |
|---|---|
| Dockerfile 6대 명령어로 이미지 빌드 | **Multi-stage 3단계 이상**, BuildKit **캐시 마운트**, `--target` 디버깅 |
| `python:3.10-slim` 같은 경량 이미지 | **Distroless** — 쉘·패키지 매니저조차 없는 최소 이미지 |
| (다루지 않음) | **Trivy로 CVE 스캔**, CI/CD에 스캔 단계 삽입 |
| Mac에서 이미지 빌드 | **buildx로 AMD64/ARM64 동시 빌드** |
| Namespace = "칸막이" | **PID / Network / Mount / UTS / IPC / User** 6종으로 세분화 |
| cgroups = "용돈" | `/sys/fs/cgroup` 파일시스템, **cgroups v2**, **OOM Kill(exit 137)** |
| "컨테이너 = 특별한 프로세스" (`docker top`) | **`unshare`·`nsenter`**로 Docker 없이 직접 재현 |
| "이미지는 레이어로 쌓임" | **OverlayFS** — LowerDir / UpperDir / MergedDir |
| "Docker 말고 containerd, Podman도 있다" | **containerd → runc** 호출 구조, **OCI 표준**(Image Spec / Runtime Spec) |
| `-e`로 비밀번호 전달 | **`docker inspect`로 노출됨** → **Secrets**로 관리 |
| (다루지 않음) | **`--user`** 비루트 실행, **`--read-only`** + `--tmpfs` |
| `--memory`, `--cpus` | **`docker stats`**로 모니터링하며 적정값 튜닝 |
| `docker logs` | **로깅 드라이버** (json-file / local / syslog / fluentd → ELK, Loki) |
| `docker-compose.yml` 하나 | **override 파일**로 개발/운영 분리, **profiles**로 선택 실행 |
| **`depends_on`은 순서만 보장** ⚠️ | **`healthcheck` + `condition: service_healthy`** ✅ |
| (다루지 않음) | **restart policy** (`unless-stopped` / `always`) |
| Compose에 비밀번호 하드코딩 | **`.env` + `${변수}`**, `docker compose config`로 검증 |

# ★ 전체 흐름 한 장 요약

```plain text
【 이미지를 더 좋게 만들기 】

  코드 ──▶ Dockerfile ──▶ build ──▶ 이미지 ──▶ Registry
            │              │                    │
            │              ├ BuildKit (병렬·Skip)│
            │              └ 캐시 마운트          │
            │                                    │
            ├ Multi-stage (deps→test→final)      ├ buildx (amd64 + arm64)
            ├ Distroless (쉘 없음)                └ Trivy 스캔 (CVE 차단)
            └ .dockerignore (.env, *.key 제외)


【 컨테이너의 진짜 정체 】

  docker CLI → Docker Daemon → containerd → runc
                                              │
                        ┌─────────────────────┴──────────────────┐
                        │                                        │
                   Namespace                                 cgroups
              (PID/Net/Mount/UTS/IPC/User)              (CPU/메모리 상한)
                   "시야를 나눔"                          "용돈을 나눔"
                                                       초과 시 OOM Kill(137)
                        │
                   OverlayFS
            LowerDir(RO) + UpperDir(RW) = MergedDir


【 운영에 내놓기 전 체크 】

  보안 ── 최소 권한(--user) · 최소 이미지(Distroless) · 최신 유지(스캔)
      └── --read-only + --tmpfs · 민감값은 Secrets (❌ -e 는 inspect로 노출)
  자원 ── docker stats로 관찰 → --memory / --cpus 적정값
  로그 ── json-file(로컬) → fluentd/gelf(중앙 집중: ELK, Loki)
  복구 ── restart: unless-stopped


【 실무형 Compose 】

  docker-compose.yml        (공통·운영 기준)
        +
  docker-compose.override.yml  (로컬 개발: bind mount, DEBUG)   ← 자동 병합
        +
  .env                      (${WAS_PORT}, ${POSTGRES_PASSWORD}) ← .gitignore 필수
        +
  profiles: ["debug"]       (adminer 등 선택 서비스)
        +
  healthcheck + condition: service_healthy   ← depends_on의 한계 해결
```

| 4 | Distroless 이미지가 보안에 유리한 이유는? | **쉘과 패키지 매니저조차 없어서**, 공격자가 침투해도 **활용할 도구 자체가 없음** (공격 표면 최소화) |
| 5 | 이미지 취약점 스캔은 왜 필요한가? | 베이스 이미지의 **오래된 라이브러리 취약점(CVE)이 함께 배포**되기 때문. Trivy/Grype로 스캔하고 **CI/CD에 단계로 삽입** |
| 6 | 멀티 아키텍처 이미지가 필요한 이유는? | Apple Silicon·AWS Graviton 등 **ARM 환경**이 늘어, Mac(ARM)에서 빌드한 이미지가 인텔 서버에서 안 돌 수 있음. **buildx**로 한 태그에 여러 아키텍처를 묶음 |

| 8 | `docker exec`은 내부적으로 무엇을 하나? | 실행 중 컨테이너의 **namespace로 진입**하는 것. 저수준으로는 **`nsenter`**와 같은 원리 |

| 11 | containerd와 runc의 역할 분담은? | **containerd** = 이미지 pull·컨테이너 생명주기 관리(K8s 기본 런타임) / **runc** = OCI 표준 저수준 실행기, 실제로 Namespace·cgroups를 만들어 격리 실행 |

| 13 | 컨테이너 보안 3대 원칙은? | **최소 권한 / 최소 이미지 / 최신 유지** |

| 15 | `--read-only`를 쓰면서 로그를 남기려면? | 쓰기가 필요한 경로에 **`--tmpfs`** 또는 볼륨을 별도로 붙임 |
