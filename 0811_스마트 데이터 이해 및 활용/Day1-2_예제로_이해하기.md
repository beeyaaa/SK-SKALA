# 1. 먼저 답: 왼쪽/오른쪽 & ON vs WHERE

## 1-1. FROM이 왼쪽, JOIN 옆이 오른쪽 ✅

```sql
FROM      student s        ←  왼쪽 테이블  (LEFT)
LEFT JOIN enroll  e        ←  오른쪽 테이블 (RIGHT)
       ON s.id = e.student_id
```

| 쓰여진 위치 | 부르는 이름 |
|------------|-----------|
| **FROM 뒤** | **왼쪽** (LEFT) |
| **JOIN 뒤** | **오른쪽** (RIGHT) |

**그래서**

| JOIN 종류 | 뜻 |
|-----------|-----|
| **LEFT** JOIN | **FROM 쪽(왼쪽)** 을 전부 살려라 |
| **RIGHT** JOIN | **JOIN 쪽(오른쪽)** 을 전부 살려라 |

### 💡 그래서 실무에서는 RIGHT JOIN을 안 씁니다

**이 둘은 완전히 같은 결과입니다.**

```sql
-- A
FROM student s LEFT  JOIN enroll  e ON s.id = e.student_id

-- B  (순서만 뒤집음)
FROM enroll  e RIGHT JOIN student s ON s.id = e.student_id
```

`A LEFT JOIN B` = `B RIGHT JOIN A`

**테이블 순서만 바꾸면 LEFT로 다 표현할 수 있으니**, 헷갈리는 RIGHT를 안 쓰고 **LEFT로 통일**하는 게 관례입니다.

> 🔑 **결론** : **"LEFT JOIN 하나만 제대로 알면 됩니다."**

## 1-2. ⭐ ON과 WHERE의 차이 (이게 핵심)

### 한 줄 정의

| | 역할 | 언제 작동 |
|---|------|----------|
| **ON** | **짝을 맺는 조건** — "이 둘을 붙일까?" | 표를 **만드는 중** |
| **WHERE** | **줄을 고르는 조건** — "이 줄을 남길까?" | 표가 **다 만들어진 뒤** |

### 🎯 왜 다들 헷갈리는가 — **INNER JOIN에서는 결과가 같기 때문**

```sql
-- ① ON에 조건
FROM student s JOIN enroll e ON s.id = e.student_id AND e.course = 'DB'

-- ② WHERE에 조건
FROM student s JOIN enroll e ON s.id = e.student_id
WHERE e.course = 'DB'
```

**INNER JOIN이면 ①과 ②의 결과가 완전히 동일합니다.**

| id | name | course | score |
|:--:|------|------|:--:|
| 1 | 홍길동 | DB | 90 |
| 2 | 이순신 | DB | 90 |
| 3 | 강감찬 | DB | 70 |

**왜 같은가?** INNER JOIN은 어차피 짝 없는 건 다 버리니까, **"안 붙인 것"이든 "붙였다 버린 것"이든 결과가 똑같습니다.**

> ⚠️ **여기서 "아, 같은 거구나" 하고 배우면 → OUTER JOIN에서 사고가 납니다.**

### 💥 OUTER JOIN에서는 완전히 달라집니다

목표: **모든 학생을 보되, DB 과목 점수만 표시**

#### ❌ WHERE에 조건

```sql
FROM student s LEFT JOIN enroll e ON s.id = e.student_id
WHERE e.course = 'DB';
```

**1단계 — LEFT JOIN 완성 (5행)**

| id | name | course | score |
|:--:|------|------|:--:|
| 1 | 홍길동 | DB | 90 |
| 1 | 홍길동 | 알고리즘 | 80 |
| 2 | 이순신 | DB | 90 |
| 3 | 강감찬 | DB | 70 |
| 4 | 유관순 | **NULL** | NULL |

**2단계 — WHERE로 줄 고르기**

| id | name | course | 판정 |
|:--:|------|------|---|
| 1 | 홍길동 | DB | ✅ |
| 1 | 홍길동 | 알고리즘 | ❌ 'DB' 아님 |
| 2 | 이순신 | DB | ✅ |
| 3 | 강감찬 | DB | ✅ |
| 4 | 유관순 | **NULL** | ❌ **`NULL = 'DB'` 는 TRUE가 아님** |

**→ 3행. 유관순 사라짐.** LEFT JOIN을 쓴 의미가 없어졌습니다.

#### ✅ ON에 조건

```sql
FROM student s LEFT JOIN enroll e
       ON s.id = e.student_id AND e.course = 'DB';
```

**짝을 맺을 때부터 'DB'인 것만 짝으로 인정합니다.**

```
홍길동(1) → student_id=1 이고 course='DB' 인 줄?  → (1,DB,90)  ✅
             (1,알고리즘,80)은 조건 불일치 → 애초에 짝 아님
이순신(2) → (2,DB,90)  ✅
강감찬(3) → (3,DB,70)  ✅
유관순(4) → 없음 → LEFT JOIN이니까 NULL 채워서 살림  ✅
```

| id | name | course | score |
|:--:|------|------|:--:|
| 1 | 홍길동 | DB | 90 |
| 2 | 이순신 | DB | 90 |
| 3 | 강감찬 | DB | 70 |
| **4** | **유관순** | **NULL** | **NULL** |

**→ 4행. 학생 4명 그대로.**

### 📌 정리

| | INNER JOIN | **OUTER JOIN (LEFT/RIGHT/FULL)** |
|---|:---:|:---:|
| ON에 조건 | 결과 A | 결과 A |
| WHERE에 조건 | 결과 A | **결과 B (다름!)** |

> 🔑 **판단 기준 딱 하나**
>
> **"오른쪽 테이블 컬럼"에 조건을 걸 때 —**
> - **NULL 행을 살리고 싶다** → **ON**
> - **NULL 행을 버려도 된다** → **WHERE** (사실상 INNER JOIN)
>
> 💡 반대로, **왼쪽 테이블 컬럼** 조건(`WHERE s.major_code='CS'`)은 **WHERE에 써도 안전합니다.** 왼쪽은 NULL이 될 일이 없으니까요.

## 2-1. 정규화 — 표가 쪼개지는 과정

### 😱 출발: 한 표에 다 때려넣기

| 학번 | 이름 | 학과코드 | 학과명 | 수강과목 |
|:--:|------|:--:|------|------|
| 1 | 홍길동 | CS | 컴퓨터공학 | **DB, 알고리즘** |
| 2 | 이순신 | CS | 컴퓨터공학 | DB |
| 3 | 강감찬 | HR | 경영학 | DB |
| 4 | 유관순 | HR | 경영학 | *(없음)* |

**이 표의 실제 문제 3가지 — 정규화 자료에 나오는 "이상(Anomaly)"이 이겁니다.**

| 문제 | 여기서 어떻게 나타나나 |
|------|---------------------|
| **갱신 이상** | "컴퓨터공학"을 "컴퓨터공학과"로 바꾸려면 **홍길동·이순신 2줄을 다 고쳐야** 함.<br>하나라도 빠뜨리면 같은 학과인데 이름이 다름 |
| **삭제 이상** | 만약 **경영학과에 강감찬 혼자**인데 자퇴하면 → 그 줄을 지우는 순간 **"HR = 경영학"이라는 정보 자체가 사라짐** |
| **삽입 이상** | 아래 1NF에서 실제로 터집니다 ↓ |

---

### 1️⃣ 1NF — 한 칸에 값 하나만

`"DB, 알고리즘"` 이 한 칸에 두 개 → **줄을 쪼갭니다.**

| 학번 | 이름 | 학과코드 | 학과명 | 과목 |
|:--:|------|:--:|------|------|
| 1 | 홍길동 | CS | 컴퓨터공학 | DB |
| 1 | 홍길동 | CS | 컴퓨터공학 | 알고리즘 |
| 2 | 이순신 | CS | 컴퓨터공학 | DB |
| 3 | 강감찬 | HR | 경영학 | DB |
| 4 | 유관순 | HR | 경영학 | **???** |

**PK = (학번, 과목)** ← 학번만으로는 홍길동 2줄을 구분 못 하니까

> 💥 **여기서 삽입 이상이 터집니다**
> **유관순은 수강을 안 했는데, PK의 일부인 "과목"을 비워둘 수가 없습니다** (PK는 NULL 불가).
> → **수강 안 한 학생은 아예 등록을 못 하는 표**가 되어버렸습니다.
> → 이걸 풀려면 **표를 나눠야 합니다.**

---

### 2️⃣ 2NF — 복합키의 "일부"에만 딸린 것 분리

**질문을 던져보세요 — "이름을 알려면 뭐가 필요하지?"**

```
이름   ← 학번만 있으면 안다        (과목은 필요 없음)
학과   ← 학번만 있으면 안다        (과목은 필요 없음)
```

**PK가 (학번, 과목)인데 학번만으로 결정된다 = 부분 종속** → 분리

**📗 학생**

| 학번(PK) | 이름 | 학과코드 | 학과명 |
|:--:|------|:--:|------|
| 1 | 홍길동 | CS | 컴퓨터공학 |
| 2 | 이순신 | CS | 컴퓨터공학 |
| 3 | 강감찬 | HR | 경영학 |
| **4** | **유관순** | **HR** | **경영학** | ✅ **드디어 등록 가능!** |

**📙 수강**

| 학번(PK,FK) | 과목(PK) |
|:--:|------|
| 1 | DB |
| 1 | 알고리즘 |
| 2 | DB |
| 3 | DB |

> ✅ **해결된 것** : 유관순이 학생 테이블에 존재합니다. 수강 테이블에 행이 없을 뿐입니다.
> → **"수강 없는 학생"이 자연스럽게 표현됩니다.** (= 나중에 LEFT JOIN으로 찾게 될 그 유관순)

---

### 3️⃣ 3NF — 키가 아닌 것에 딸린 것 분리

**또 질문 — "학과명을 알려면 뭐가 필요하지?"**

```
학과명  ← 학번?  아니오
        ← 학과코드만 있으면 안다 ✅

학번 → 학과코드 → 학과명     ← 두 다리 건넘 = 이행 종속
```

**📗 학생**

| 학번(PK) | 이름 | 학과코드(FK) |
|:--:|------|:--:|
| 1 | 홍길동 | CS |
| 2 | 이순신 | CS |
| 3 | 강감찬 | HR |
| 4 | 유관순 | HR |

**📘 학과**

| 학과코드(PK) | 학과명 |
|:--:|------|
| CS | 컴퓨터공학 |
| HR | 경영학 |

> ✅ **해결된 것** : "컴퓨터공학"을 바꾸려면 이제 **학과 테이블 1줄만** 고치면 됩니다. (갱신 이상 해결)
> ✅ 강감찬이 자퇴해도 **"HR = 경영학"은 학과 테이블에 남아 있습니다.** (삭제 이상 해결)

### 🔑 정규화 3단계를 질문 하나로

> ## **"이 칸을 알아내려면 최소한 무엇이 필요한가?"**

| 증상 | 위반 | 처방 |
|------|------|------|
| 한 칸에 값이 **여러 개** | **1NF** | 줄을 쪼갠다 |

## 2-2. PK · FK · UK — 무엇이 다른가

| | **PK** (기본키) | **FK** (외래키) | **UK** (고유키) |
|---|---|---|---|
| **역할** | 이 줄을 **콕 집어 식별** | **다른 표를 가리킴** | **중복만 금지** |
| **NULL** | ❌ 불가 | 가능 | ✅ **가능** |
| **중복** | ❌ 불가 | 가능 | ❌ 불가 |
| **개수** | 표당 **1개** | 여러 개 | 여러 개 |
| **우리 데이터에서** | `student.id`<br>`major.code` | `student.major_code`<br>→ `major.code` | (예) `student.email` |

**UK가 NULL을 허용하는 이유** — 이메일을 아직 안 낸 학생이 있을 수 있으니까요. 단, **낸 사람끼리는 중복되면 안 됩니다.**

| id | name | email (UK) | |
|:--:|------|------|---|
| 1 | 홍길동 | hong@x.com | ✅ |
| 2 | 이순신 | **NULL** | ✅ NULL은 허용 |
| 3 | 강감찬 | **NULL** | ✅ NULL은 여러 개도 OK |
| 4 | 유관순 | ~~hong@x.com~~ | ❌ **중복 불가** |

## 2-3. 1:1 / 1:N / N:M — 우리 데이터로

### 1:N — 학생 : 수강

```
홍길동 ──┬── DB
         └── 알고리즘        한 학생이 여러 수강 ✅
                            한 수강은 한 학생 ✅
```
**구현** : **"N"쪽에 FK를 둡니다.** → `enroll.student_id`

> 💡 **왜 N쪽에 FK를 두나?** 반대로 하면 `student` 테이블에 `수강1, 수강2, 수강3…` 컬럼을 만들어야 하는데 — **몇 개를 만들어야 할지 모릅니다.** (그리고 1NF 위반)

### N:M — 학생 : 과목 (사람들이 제일 헷갈려하는 것)

```
홍길동 ──┬── DB ──┬── 이순신
         │        └── 강감찬
         └── 알고리즘

한 학생이 여러 과목 ✅   +   한 과목을 여러 학생 ✅   =  N:M
```

**❌ 직접 연결이 불가능합니다**

| 시도 | 왜 안 되나 |
|------|-----------|
| `student`에 `수강과목` 컬럼 | 여러 개를 못 넣음 (1NF 위반) |
| `course`에 `수강학생` 컬럼 | 마찬가지 |

**✅ 그래서 중간에 표를 하나 낍니다**

```
student  ──1:N──▶  enroll  ◀──N:1──  course
  (1)                 (N)              (1)

N:M 하나 = 1:N 두 개
```

**📙 enroll (교차 테이블)**

| student_id (PK,FK) | course (PK,FK) | score ← **추가 정보도 넣을 수 있음!** |
|:---:|:---:|:--:|
| 1 | DB | 90 |
| 1 | 알고리즘 | 80 |
| 2 | DB | 90 |

> 🔑 **교차 테이블의 두 가지 이점**
> 1. **복합 PK (student_id, course)** → 같은 학생이 같은 과목을 **두 번 신청하는 것을 원천 차단**
> 2. **`score`, `수강일` 같은 "관계 자체의 정보"** 를 넣을 자리가 생김

## 2-4. 약한 엔티티 — "혼자서는 못 서는 표"

**주문**

| order_id (PK) | 고객 | 주문일 |
|:--:|------|------|
| 1001 | 홍길동 | 2026-08-12 |
| 1002 | 이순신 | 2026-08-12 |

**주문상세**

| order_id (PK,FK) | **item_no (PK)** | 상품 | 수량 |
|:--:|:--:|------|:--:|
| 1001 | **1** | 노트북 | 1 |
| 1001 | **2** | 마우스 | 2 |
| 1002 | **1** | 키보드 | 1 |

> 🔍 **`item_no`를 보세요. 1001번에도 1이 있고, 1002번에도 1이 있습니다.**
>
> **"1번 항목"이라는 말은 그 자체로는 아무 의미가 없습니다.** "1001번 주문의 1번 항목"이어야 의미가 생깁니다.
> → **혼자서는 자기를 식별 못 함 = 약한 엔티티**
> → **PK = (order_id, item_no)** 복합키
> → 주문이 삭제되면 상세도 함께 삭제 → **`ON DELETE CASCADE`**

## 2-5. 격리 수준 — 두 사람이 동시에 만졌을 때

**상황** : 계좌 A의 잔액 **1000원**

### ① Dirty Read — 아직 확정 안 된 값을 봄

| 시각 | 🅰 세션 1 (송금) | 🅱 세션 2 (조회) |
|:--:|---|---|
| ① | `BEGIN` | |
| ② | 1000 → **500** UPDATE | |
| ③ | *(COMMIT 안 함)* | 조회 → **500** 😱 |
| ④ | **ROLLBACK** (취소) | |
| ⑤ | 실제 잔액 = **1000** | 500인 줄 알고 있음 ❌ |

→ **READ COMMITTED 이상**이면 ③에서 **1000**을 봅니다.

### ② Non-Repeatable Read — 같은 걸 두 번 읽었는데 **값**이 다름

| 시각 | 🅰 세션 1 | 🅱 세션 2 |
|:--:|---|---|
| ① | `BEGIN` / 조회 → **1000** | |
| ② | | 500으로 UPDATE + **COMMIT** |
| ③ | 같은 걸 다시 조회 → **500** 😱 | |

→ **REPEATABLE READ 이상**이면 ③에서도 **1000**을 봅니다.

### ③ Phantom Read — 같은 조건인데 **개수**가 다름

| 시각 | 🅰 세션 1 | 🅱 세션 2 |
|:--:|---|---|
| ① | `COUNT(*) WHERE score>=80` → **3건** | |
| ② | | 85점짜리 **INSERT** + COMMIT |
| ③ | 같은 조건 다시 → **4건** 😱 | |

→ **SERIALIZABLE**이면 차단됩니다.

### 📌 셋의 차이를 한 줄로

| | 무엇이 문제인가 |
|---|---|
| **Dirty** | 남이 **아직 확정 안 한** 걸 읽음 |
| **Non-Repeatable** | 있던 줄의 **값**이 바뀜 |
| **Phantom** | **줄이 새로 생김** (개수가 바뀜) |

| 격리 수준 | Dirty | Non-Rep | Phantom | 기본값인 DB |
|---|:--:|:--:|:--:|---|
| READ UNCOMMITTED | 허용 | 허용 | 허용 | (거의 안 씀) |
| **READ COMMITTED** | **차단** | 허용 | 허용 | **PostgreSQL, Oracle** |
| **REPEATABLE READ** | 차단 | **차단** | 허용* | **MySQL** |
| **SERIALIZABLE** | 차단 | 차단 | **차단** | (느림) |

> \* 표준상 허용이지만 MySQL·PostgreSQL은 실제로는 대부분 막습니다.
> 🔑 **위로 갈수록 빠르고 위험, 아래로 갈수록 안전하고 느림.**

# 3. 표에서 꺼내는 이야기 (Day 2)

## 3-1. SELECT 실행 순서 — 한 쿼리를 8단계로 추적

```sql
SELECT   s.major_code, COUNT(*) AS cnt, AVG(e.score) AS avg_score
FROM     student s
JOIN     enroll e ON s.id = e.student_id
WHERE    e.score >= 80
GROUP BY s.major_code
HAVING   COUNT(*) >= 2
ORDER BY avg_score DESC
LIMIT    1;
```

**⚠️ 쓰는 순서는 SELECT가 먼저지만, 실행은 FROM이 먼저입니다.**

### 1단계 `FROM student` → 4행
| id | name | major_code |
|:--:|---|:--:|
| 1 | 홍길동 | CS |
| 2 | 이순신 | CS |
| 3 | 강감찬 | HR |
| 4 | 유관순 | HR |

### 2단계 `JOIN enroll` → 4행 (유관순·99번 탈락)
| id | name | major_code | course | score |
|:--:|---|:--:|---|:--:|
| 1 | 홍길동 | CS | DB | 90 |
| 1 | 홍길동 | CS | 알고리즘 | 80 |
| 2 | 이순신 | CS | DB | 90 |
| 3 | 강감찬 | HR | DB | 70 |

### 3단계 `WHERE score >= 80` → 3행
| id | name | major_code | score | 판정 |
|:--:|---|:--:|:--:|---|
| 1 | 홍길동 | CS | 90 | ✅ |
| 1 | 홍길동 | CS | 80 | ✅ |
| 2 | 이순신 | CS | 90 | ✅ |
| ~~3~~ | ~~강감찬~~ | ~~HR~~ | ~~70~~ | ❌ 탈락 |

### 4단계 `GROUP BY major_code` → 그룹 1개
```
CS 그룹 : [90, 80, 90]   ← 3건
HR 그룹 : 없음!           ← 강감찬이 3단계에서 빠져서 그룹 자체가 안 생김
```

### 5단계 `HAVING COUNT(*) >= 2`
```
CS : 3건 >= 2  ✅ 통과
```

### 6단계 `SELECT` — 여기서 비로소 별칭이 생김
| major_code | cnt | avg_score |
|:--:|:--:|:--:|
| CS | 3 | **86.7** | ← (90+80+90)/3

### 7~8단계 `ORDER BY` → `LIMIT 1` → 최종 1행

> 🔑 **이 순서를 알면 자동으로 풀리는 의문 2개**
>
> **Q. 왜 WHERE에서 별칭(`avg_score`)을 못 쓰나?**
> → WHERE(3단계)가 SELECT(6단계)보다 **먼저** 실행되므로, 그때는 **별칭이 아직 존재하지 않습니다.**
>
> **Q. 왜 ORDER BY에서는 별칭을 쓸 수 있나?**
> → ORDER BY(7단계)는 SELECT(6단계) **다음**이라 별칭이 이미 만들어져 있습니다.

## 3-2. WHERE vs HAVING — 숫자가 실제로 달라집니다

JOIN 결과 4행이 출발점입니다.

| name | major_code | score |
|---|:--:|:--:|
| 홍길동 | CS | 90 |
| 홍길동 | CS | 80 |
| 이순신 | CS | 90 |
| 강감찬 | HR | 70 |

### 🅐 조건 없이

| major_code | AVG | COUNT |
|:--:|:--:|:--:|
| CS | **86.7** | 3 |
| HR | **70.0** | 1 |

### 🅑 `WHERE score >= 85` — **먼저 줄을 지움**

```
90 ✅    80 ❌지움    90 ✅    70 ❌지움
```

| major_code | AVG | COUNT |
|:--:|:--:|:--:|
| CS | **90.0** | **2** |
| ~~HR~~ | — | — | ← **그룹 자체가 소멸** |

### 🅒 `HAVING AVG(score) >= 85` — **그룹 다 만들고 나서 버림**

| major_code | AVG | COUNT | 판정 |
|:--:|:--:|:--:|---|
| CS | **86.7** | **3** | ✅ 통과 |
| HR | 70.0 | 1 | ❌ 탈락 |

### 📊 나란히 비교

| | CS 평균 | CS 건수 | HR |
|---|:--:|:--:|:--:|
| 🅑 WHERE | **90.0** | **2** | 그룹 없음 |
| 🅒 HAVING | **86.7** | **3** | 탈락 |

> 🔑 **WHERE는 80점을 계산에서 빼버렸고, HAVING은 80점도 넣어 평균을 낸 뒤 판단했습니다.**
> - **WHERE = 재료를 골라낸다** (요리 전)
> - **HAVING = 완성된 요리를 골라낸다** (요리 후)

## 3-3. JOIN — 무엇과 무엇이 붙는가

### 🗺 짝짓기 지도

```
   student                          enroll
 ┌───────────┐                 ┌──────────────────┐
 │ 1 홍길동  │ ──────┬───────→ │ 1  DB       90   │
 │           │       └───────→ │ 1  알고리즘  80   │  ← 짝이 2개
 │ 2 이순신  │ ──────────────→ │ 2  DB       90   │
 │ 3 강감찬  │ ──────────────→ │ 3  DB       70   │
 │ 4 유관순  │   ✗ 짝 없음     │                  │
 │           │      짝 없음 ✗  │ 99 네트워크  60   │
 └───────────┘                 └──────────────────┘
    (왼쪽)                          (오른쪽)
```

### 🚶 DB가 실제로 하는 일 — 홍길동 추적

```
홍길동의 id = 1. 이 1과 같은 student_id를 enroll에서 찾자!

enroll 1번줄:  student_id = 1   →  1 = 1   ✅ 짝!
enroll 2번줄:  student_id = 1   →  1 = 1   ✅ 짝!
enroll 3번줄:  student_id = 2   →  2 ≠ 1   ❌
enroll 4번줄:  student_id = 3   →  3 ≠ 1   ❌
enroll 5번줄:  student_id = 99  →  99 ≠ 1  ❌

짝 2개 발견  →  홍길동 줄을 2개 만들고 각각 붙인다
```

| id | name | major ‖ | student_id | course | score |
|:--:|---|:--:|:--:|---|:--:|
| 1 | 홍길동 | CS ‖ | 1 | DB | 90 |
| 1 | 홍길동 | CS ‖ | 1 | 알고리즘 | 80 |
| ← **student에서 온 값** | | | ← **enroll에서 온 값** | | |

> 💡 **`‖` 왼쪽 = student, 오른쪽 = enroll.** `id`와 `student_id`가 둘 다 1인 게 "짝이 맞았다"는 증거입니다.

### ⚠️ 왜 홍길동이 2줄이 됐나 — "행 복제"

```
student에 홍길동은 1명
enroll에 홍길동 수강은 2건
        ↓
결과에서 홍길동이 2줄로 복제됨
```

**여기서 사고가 납니다.**

```sql
-- ❌ "학생이 몇 명이지?"
SELECT COUNT(*) FROM student s JOIN enroll e ON s.id = e.student_id;
→ 4     (홍길동을 2번 셈!)

-- ✅
SELECT COUNT(DISTINCT s.id) FROM ...;
→ 3
```

> 💡 홍길동이 10과목을 들었다면 **홍길동 줄이 10개**가 됩니다.
> → 자료의 *"COUNT(\*)가 이상하게 크면 다중 JOIN 중복 의심"* 이 이 얘기입니다.

---

### ⚠️ COUNT(\*) vs COUNT(컬럼) — 유관순으로 확인

LEFT JOIN 후 학생별로 세면:

| name | `COUNT(*)` | `COUNT(e.course)` | 정답 |
|---|:--:|:--:|:--:|
| 홍길동 | 2 | 2 | 2 |
| 이순신 | 1 | 1 | 1 |
| 강감찬 | 1 | 1 | 1 |
| **유관순** | **1** ❌ | **0** ✅ | **0** |

> 🔑 유관순은 **줄은 1개 있지만(NULL로 채워진 줄)** 실제 수강은 **0건**.
> `COUNT(*)`는 **줄을 세고**, `COUNT(컬럼)`은 **NULL 아닌 값을 셉니다.**
> **LEFT JOIN + COUNT는 반드시 `COUNT(컬럼)`.**

## 3-4. 서브쿼리 3종 — 어디에 쓰느냐로 구분

### ① 스칼라 서브쿼리 (SELECT 절) — 값 하나를 옆에 붙임

```sql
SELECT s.name,
       (SELECT COUNT(*) FROM enroll e WHERE e.student_id = s.id) AS 수강수
FROM   student s;
```

**학생 한 명씩 처리합니다.**

```
홍길동 → enroll에서 student_id=1 세기 → 2
이순신 → student_id=2 세기          → 1
강감찬 → student_id=3 세기          → 1
유관순 → student_id=4 세기          → 0
```

| name | 수강수 |
|---|:--:|
| 홍길동 | 2 |
| 이순신 | 1 |
| 강감찬 | 1 |
| 유관순 | **0** |

> ⚠️ **학생 수만큼 서브쿼리가 반복 실행됩니다.** 4명이면 4번, 100만 명이면 100만 번 → **JOIN으로 대체 검토**

---

### ② WHERE 절 서브쿼리 — 값 하나를 조건에 씀

```sql
SELECT course, score FROM enroll
WHERE  score > (SELECT AVG(score) FROM enroll);
```

**안쪽부터 계산합니다.**

```
1단계: AVG(score) = (90+80+90+70+60)/5 = 78
2단계: WHERE score > 78 로 치환
```

| course | score | 판정 |
|---|:--:|---|
| DB | 90 | ✅ |
| 알고리즘 | 80 | ✅ |
| DB | 90 | ✅ |
| ~~DB~~ | ~~70~~ | ❌ |
| ~~네트워크~~ | ~~60~~ | ❌ |

> 💡 **안쪽 쿼리가 딱 한 번만 실행됩니다.** (바깥을 참조하지 않으니까)

---

### ③ 상관 서브쿼리 — 바깥을 참조 (느림)

```sql
SELECT s.name, e.score
FROM   student s JOIN enroll e ON s.id = e.student_id
WHERE  e.score > (SELECT AVG(e2.score)
                  FROM   student s2 JOIN enroll e2 ON s2.id = e2.student_id
                  WHERE  s2.major_code = s.major_code);  -- ← 바깥 참조!
```

**"자기 학과 평균보다 높은 학생"** — 학과마다 기준이 달라집니다.

```
학과 평균:  CS = (90+80+90)/3 = 86.7      HR = 70

홍길동 DB  90  vs CS 86.7  →  ✅
홍길동 알고 80 vs CS 86.7  →  ❌
이순신 DB  90  vs CS 86.7  →  ✅
강감찬 DB  70  vs HR 70    →  ❌ (같음, 초과 아님)
```

| name | score | 내 학과 평균 |
|---|:--:|:--:|
| 홍길동 | 90 | 86.7 |
| 이순신 | 90 | 86.7 |

> ⚠️ **줄마다 서브쿼리가 다시 실행됩니다** (4번). 그래서 느립니다.

## 3-5. CTE — 위 상관 서브쿼리를 읽기 쉽게

```sql
WITH major_avg AS (                      -- 1단계: 학과 평균을 미리 계산
  SELECT s.major_code, AVG(e.score) AS avg_score
  FROM   student s JOIN enroll e ON s.id = e.student_id
  GROUP BY s.major_code
)
SELECT s.name, e.score, m.avg_score      -- 2단계: 그걸 갖다 씀
FROM   student s
  JOIN enroll    e ON s.id = e.student_id
  JOIN major_avg m ON m.major_code = s.major_code
WHERE  e.score > m.avg_score;
```

**1단계 결과 (`major_avg`) — 임시 표가 하나 생긴 셈**

| major_code | avg_score |
|:--:|:--:|
| CS | 86.7 |
| HR | 70.0 |

**2단계 — 이 표를 그냥 JOIN**

| name | score | avg_score |
|---|:--:|:--:|
| 홍길동 | 90 | 86.7 |
| 이순신 | 90 | 86.7 |

> 🔑 **결과는 상관 서브쿼리와 같지만**
> - 평균을 **딱 한 번만** 계산 → **빠름**
> - 위에서 아래로 **읽는 순서 = 실행 순서** → **읽기 쉬움**

## 3-6. 재귀 CTE — 조직도가 펼쳐지는 과정

**📗 emp**

| id | name | manager_id |
|:--:|---|:--:|
| 1 | 사장 | **NULL** |
| 2 | 김부장 | 1 |
| 3 | 박부장 | 1 |
| 4 | 이대리 | 2 |
| 5 | 최사원 | 4 |

```sql
WITH RECURSIVE tree AS (
  -- ① 시작점(Anchor): 사장
  SELECT id, name, 1 AS depth, name AS path
  FROM   emp WHERE manager_id IS NULL

  UNION ALL

  -- ② 재귀: 방금 찾은 사람의 부하를 찾는다
  SELECT e.id, e.name, t.depth + 1, t.path || ' > ' || e.name
  FROM   emp e JOIN tree t ON t.id = e.manager_id
  WHERE  t.depth < 10                        -- ③ 종료 조건
)
SELECT * FROM tree ORDER BY path;
```

### 🎞 한 회차씩 펼쳐지는 모습

**1회차 (Anchor)** — `manager_id IS NULL` 인 사람

| id | name | depth | path |
|:--:|---|:--:|---|
| 1 | 사장 | 1 | `사장` |

**2회차** — 방금 찾은 **사장(1)** 을 상사로 둔 사람

| id | name | depth | path |
|:--:|---|:--:|---|
| 2 | 김부장 | 2 | `사장 > 김부장` |
| 3 | 박부장 | 2 | `사장 > 박부장` |

**3회차** — **김부장(2), 박부장(3)** 을 상사로 둔 사람

| id | name | depth | path |
|:--:|---|:--:|---|
| 4 | 이대리 | 3 | `사장 > 김부장 > 이대리` |

**4회차** — **이대리(4)** 를 상사로 둔 사람

| id | name | depth | path |
|:--:|---|:--:|---|
| 5 | 최사원 | 4 | `사장 > 김부장 > 이대리 > 최사원` |

**5회차** — 최사원의 부하? **없음 → 종료**

### 🏁 최종 결과 (전부 합침)

| depth | name | path |
|:--:|---|---|
| 1 | 사장 | 사장 |
| 2 | 김부장 | 사장 > 김부장 |
| 3 | 이대리 | 사장 > 김부장 > 이대리 |
| 4 | 최사원 | 사장 > 김부장 > 이대리 > 최사원 |
| 2 | 박부장 | 사장 > 박부장 |

> 🔑 **재귀 CTE는 항상 이 3덩어리입니다**
> ```
> ① 시작점        : WHERE 상사 IS NULL   ← 어디서 출발할까
>    UNION ALL
> ② 재귀 단계     : JOIN 자기자신(CTE)   ← 한 층씩 내려가기
> ③ 종료 조건     : WHERE depth < N      ← 빼먹으면 무한 루프 ⚠️
> ```

## 3-7. GROUP BY vs Window — "줄이 줄어드냐"

### GROUP BY → **줄이 줄어듭니다**

```sql
SELECT major_code, AVG(score) FROM ... GROUP BY major_code;
```

```
홍길동 CS 90 ┐
홍길동 CS 80 ├─▶  CS  86.7
이순신 CS 90 ┘
강감찬 HR 70 ──▶  HR  70.0
```

| major_code | avg |
|:--:|:--:|
| CS | 86.7 |
| HR | 70.0 |

**4줄 → 2줄.** 홍길동이 몇 점이었는지는 **사라졌습니다.**

### Window → **줄이 그대로**

```sql
SELECT name, major_code, score,
       AVG(score) OVER (PARTITION BY major_code) AS 학과평균
FROM ...;
```

| name | major_code | score | 학과평균 |
|---|:--:|:--:|:--:|
| 홍길동 | CS | 90 | 86.7 |
| 홍길동 | CS | 80 | 86.7 |
| 이순신 | CS | 90 | 86.7 |
| 강감찬 | HR | 70 | 70.0 |

**4줄 그대로 + 옆에 평균이 붙었습니다.**

> 🔑 **"내 점수 90, 우리 과 평균 86.7"** 처럼 **개별 값과 집계값을 한 줄에** 놓고 비교 —
> **GROUP BY로는 절대 못 만드는 표**입니다.
>
> - **`PARTITION BY`** = GROUP BY와 같은 "묶는 기준"인데, **줄을 없애지 않음**

## 3-8. 순위 3종 — 동점일 때만 갈립니다

점수 내림차순. **90점이 두 명(동점)** 입니다.

| name | score | ROW_NUMBER | RANK | DENSE_RANK |
|---|:--:|:--:|:--:|:--:|
| 홍길동 | 90 | **1** | **1** | **1** |
| 이순신 | 90 | **2** | **1** | **1** |
| 홍길동 | 80 | **3** | **3** | **2** |
| 강감찬 | 70 | **4** | **4** | **3** |

> 🏅 **올림픽 시상대로 외우세요**
>
> | 함수 | 결과 | 뜻 |
> |---|---|---|
> | **ROW_NUMBER** | 1, 2, 3, 4 | 동점이든 말든 **번호표** |
> | **RANK** | 1, 1, **3**, 4 | 공동 1등이 둘 → **2등 없이 바로 3등** |
> | **DENSE_RANK** | 1, 1, **2**, 3 | 공동 1등이어도 **다음은 2등** |
>
> **DENSE = 촘촘하다** → 번호를 건너뛰지 않는다, 로 기억하면 편합니다.

## 3-9. LAG / LEAD — 앞뒤 줄 값 끌어오기

**📕 sales (서울만)**

```sql
SELECT month, revenue,
       LAG(revenue)  OVER (PARTITION BY region ORDER BY month) AS 전월,
       revenue - LAG(revenue) OVER (PARTITION BY region ORDER BY month) AS 증감,
       LEAD(revenue) OVER (PARTITION BY region ORDER BY month) AS 다음달
FROM sales WHERE region = '서울';
```

| month | revenue | 전월 (LAG) | 증감 | 다음달 (LEAD) |
|:--:|:--:|:--:|:--:|:--:|
| 1월 | 100 | **NULL** | NULL | 130 |
| 2월 | 130 | **100** | **+30** | 120 |
| 3월 | 120 | **130** | **−10** | **NULL** |

```
        1월 ← LAG(한 칸 위) ─┐
        2월 ─────────────────┤ 지금 여기
        3월 ← LEAD(한 칸 아래)┘
```

> 🔑 **LAG = 위 칸 끌어오기 / LEAD = 아래 칸 끌어오기**
> 첫 줄은 위가 없어서 **NULL**, 마지막 줄은 아래가 없어서 **NULL**.
> → 전월 대비 증감률(MoM), 연속 로그인, 이벤트 간격 계산에 씁니다.

## 3-10. 누적합 / 이동평균 — 프레임이 움직이는 모습

```sql
SELECT month, revenue,
  SUM(revenue) OVER (ORDER BY month
      ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS 누적합,
  AVG(revenue) OVER (ORDER BY month
      ROWS BETWEEN 2 PRECEDING AND CURRENT ROW)          AS 이동평균3
FROM sales WHERE region = '서울';
```

### 누적합 — 프레임이 **점점 커집니다**

| month | revenue | 보는 범위 | 누적합 |
|:--:|:--:|---|:--:|
| 1월 | 100 | `[100]` | **100** |
| 2월 | 130 | `[100, 130]` | **230** |
| 3월 | 120 | `[100, 130, 120]` | **350** |

```
1월 ▓
2월 ▓▓
3월 ▓▓▓        ← 처음부터 지금까지 계속 누적
```

### 이동평균 3 — 프레임이 **크기를 유지하며 미끄러집니다**

| month | revenue | 보는 범위 (최대 3칸) | 이동평균 |
|:--:|:--:|---|:--:|
| 1월 | 100 | `[100]` | **100.0** |
| 2월 | 130 | `[100, 130]` | **115.0** |
| 3월 | 120 | `[100, 130, 120]` | **116.7** |

```
1월 ▓
2월 ▓▓
3월 ▓▓▓        ← 3개가 되면 이제부터 창문이 미끄러짐
4월  ▓▓▓       (1월은 빠지고 4월이 들어옴)
```

> 🔑 **`ROWS BETWEEN A AND B` = "지금 줄 기준으로 어디부터 어디까지 볼래?"**
>
> | 키워드 | 뜻 |
> |---|---|
> | `UNBOUNDED PRECEDING` | 맨 처음부터 |
> | `2 PRECEDING` | 2줄 위부터 |
> | `CURRENT ROW` | 지금 줄 |
> | `UNBOUNDED FOLLOWING` | 맨 끝까지 |

## 3-11. NOT IN의 함정 — 결과가 통째로 사라집니다

`enroll`에 이런 줄이 하나 더 있다고 합시다.

| student_id | course | score |
|:--:|---|:--:|
| **NULL** | 교양 | 50 | ← 학생 정보가 아직 안 들어옴

**목표** : 한 번도 수강 안 한 학생 → 정답은 **유관순**

### ❌ NOT IN → **0행!**

```sql
SELECT name FROM student
WHERE id NOT IN (SELECT student_id FROM enroll);
```

**유관순(id=4)이 왜 탈락하는지 계산해 봅시다.**

```
서브쿼리 결과 = {1, 1, 2, 3, 99, NULL}

NOT IN 은 이렇게 풀립니다:
   4 <> 1     →  TRUE
   4 <> 2     →  TRUE
   4 <> 3     →  TRUE
   4 <> 99    →  TRUE
   4 <> NULL  →  UNKNOWN   ⚠️  (NULL은 "모름"이라 비교 자체가 불가)
   ───────────────────────────
   TRUE AND TRUE AND TRUE AND TRUE AND UNKNOWN  =  UNKNOWN

WHERE는 TRUE만 통과시킴  →  UNKNOWN은 탈락
```

**누구를 넣어도 마지막에 UNKNOWN이 붙습니다 → 전원 탈락 → 빈 결과.**

### ✅ NOT EXISTS → **유관순** (정상)

```sql
SELECT name FROM student s
WHERE NOT EXISTS (SELECT 1 FROM enroll e WHERE e.student_id = s.id);
```

| name |
|---|
| 유관순 |

> ⚠️ **가장 무서운 점** : **에러가 안 납니다.** 조용히 빈 결과를 냅니다.
> → 그래서 **무조건 `NOT EXISTS`** 를 쓰는 게 안전합니다.

## 3-12. ROLLUP — 소계가 NULL로 나옵니다

```sql
SELECT major_code, course, SUM(score)
FROM ... GROUP BY ROLLUP(major_code, course);
```

| major_code | course | SUM | 이게 뭔가요 |
|:--:|---|:--:|---|
| CS | DB | 180 | 상세 (90+90) |
| CS | 알고리즘 | 80 | 상세 |
| CS | **NULL** | **260** | ⬅️ **CS 소계** |
| HR | DB | 70 | 상세 |
| HR | **NULL** | **70** | ⬅️ **HR 소계** |
| **NULL** | **NULL** | **330** | ⬅️ **전체 총계** |

```
        CS ─┬─ DB       180
            ├─ 알고리즘   80
            └─ 소계      260  ← course 자리가 NULL
        HR ─┬─ DB        70
            └─ 소계       70
        총계             330  ← 둘 다 NULL
```

> 🔑 **NULL = "이 칸은 묶어서 합친 것"**
> 그래서 `GROUPING()` 함수로 `'전체'`, `'소계'` 라벨을 붙입니다.
> **안 붙이면 진짜 NULL 데이터와 구분이 안 됩니다.**

# 4. 한 장 치트시트

## 🔍 헷갈릴 때 여기만 보세요

| 헷갈리는 것 | 한 줄 판별법 |
|---|---|
| **FROM / JOIN 어느 쪽?** | **FROM 뒤 = 왼쪽**, **JOIN 뒤 = 오른쪽** |
| **LEFT vs RIGHT** | **LEFT = FROM 쪽 살림.** RIGHT는 안 써도 됨 (순서 바꾸면 LEFT로 표현 가능) |
| **ON vs WHERE** | **오른쪽 테이블 조건에서 NULL 행을 살리고 싶으면 → ON.** 아니면 WHERE<br>⚠️ **INNER JOIN에서는 둘이 같음. OUTER에서만 다름** |
| **WHERE vs HAVING** | **WHERE = 재료 고르기(집계 전)** / **HAVING = 완성품 고르기(집계 후)** |
| **COUNT(\*) vs COUNT(col)** | LEFT JOIN 했으면 **무조건 COUNT(컬럼)** (NULL 줄을 1로 세지 않으려고) |
| **GROUP BY vs Window** | **줄이 줄어도 되면 GROUP BY**, **줄을 남겨야 하면 Window** |
| **ROW_NUMBER / RANK / DENSE_RANK** | 1234 / 1**134** / 1**123** — 동점 다음을 **건너뛰면 RANK**, **안 건너뛰면 DENSE** |
| **NOT IN vs NOT EXISTS** | **무조건 NOT EXISTS.** NOT IN은 NULL 하나에 결과가 통째로 사라짐 |
| **서브쿼리 vs CTE** | **한 번 쓰면 서브쿼리, 여러 번 쓰거나 3단계 넘으면 CTE** |
| **View vs Materialized View** | **최신 데이터 필요 → View** / **속도 필요 + 인덱스 필요 → MV(수동 갱신)** |
| **ROWS vs RANGE** | **몇 "줄" 기준이면 ROWS**, **날짜·값 "범위" 기준이면 RANGE** |

## 🎯 우리 데이터로 외우는 숫자

```
student 4명  ×  enroll 5건

INNER  4행     짝 맞은 것만
LEFT   5행     + 유관순 (왼쪽 외톨이)
RIGHT  5행     + 99번   (오른쪽 외톨이)
FULL   6행     + 둘 다
CROSS 20행     4 × 5

학과 평균  CS 86.7 (3건)   HR 70.0 (1건)
WHERE score>=85 걸면  →  CS 90.0 (2건),  HR 그룹 소멸
HAVING AVG>=85 걸면   →  CS 86.7 (3건),  HR 탈락
```

## ⚠️ NULL 3대 함정

```
①  NULL = NULL      →  TRUE 아님 (UNKNOWN)   →  IS NULL 써야 함
②  NULL 이 섞인 NOT IN               →  결과 통째로 빈 집합
③  LEFT JOIN 후 WHERE 에 오른쪽 조건  →  NULL 줄이 삭제되어 INNER JOIN화
```

# 5. 서브쿼리 vs CTE vs Window Function — 한 문제, 4가지 풀이

> 💡 셋의 차이는 설명으로는 안 잡힙니다. **똑같은 문제를 4가지 방법으로 풀어보면** 바로 보입니다.

## 🎯 문제

> **"자기 학과 평균보다 높은 점수를 받은 학생을 찾아라"**

### 정답 확인부터

JOIN 결과 4행이 출발점입니다.

| name | major_code | score |
|---|:--:|:--:|
| 홍길동 | CS | 90 |
| 홍길동 | CS | 80 |
| 이순신 | CS | 90 |
| 강감찬 | HR | 70 |

```
학과 평균:  CS = (90+80+90)/3 = 86.7      HR = 70.0

홍길동 90  vs  CS 86.7   →  ✅
홍길동 80  vs  CS 86.7   →  ❌
이순신 90  vs  CS 86.7   →  ✅
강감찬 70  vs  HR 70.0   →  ❌  (같음, 초과 아님)
```

**정답 = 홍길동(90), 이순신(90)**

이제 이걸 **4가지 방법**으로 풀어보겠습니다.

---

## 방법 ① 상관 서브쿼리 — 줄마다 다시 계산

```sql
SELECT s.name, e.score
FROM   student s JOIN enroll e ON s.id = e.student_id
WHERE  e.score > (
         SELECT AVG(e2.score)
         FROM   student s2 JOIN enroll e2 ON s2.id = e2.student_id
         WHERE  s2.major_code = s.major_code     -- ← 바깥 참조!
       );
```

**실행 과정**

```
1번째 줄 (홍길동 CS 90) → 서브쿼리 실행 → CS 평균 86.7 → 90 > 86.7  ✅
2번째 줄 (홍길동 CS 80) → 서브쿼리 실행 → CS 평균 86.7 → 80 > 86.7  ❌
3번째 줄 (이순신 CS 90) → 서브쿼리 실행 → CS 평균 86.7 → 90 > 86.7  ✅
4번째 줄 (강감찬 HR 70) → 서브쿼리 실행 → HR 평균 70.0 → 70 > 70.0  ❌
                          ────────────
                          서브쿼리 4번 실행!
```

| 👍 | 👎 |
|---|---|
| 문장이 짧다 | **줄 수만큼 반복 실행 → 느림** |
| "~보다 큰" 의도가 직관적 | 100만 줄이면 **100만 번** 실행 |
| | **평균값을 결과에 못 보여줌** |

---

## 방법 ② CTE — 미리 한 번만 계산

```sql
WITH major_avg AS (                          -- 1단계: 평균표를 만들어둔다
  SELECT s.major_code, AVG(e.score) AS avg_score
  FROM   student s JOIN enroll e ON s.id = e.student_id
  GROUP BY s.major_code
)
SELECT s.name, e.score, m.avg_score          -- 2단계: 그 표를 갖다 쓴다
FROM   student s
  JOIN enroll    e ON s.id = e.student_id
  JOIN major_avg m ON m.major_code = s.major_code
WHERE  e.score > m.avg_score;
```

**실행 과정**

```
1단계) major_avg 를 딱 한 번 계산 → 임시 표 완성

        | major_code | avg_score |
        | CS         | 86.7      |
        | HR         | 70.0      |

2단계) 이 표를 그냥 JOIN해서 비교
```

**결과 — 평균도 같이 보입니다**

| name | score | avg_score |
|---|:--:|:--:|
| 홍길동 | 90 | 86.7 |
| 이순신 | 90 | 86.7 |

| 👍 | 👎 |
|---|---|
| **평균 계산 1번** → 빠름 | 문장이 길어짐 |
| **위→아래로 읽는 순서 = 실행 순서** | JOIN을 한 번 더 써야 함 |
| **평균값을 결과에 표시 가능** | |
| 여러 번 재사용 가능 | |

---

## 방법 ③ Window Function — 줄을 유지한 채 옆에 붙임

> ⚠️ **중요** : Window Function은 **`WHERE`에 직접 쓸 수 없습니다.**
> `WHERE`가 Window 계산보다 **먼저** 실행되기 때문입니다. → **한 겹 감싸야 합니다.**

```sql
SELECT name, score, 학과평균
FROM (
  SELECT s.name, e.score,
         AVG(e.score) OVER (PARTITION BY s.major_code) AS 학과평균
  FROM   student s JOIN enroll e ON s.id = e.student_id
) t
WHERE score > 학과평균;
```

**실행 과정**

```
안쪽) 모든 줄을 유지한 채, 옆에 학과평균을 붙인다

   | name   | score | 학과평균 |
   | 홍길동 |  90   |  86.7   |
   | 홍길동 |  80   |  86.7   |
   | 이순신 |  90   |  86.7   |
   | 강감찬 |  70   |  70.0   |
                        ↑ 한 번의 스캔으로 전부 계산

바깥) 이 표에서 score > 학과평균 인 줄만 고른다
```

| name | score | 학과평균 |
|---|:--:|:--:|
| 홍길동 | 90 | 86.7 |
| 이순신 | 90 | 86.7 |

| 👍 | 👎 |
|---|---|
| **한 번의 스캔**으로 처리 → 가장 빠름 | **WHERE에 직접 못 씀** → 감싸야 함 |
| **집계값이 자연스럽게 옆에 붙음** | 처음엔 문법이 낯섦 |
| GROUP BY 없이 개별 행 + 집계 동시에 | |

> 🚨 **강의 자료 191p 오류 주의**
> 자료에는 이렇게 적혀 있는데 — **이 쿼리는 실행하면 에러가 납니다.**
> ```sql
> SELECT emp_name, salary,
>        AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
> FROM   employees
> WHERE  salary > AVG(salary) OVER (PARTITION BY dept_id);   -- ❌ ERROR
> ```
> `ERROR: window functions are not allowed in WHERE`
>
> **이유** : 실행 순서가 `WHERE → ... → Window 계산 → SELECT` 라서, WHERE 시점엔 Window 결과가 **아직 없습니다.**
> **해결** : 위 예시처럼 **서브쿼리나 CTE로 한 겹 감싸세요.**

---

## 방법 ④ 인라인 뷰 — CTE를 FROM 안에 직접

```sql
SELECT s.name, e.score, m.avg_score
FROM   student s
  JOIN enroll e ON s.id = e.student_id
  JOIN ( SELECT s2.major_code, AVG(e2.score) AS avg_score
         FROM   student s2 JOIN enroll e2 ON s2.id = e2.student_id
         GROUP BY s2.major_code ) m            -- ← CTE 내용을 여기 그대로
    ON m.major_code = s.major_code
WHERE  e.score > m.avg_score;
```

**CTE(②)와 성능·결과가 동일합니다.** 위치만 다릅니다.

| | CTE | 인라인 뷰 |
|---|---|---|
| 위치 | 쿼리 **맨 위** (WITH) | **FROM 절 안** |
| 가독성 | ✅ **좋음** (이름이 먼저 보임) | 중첩되면 나빠짐 |
| 재사용 | ✅ 여러 번 참조 가능 | ❌ 그 자리에서만 |

> 💡 **CTE는 "인라인 뷰를 위로 빼서 이름 붙인 것"** 이라고 생각하면 됩니다.

| **평균 계산 횟수** | **줄마다 (4번)** | 1번 | **1번** | 1번 |

| **가독성** | 중첩되면 나쁨 | ✅ **최고** | 좋음 | 중첩되면 나쁨 |
| **재사용** | ❌ | ✅ | ❌ | ❌ |
| **WHERE에 직접** | ✅ 가능 | ✅ 가능 | ❌ **감싸야 함** | ✅ 가능 |

# 6. 자주 막히는 지점 Q&A

## Q1. ON이 FROM보다 먼저 처리되나요?

**아니요. FROM이 먼저입니다.** ON은 **독립 단계가 아니라 JOIN 단계의 일부**입니다.

```
1. FROM student s      ← 왼쪽 테이블을 꺼낸다
2. JOIN enroll e       ← 오른쪽 테이블을 꺼낸다
     ON s.id = e...    ← 이 둘을 어떻게 붙일지 (JOIN과 한 세트)
3. WHERE ...           ← 다 붙은 표에서 줄을 고른다
```

테이블을 꺼내지도 않았는데 짝을 맺을 수는 없죠.

> 🔑 **중요한 건 이것** — **`ON`은 `WHERE`보다 먼저입니다.**
> ON이 표를 완성시키고, WHERE는 완성된 표에서 줄을 지웁니다. **이 순서 때문에 결과가 달라집니다.**

---

## Q2. 유관순은 "NULL이라서" 살아남은 건가요?

**반대입니다. 살아남았기 때문에 NULL이 채워진 것입니다.**

```
① LEFT JOIN이니까  →  유관순은 무조건 살린다    ← 살아남는 게 먼저
② 붙일 게 없다      →  그래서 NULL로 채운다      ← NULL은 결과
```

**증명 — 반례를 보세요.** 만약 홍길동이 DB를 안 듣고 알고리즘만 들었다면?

| id | name | course | score |
|:--:|---|---|:--:|
| 1 | **홍길동** | **NULL** | **NULL** |

**홍길동도 NULL 줄이 됩니다.** 유관순이 특별한 게 아니라, **짝이 없으면 누구든** 그렇게 됩니다.

---

## Q3. "알고리즘" 줄은 삭제된 건가요?

**ON에 조건을 쓴 경우 — 삭제가 아니라 "애초에 안 붙음"입니다.**

| | **ON에 조건** | **WHERE에 조건** |
|---|---|---|
| 알고리즘 줄 | **아예 짝으로 안 침** (붙은 적 없음) | **붙였다가 → 지움** |
| 유관순 줄 | 그 뒤에 **NULL로 만들어짐** ✅ | 만들어졌다가 → **지워짐** ⚠️ |
| 결과 | **4행** | **3행** |

```
[ON]     짝 맺을 때 걸러냄  →  유관순 NULL 줄은 그 다음에 생성  →  안전
[WHERE]  일단 다 붙임(유관순 NULL 줄 포함) → 조건으로 지움 → NULL 줄도 삭제
```

**WHERE가 유관순을 지우는 이유** : `NULL = 'DB'` 는 TRUE가 아닙니다. WHERE는 **TRUE인 줄만** 통과시킵니다.

---

## Q4. 2NF와 3NF가 계속 헷갈립니다

**"무엇이 결정하느냐"로 구분하세요.** 같은 표에 두 위반이 동시에 있습니다.

| 학번 | 이름 | 학과코드 | 학과명 | 과목 |
|:--:|---|:--:|---|---|
| 1 | 홍길동 | CS | 컴퓨터공학 | DB |

**PK = (학번, 과목)** ← 복합키

```
[2NF 위반]  "이름"을 알려면?
              학번만 있으면 안다 (과목 불필요)
              → PK의 "일부"가 결정            → 키 쪽 문제

[3NF 위반]  "학과명"을 알려면?
              학과코드만 있으면 안다
              → 학과코드는 PK가 아님!         → 비-키 쪽 문제
```

| | **2NF** | **3NF** |
|---|---|---|
| **무엇이 결정** | **PK의 일부** | **PK가 아닌 일반 컬럼** |
| **화살표** | `학번` → 이름 | `학과코드` → 학과명 |
| **문제 위치** | **키 쪽** | **비-키 쪽** |
| **언제 발생** | **PK가 복합키일 때만** | 항상 가능 |

### ⚡ 판별 순서

```
① PK가 컬럼 1개인가?
     YES →  2NF 자동 통과!  (쪼갤 "일부"가 없으니까)  → ③으로
     NO  →  ②로

② 복합키 중 "한쪽만" 있어도 알 수 있는 컬럼이 있나?   → 있으면 2NF 위반

③ PK 말고 "다른 일반 컬럼"만 있어도 알 수 있나?      → 있으면 3NF 위반
```

> 🔑 **한 줄 암기**
> **2NF** = "**키의 일부**만 봐도 안다" → **키 문제**
> **3NF** = "**키를 아예 안 봐도** 안다" → **비-키 문제**
>
> 💡 **PK가 단일 컬럼이면 2NF는 신경 쓸 필요 없습니다.** 2NF는 **복합키 전용 문제**입니다.

## Q5. FK는 "다른 데서 온 것"을 내 표에 표시하는 건가요?

**맞습니다. 컬럼을 실제로 가진 쪽(가리키는 쪽)에 표시합니다.**

```
   student (내 표)                    major (남의 표)
 ┌────────────────────┐           ┌──────────────────┐
 │ id (PK)            │           │ code (PK)        │
 │ name               │           │ name             │
 │ major_code  (FK) ──┼──가리킴──▶│ CS = 컴퓨터공학   │
 └────────────────────┘           └──────────────────┘
        ↑
   FK 표시는 여기!
```

**FK의 정확한 의미** : *"내 표의 이 컬럼 값은, 반드시 저 표의 PK 중 하나여야 한다"*

### 짚어둘 3가지

**① FK는 "복사"가 아니라 "포인터"**
```
❌ student에 학과명 "컴퓨터공학"을 복사 저장  →  중복! (3NF 위반)
✅ 코드 "CS"만 갖고, 이름이 필요하면 JOIN
```

**② 어느 쪽에 두나 → 1:N의 "N" 쪽**
```
학과 1개  ←──  학생 여러 명       (1 : N)
                    ↑
              여기(N쪽)에 FK
```
반대로 하면 `major` 표에 `학생1, 학생2, 학생3…` 컬럼을 만들어야 하는데 **몇 개일지 모릅니다.**

**③ 없는 값은 못 넣습니다 (참조 무결성)**
```sql
INSERT INTO student VALUES (5, '신사임당', 'ZZ');
-- ❌ 에러! major 표에 'ZZ' code가 없음
```
이게 FK를 거는 **진짜 이유**입니다. 오타·잘못된 값이 **DB 차원에서 막힙니다.**

## Q6. 약한 엔티티는 항상 부모와 같이 삭제되나요?

**개념상으로는 맞지만, DB가 알아서 해주진 않습니다. 설정해야 합니다.**

```sql
-- ❌ 아무 설정 없이
FOREIGN KEY (order_id) REFERENCES orders(id)
-- 주문 삭제 시도 → 에러! "자식이 남아 있어 부모를 못 지웁니다" (RESTRICT가 기본)

-- ✅ CASCADE 명시
FOREIGN KEY (order_id) REFERENCES orders(id) ON DELETE CASCADE
-- 주문 삭제 → 주문상세도 자동 삭제 ✅
```

> 🔑 자료의 **"`ON DELETE CASCADE` 필수"** 는
> *"자동으로 된다"* 가 아니라 **"설계할 때 반드시 지정하라"** 는 뜻입니다.
> 안 하면 **부모 삭제 자체가 거부**됩니다.

### ⚠️ 방향은 한쪽뿐

```
부모(주문) 삭제      →  자식(주문상세) 삭제    ✅  CASCADE
자식(주문상세) 삭제  →  부모(주문)는 그대로     ✅  당연
```

주문상세 한 줄 지웠다고 주문 전체가 사라지면 안 되겠죠. **CASCADE는 위에서 아래로만 흐릅니다.**

## Q7. COUNT(\*)와 COUNT(컬럼)이 왜 다른가요?

**질문** : "학생별로 몇 과목 들었나?"

**LEFT JOIN 결과에서 유관순 그룹만 확대해 봅시다.**

```
    ┌─────────────────────┐
    │ 유관순 │  NULL      │   ←  줄이 1개 있다 (내용은 비었지만)
    └─────────────────────┘

  COUNT(*)       =  "줄이 몇 개?"          →  1
  COUNT(course)  =  "course 값이 몇 개?"   →  0   (NULL은 안 셈)
```

| name | `COUNT(*)` | `COUNT(e.course)` | **실제 수강** |
|---|:--:|:--:|:--:|
| 홍길동 | 2 | 2 | 2 |
| 이순신 | 1 | 1 | 1 |
| 강감찬 | 1 | 1 | 1 |
| **유관순** | **1** ❌ | **0** ✅ | **0** |

**왜 이런 일이**
```
LEFT JOIN이 유관순을 살리려고
"내용은 비었지만 자리는 있는 줄"을 하나 만들었습니다.

COUNT(*)      : 그 빈 줄도 "줄이니까" 세어버림   →  1  (거짓말!)
COUNT(course) : 내용이 NULL이니까 안 셈         →  0  (정답)
```

| | 세는 대상 | NULL은? |
|---|---|---|
| `COUNT(*)` | **줄** | **셈** |
| `COUNT(컬럼)` | **그 컬럼의 값** | **안 셈** |

> 🔑 **LEFT JOIN 뒤 COUNT는 무조건 `COUNT(컬럼)`.**
> `COUNT(*)`를 쓰면 **수강 0건인 학생이 1건으로 둔갑**합니다.

## Q8. Materialized(머터리얼라이즈드)가 뭔가요?

**단어 뜻** : `material`(물질, 실체) → `materialized` = **"실체가 된"**

> View는 원래 **실체가 없는 가상의 표**입니다.
> 여기에 **실체(=실제 데이터)를 부여**한 것이 **Materialized View**입니다.

### 🍱 비유

| | **View** | **Materialized View** |
|---|---|---|
| 정체 | **레시피** 📝 | **미리 만들어둔 도시락** 🍱 |
| 저장된 것 | **쿼리문** | **결과 데이터** |
| 조회 시 | 레시피 보고 **매번 요리** | 꺼내서 **바로 먹음** |
| 속도 | 느림 | **빠름** |
| 신선도 | **항상 최신** | 만든 시점 그대로 (**시간 지나면 상함**) |

### 💥 결정적 차이 — 데이터가 바뀌면

```sql
-- 강감찬이 알고리즘 100점을 추가 수강
INSERT INTO enroll VALUES (3, '알고리즘', 100);
-- HR 평균은 (70+100)/2 = 85.0 이 되어야 맞음
```

| | HR 평균 조회 결과 |
|---|---|
| **View** | **85.0** ✅ (매번 다시 계산하니까) |
| **Materialized View** | **70.0** ❌ (**저장된 옛날 값**) |

```sql
REFRESH MATERIALIZED VIEW mv_major_avg;   -- 이제야 85.0
```

> ⚠️ **자동 갱신 안 됩니다.** 사람이 직접 하거나 `pg_cron` 같은 스케줄러로 걸어둬야 합니다.

### 그럼 왜 쓰나 — **속도**

```
주문 1억 건을 월별 집계하는 뷰

  View  :  조회마다 1억 건 스캔  →  30초  (새로고침마다 30초 😱)
  MV    :  계산된 12줄만 읽음    →  0.01초 ✅  (대신 "어젯밤 3시 기준")
```

**그리고 MV만의 강점 — 인덱스를 걸 수 있습니다.**
```sql
CREATE INDEX ON mv_major_avg (major_code);   -- ✅ MV는 실제 표라서 가능
                                             -- ❌ View는 실체가 없어 불가
```

### 📊 표 4형제

| | **테이블** | **View** | **Materialized View** | **CTE** |
|---|---|---|---|---|
| **저장되는 것** | 데이터 | **쿼리문** | **결과 데이터** | 아무것도 |
| **실체** | 있음 | **없음** | **있음** | 없음 |
| **언제 계산** | — | 조회할 때마다 | 만들 때 + **REFRESH** | 쿼리 실행 중에만 |
| **인덱스** | ✅ | ❌ | ✅ | ❌ |
| **최신성** | 실시간 | **항상 최신** | **REFRESH 시점까지** | 그 순간 |
| **재사용** | ✅ | ✅ | ✅ | ❌ 그 쿼리 안에서만 |

### 🎯 언제 쓰나

> **판단 기준 한 줄 — "이 숫자가 5분 늦어도 괜찮은가?"**
> - 괜찮다 → **MV** (대시보드, 무거운 집계, 일 1회 배치)
> - 안 된다 → **View** (계좌 잔액, 재고 수량)

### 🔁 CTE에도 나오는 MATERIALIZED

```sql
WITH x AS MATERIALIZED     ( ... )   -- 결과를 임시 실체화 → 딱 한 번만 계산
WITH x AS NOT MATERIALIZED ( ... )   -- 본 쿼리에 녹여 넣음 → 옵티마이저가 통째 최적화 (기본)
```

**같은 단어, 같은 뜻** — *"결과를 실제로 만들어 들고 있을래?"*

**MATERIALIZED를 강제할 때**
```
① CTE를 여러 번 참조할 때         → 매번 계산하면 손해
② 안에 random(), now() 가 있을 때 → 매번 값이 달라지면 곤란
③ 옵티마이저가 이상한 플랜을 짤 때 → 강제로 고정
```

> 💡 PostgreSQL 12 이전엔 **CTE가 항상 MATERIALIZED**였습니다 (그래서 "CTE는 최적화 장벽"이라는 말이 있었죠). 12부터 **기본이 NOT MATERIALIZED**로 바뀌었습니다.

## 🚨 [정오] 강의 자료 191p — Window Function을 WHERE에 쓸 수 없습니다

강의 자료에 이 쿼리가 "빠른 방법"으로 실려 있는데, **실행하면 에러가 납니다.**

```sql
SELECT emp_name, salary, dept_id,
       AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
FROM   employees
WHERE  salary > AVG(salary) OVER (PARTITION BY dept_id);   -- ❌
```
```
ERROR:  window functions are not allowed in WHERE
```

**이유** — 실행 순서 때문입니다.

```
FROM → WHERE → GROUP BY → HAVING → [Window 계산] → SELECT → ORDER BY
         ↑                              ↑
      여기선 아직                    여기서 계산됨
   Window 결과가 없음
```

**✅ 올바른 방법 — 한 겹 감싸기**

```sql
-- 서브쿼리로 감싸기
SELECT * FROM (
  SELECT emp_name, salary, dept_id,
         AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
  FROM   employees
) t
WHERE salary > dept_avg;

-- 또는 CTE로
WITH t AS (
  SELECT emp_name, salary, dept_id,
         AVG(salary) OVER (PARTITION BY dept_id) AS dept_avg
  FROM   employees
)
SELECT * FROM t WHERE salary > dept_avg;
```

> 💡 **같은 이유로 `GROUP BY`, `HAVING`에도 Window Function을 쓸 수 없습니다.**
> Window를 쓸 수 있는 곳은 **`SELECT` 절과 `ORDER BY` 절뿐**입니다.
