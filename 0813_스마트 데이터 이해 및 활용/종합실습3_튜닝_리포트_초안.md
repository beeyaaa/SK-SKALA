# 종합실습 3 - HR DB 느린 쿼리 튜닝 리포트

- 소속: 판교 5반
- 성명: 홍은비
- DBMS: PostgreSQL 17
- 주요 테이블: `hr.employees` 50,000건
- 측정 명령: `EXPLAIN (ANALYZE, BUFFERS)`

> 실행시간은 캐시와 PC 상태에 따라 달라질 수 있다. 버퍼는 각 실행계획의 최상위 실행 노드에 표시된 누적 `Buffers` 값을 기록했으며, `Planning` 버퍼는 비교에서 제외했다.

## 1. 실습 목적

같은 결과를 반환하는 SQL이라도 조건식과 인덱스 설계에 따라 처리 방식과 성능이 달라질 수 있다. 본 실습에서는 컬럼 함수, 선행 와일드카드, 필터와 정렬, OR와 UNION이 실행계획에 미치는 영향을 확인한다. 각 느린 쿼리에 대해 독립적인 튜닝 방법을 적용하고, Scan 방식·버퍼·실행시간을 튜닝 전후로 비교한다.

## 2. `lower(email)` 이메일 검색

### 2-1. 함수 기반 인덱스 방식

#### 느린 이유

기존 `employees_email_key` B-tree 인덱스는 원본 `email` 값을 색인한다. 그러나 검색 조건은 `lower(email)`이므로 인덱스에 저장된 키와 표현식이 다르다. 전용 표현식 인덱스가 없으면 PostgreSQL은 50,000개의 email에 `lower()`를 적용하며 전체 테이블을 검색할 수 있다.

#### 개선 방법과 주요 효과

조회식과 같은 `lower(email)` 표현식 인덱스를 생성했다. 애플리케이션 SQL을 변경하지 않고도 해당 표현식의 인덱스 탐색이 가능해진다. 전체 행에 함수를 계산하는 작업과 불필요한 버퍼 접근이 감소할 것으로 예상했다.

| 구분 | Scan 방식 | Rows Removed | Buffers | Execution Time |
|---|---|---:|---:|---:|
| 2-1 튜닝 전 | Seq Scan | 49,999 | `shared hit=786` | 35.924 ms |
| 2-1 튜닝 후 | Index Scan (`lab_q2_lower_email_idx`) | - | `shared hit=1, read=3` | 0.274 ms |

튜닝 후에는 50,000행 전체를 검사하던 Seq Scan이 표현식 인덱스를 사용하는 Index Scan으로 변경되었다. 실행시간은 35.924ms에서 0.274ms로 약 99.24% 감소했고, 실행 버퍼도 786개 히트에서 히트 1개와 읽기 3개로 크게 감소했다.

### 2-2. 소문자 저장 규칙을 이용한 SQL 재작성

#### 느린 이유

입력값이 이미 소문자인데도 `lower(email) = 'user1234@corp.com'`으로 작성하면 저장된 50,000개 email에 불필요하게 `lower()`를 적용한다. 이로 인해 이미 존재하는 UNIQUE(email) 인덱스를 활용하지 못한다.

#### 개선 방법과 주요 효과

환경설정 SQL은 email을 `lower()`로 저장한다. 따라서 `email = 'user1234@corp.com'`으로 컬럼 함수를 제거했다. 추가 인덱스 없이 기존 UNIQUE 인덱스를 재사용하므로 저장공간과 INSERT/UPDATE 유지비용이 추가되지 않는다.

| 구분 | Scan 방식 | Rows Removed | Buffers | Execution Time |
|---|---|---:|---:|---:|
| 2-2 튜닝 전 | Seq Scan | 50,000 | `shared hit=786` | 16.353 ms |
| 2-2 튜닝 후 | Index Scan (`employees_email_key`) | - | `shared hit=3` | 0.039 ms |

컬럼에서 `lower()`를 제거한 후 기존 UNIQUE 인덱스를 사용하는 Index Scan으로 변경되었다. 튜닝 후에는 대상 행 1건을 정상적으로 반환했으며, 실행 버퍼는 `shared hit=3`, 실행시간은 0.039ms로 측정되었다. 기존 튜닝 전 측정값 16.353ms와 비교하면 약 99.76% 감소했다.

### 2번 쿼리 차이·조별 의견·최적 포인트

2-1은 기존 SQL을 유지하기 위한 방법이지만 추가 인덱스 관리비용이 발생한다. 2-2는 데이터의 소문자 표준화가 보장될 때 기존 UNIQUE 인덱스를 재사용한다. 조원들은 입력 규칙을 보장할 수 있다면 2-2가 가장 간단하고 유지비용이 낮으며, 기존 SQL을 변경할 수 없다면 2-1이 적합하다고 판단했다.

## 3. Gmail 접미사 검색

### 3-1. `pg_trgm` GIN 인덱스

#### 느린 이유

`LIKE '%gmail.com'`은 앞에 `%`가 있어 B-tree가 탐색할 문자열의 시작값을 알 수 없다. 따라서 일반 email 인덱스로는 접미사 검색을 빠르게 처리하기 어렵고 전체 스캔이 발생할 수 있다.

#### 개선 방법과 주요 효과

`pg_trgm`의 GIN 인덱스를 생성했다. 이 인덱스는 문자열을 삼항으로 색인하여 SQL을 변경하지 않고도 부분 문자열 후보를 빠르게 찾을 수 있다. 전체 50,000행 대신 gmail 후보만 확인하므로 스캔 범위와 실행시간이 감소할 수 있다.

| 구분 | Scan 방식 | Buffers | Execution Time |
|---|---|---:|---:|
| 3-1 튜닝 전 | Seq Scan | `shared hit=786` | 13.746 ms |
| 3-1 튜닝 후 | Bitmap Heap Scan + GIN Bitmap Index Scan | `shared hit=745` | 2.429 ms |

GIN 인덱스 적용 후 Seq Scan이 Bitmap Index Scan과 Bitmap Heap Scan으로 변경되었다. 후보 1,502건을 비트맵으로 찾았으며 실행시간은 13.746ms에서 2.429ms로 약 82.33% 감소했다.

### 3-2. `right(email, 10)` 표현식 B-tree 인덱스

#### 느린 이유

표현식 인덱스가 없는 상태에서 `right(email, 10)`을 사용하면 50,000행 모두에 함수를 적용한 뒤 `@gmail.com`과 비교해야 한다.

#### 개선 방법과 주요 효과

조회식과 같은 `right(email, 10)` 표현식을 B-tree로 색인했다. 매번 전체 행에 `right()`를 계산하는 대신 미리 색인된 접미사 값을 탐색할 수 있다.

| 구분 | Scan 방식 | Buffers | Execution Time |
|---|---|---:|---:|
| 3-2 튜닝 전 | Seq Scan | `shared hit=786` | 11.984 ms |
| 3-2 튜닝 후 | Bitmap Heap Scan + 표현식 Bitmap Index Scan | `shared hit=663` | 0.965 ms |

`right(email, 10)` 표현식 인덱스 적용 후 전체 스캔이 제거되었다. 실행시간은 11.984ms에서 0.965ms로 약 91.95% 감소했고, 실행 버퍼는 786에서 663으로 감소했다.

### 3번 쿼리 차이·조별 의견·최적 포인트

3-1은 임의의 부분 문자열 검색에 범용적이지만 GIN 인덱스의 크기와 쓰기 유지비용이 클 수 있다. 3-2는 단순하지만 10글자 접미사 조회에 종속된다. 조원들은 다양한 부분 검색이 필요하면 3-1을 선택하고, 이메일 도메인만 자주 검색한다면 실무적으로는 domain 컬럼을 분리해 일반 B-tree를 사용하는 방법이 가장 명확하다고 판단했다.

## 4. 최근 365일 ACTIVE 직원의 연봉 상위 100명

### 4-1. LIMIT + 정렬 우선 복합/커버링 인덱스

#### 느린 이유

튜닝 전에는 `status`, `hire_date` 필터와 `salary DESC, employee_id` 정렬을 지원하는 인덱스가 없다. 따라서 전체 테이블에서 약 9,500개의 최근 ACTIVE 행을 찾고 Top-N Sort를 수행한 뒤 100건을 추출할 수 있다.

#### 개선 방법과 주요 효과

`(salary DESC, employee_id)` 복합 인덱스를 생성하고 `email`, `hire_date`, `status`를 INCLUDE했다. `ORDER BY salary DESC, employee_id`와 인덱스 순서를 일치시켜 이미 정렬된 순서로 읽다가 최근 ACTIVE 입사자 100명을 채우면 중단할 수 있게 했다. 조회 컬럼을 모두 인덱스에 포함해 Index Only Scan을 유도했다.

| 구분 | Scan/Sort 방식 | Buffers | Execution Time |
|---|---|---:|---:|
| 4-1 튜닝 전 | Seq Scan + Top-N heapsort | `shared hit=786` | 20.050 ms |
| 4-1 튜닝 후(최종) | Index Only Scan, Sort 제거 | `shared hit=11` | 0.169 ms |

최종 커버링 인덱스 적용 후 Seq Scan과 Top-N Sort가 제거되고 `idx_employees_salary_desc_cover`를 사용하는 Index Only Scan으로 변경되었다. 최근 ACTIVE 조건을 만족하는 100명을 찾는 과정에서 482행이 필터되었고, Heap Fetches는 2회였다. 실행시간은 20.050ms에서 0.169ms로 약 99.16% 감소했고, 실행 버퍼는 786에서 11로 감소했다.

#### 4-1 기존 본인 코드와 최종 코드 비교

| 구분 | 인덱스 키 | INCLUDE | Buffer | Execution Time |
|---|---|---|---:|---:|
| 기존 본인 코드 | `(status, salary DESC, employee_id)` | `(email, hire_date)` | 10 | 0.147 ms |
| 최종 조별 코드 | `(salary DESC, employee_id)` | `(email, hire_date, status)` | 11 | 0.169 ms |

기존 코드는 `status` 동등 조건을 인덱스의 선두에 두어 ACTIVE 범위 내에서 정렬된 값을 읽는 방식이다. 최종 조별 코드는 `salary DESC, employee_id`를 선두에 두어 status와 관계없이 연봉순 조회에 재사용할 수 있다. 본인 환경의 단일 측정에서는 기존 코드가 0.147ms, 최종 코드가 0.169ms로 기존 코드가 미세하게 빨랐지만 차이는 0.022ms로 매우 작다. 두 방식 모두 Index Only Scan과 정렬 제거에 성공했으며, 특정 status 조회만 자주 실행하면 기존 방식이, 다양한 status의 연봉순 조회에 재사용하려면 최종 방식이 적합하다.

### 4-2. FETCH FIRST + ACTIVE 전용 부분 인덱스

#### 느린 이유

`FETCH FIRST 100 ROWS ONLY`도 LIMIT와 같은 상위 100건을 요청한다. 튜닝 전에는 ACTIVE 행 필터와 정렬을 지원하는 인덱스가 없으므로 Seq Scan과 Top-N Sort가 발생할 수 있다.

#### 개선 방법과 주요 효과

ACTIVE 행만 색인하는 `(salary DESC, employee_id) WHERE status='ACTIVE'` 부분 인덱스를 생성했다. 전체 employees보다 인덱스 범위를 줄이고 `ORDER BY`와 순서를 일치시켰다. 최근 입사자 100명을 찾으면 스캔을 조기 중단할 수 있다.

| 구분 | Scan/Sort 방식 | Buffers | Execution Time |
|---|---|---:|---:|
| 4-2 튜닝 전 | Seq Scan + Top-N heapsort | `shared hit=786` | 17.530 ms |
| 4-2 튜닝 후 | Partial Index Only Scan, Sort 제거 | `shared hit=10` | 0.146 ms |

ACTIVE 전용 부분 인덱스 적용 후 별도 정렬 없이 연봉순으로 스캔하였다. 최근 입사자 100명을 찾기 위해 456행만 필터에서 제거한 뒤 조기 중단했다. 실행시간은 17.530ms에서 0.146ms로 약 99.17% 감소했다.

### 4번 쿼리 차이·조별 의견·최적 포인트

LIMIT와 FETCH FIRST는 현재 PostgreSQL 실행계획에서 거의 동일한 의미를 가진다. 실질적인 차이는 문법보다 인덱스 설계에 있다. 4-1은 `status`를 인덱스 키로 포함하여 다른 status 조회에도 활용할 수 있고, 4-2는 ACTIVE 행만 색인하여 크기가 작다. 현재 조회가 ACTIVE에 고정된다면 4-2의 부분 인덱스가 더 적합하며, 다양한 status 조회가 필요하면 4-1이 재사용성이 높다.

## 5. 부서 또는 직무 검색

### 5-1. OR 유지 + 개별 인덱스

#### 느린 이유

`department_id` 조건과 `job_id` 조건은 서로 다른 컬럼에 있다. 두 컬럼에 인덱스가 없으면 OR의 한 쪽을 만족하는지 확인하기 위해 50,000행을 전체 스캔할 수 있다.

#### 개선 방법과 주요 효과

`department_id`, `job_id`에 각각 B-tree 인덱스를 생성했다. PostgreSQL은 각 조건의 인덱스 비트맵을 `BitmapOr`로 결합하여 원본 OR SQL을 유지하면서 전체 스캔을 줄일 수 있다.

| 구분 | Scan 방식 | Buffers | Execution Time |
|---|---|---:|---:|
| 5-1 튜닝 전 | Seq Scan | `shared hit=786` | 13.464 ms |
| 5-1 튜닝 후 | BitmapOr + Bitmap Heap Scan | `shared hit=788` | 2.195 ms |

튜닝 후 PostgreSQL은 `department_id`와 `job_id`의 개별 인덱스를 BitmapOr로 결합했다. 실행 버퍼는 786에서 788로 거의 같았지만, 50,000행에 두 조건을 평가하는 작업이 사라져 실행시간은 13.464ms에서 2.195ms로 약 83.70% 감소했다. 따라서 버퍼 수만이 아니라 CPU 필터 연산과 실행시간을 함께 보아야 한다.

### 5-2. UNION으로 조건 분리

#### 느린 이유

튜닝 전 UNION SQL은 department 분기와 job 분기에서 각각 Seq Scan이 발생할 수 있다. 또한 두 분기의 결과를 합친 후 UNION이 Sort/Unique 또는 HashAggregate로 중복을 제거해야 한다.

#### 개선 방법과 주요 효과

각 조건에 해당하는 행만 저장하는 부분 커버링 인덱스를 생성했다. 반환할 컬럼을 `INCLUDE`하여 Index Only Scan을 유도했고, `UNION`을 `UNION ALL`로 변경해 HashAggregate 중복 제거를 없앰다. `UNION ALL`이 중복을 제거하지 않는 문제는 두 번째 분기에 `department_id <> 10`을 추가해 논리적으로 해결했다.

| 구분 | 분기 Scan / 중복 제거 | Buffers | Execution Time |
|---|---|---:|---:|
| 5-2 튜닝 전 | Seq Scan 2회 + HashAggregate | `shared hit=1572` | 70.309 ms |
| 5-2 튜닝 후(최종) | Index Only Scan 2회 + Append | `shared hit=40` | 0.801 ms |

최종 튜닝 후 최상위 노드는 HashAggregate가 아닌 Append로 변경되었고, 두 분기 모두 부분 커버링 인덱스를 사용한 Index Only Scan으로 처리되었다. 반환 행 수는 4,062건으로 기존 결과와 동일했다. 실행 버퍼는 1,572에서 40으로 약 97.46% 감소했고, 실행시간은 70.309ms에서 0.801ms로 약 98.86% 감소했다. 실행계획에서 Heap Fetches는 첫 분기 1회, 두 번째 분기 6회로 총 7회였다. 완전히 0은 아니지만 테이블 접근이 매우 적어 Index Only Scan의 효과가 확인되었다.

#### 5-2 기존 본인 코드와 최종 코드 비교

| 구분 | 인덱스 | 합침 방식 | 최상위 연산 | Buffer | Execution Time |
|---|---|---|---|---:|---:|
| 기존 본인 튜닝 | 일반 단일 컬럼 인덱스 2개 | `UNION` | HashAggregate | 975 | 4.082 ms |
| 최종 조별 튜닝 | 부분 커버링 인덱스 2개 | `UNION ALL` + 중복 방지 조건 | Append | 40 | 0.801 ms |

기존 본인 코드는 일반 인덱스로 후보를 찾은 뒤 Heap에 접근하고 `UNION` 중복 제거를 위해 HashAggregate를 수행했다. 최종 코드는 조건별 부분 인덱스로 색인 범위를 줄이고, 조회 컬럼을 INCLUDE해 Heap 접근을 거의 제거했다. 또한 `UNION ALL`과 `department_id <> 10`의 조합으로 결과 중복 없이 HashAggregate를 제거했다. 기존 튜닝 결과와 비교하면 실행시간은 4.082ms에서 0.801ms로 약 80.38%, 버퍼는 975에서 40으로 약 95.90% 추가 감소했다.

### 5번 쿼리 차이·조별 의견·최적 포인트

5-1은 SQL이 간결하고 PostgreSQL이 BitmapOr로 두 인덱스를 결합할 수 있다. 5-2는 각 조건의 실행 경로를 분리하여 확인하기 쉽지만, UNION의 중복 제거 비용과 SQL 복잡도가 추가된다. 조원들은 개별 인덱스와 원본 OR를 우선 적용하고, 실행계획이 여전히 비효율적이거나 각 분기를 독립적으로 관리해야 할 때 UNION을 비교하는 것이 적합하다고 판단했다.

### 6.2 최종 분석

튜닝은 인덱스를 무조건 추가하는 작업이 아니라 조회 패턴과 데이터 규칙에 맞는 실행 경로를 선택하는 작업이다. 2번에서는 컬럼 함수를 제거하거나 동일한 표현식 인덱스를 사용했고, 3번에서는 선행 와일드카드와 접미사 함수에 맞는 GIN/표현식 인덱스를 적용했다. 4번에서는 `ORDER BY` 순서와 인덱스 순서를 일치시켜 정렬을 제거했으며, 5번에서는 OR의 개별 인덱스 결합과 부분 커버링 인덱스를 검증했다.

조별 비교에서 같은 튜닝 구조를 사용해도 실행시간과 버퍼는 캐시 상태, `random()`으로 생성된 데이터 분포, 물리적 페이지 배치, Visibility Map 상태에 따라 달랐다. 따라서 절대 시간만으로 코드를 평가하지 않고 Seq Scan이 인덱스 스캔으로 변경되었는지, Sort와 HashAggregate가 제거되었는지, Heap Fetches와 읽은 페이지 수가 줄었는지를 함께 확인했다.

특히 5-2에서 기존 본인 코드는 일반 인덱스를 사용해도 HashAggregate와 Heap 접근이 남았지만, 최종 코드는 부분 커버링 인덱스와 `UNION ALL`을 사용해 실행시간과 버퍼를 추가로 크게 줄였다. 이는 인덱스 생성만으로 끝나는 것이 아니라 중복 방지 논리를 SQL에 명시하여 불필요한 집계 연산을 제거하는 것도 핵심 튜닝 포인트임을 보여준다.
