## 0. 오늘 무엇을 배우는가

1일차에는 하나의 모델 파일을 애플리케이션에서 불러와 API로 제공하는 가장 기본적인 구조를 배웠다.

```text
사용자 → FastAPI → 모델 하나 → 예측 결과
```

실제 시스템에서는 다음과 같은 요구가 생긴다.

- 수백만 건을 정해진 시간에 한꺼번에 예측해야 한다.
- 전처리, 모델 A, 모델 B, 후처리를 순서대로 실행해야 한다.
- 여러 모델의 결과를 결합해야 한다.
- 모델 결과에 회사 정책과 업무 규칙을 적용해야 한다.
- 요청량에 따라 서버를 자동으로 늘리거나 줄여야 한다.
- Large Language Model(LLM)을 높은 처리량으로 제공해야 한다.

2일차는 단일 모델 API를 넘어 모델 서빙 시스템을 확장하는 방법을 다룬다.

## 1. Batch Training과 Batch Serving

> 원본 PDF 127~136쪽

### 1.1 Batch의 의미

**Batch(배치)**는 데이터를 일정량 모은 뒤 한 번에 처리하는 방식이다.

- **Batch Training(배치 학습)**: 일정 기간 동안 모인 데이터를 이용해 정해진 시점에 모델을 학습한다.
- **Batch Serving 또는 Batch Inference(배치 서빙/배치 추론)**: 많은 입력에 대한 예측을 한 번에 계산해 파일이나 데이터베이스에 저장한다.

```text
[Batch Training]
지난 1주일의 데이터
→ 전처리
→ 모델 학습
→ 평가
→ 새 모델 등록

[Batch Serving]
전체 고객 데이터
→ 모델 추론
→ 고객별 예측 결과 저장
```

### 1.2 Online Serving과의 차이

| 구분 | Batch Serving | Online Serving |
|---|---|---|
| 처리 시점 | 예약된 시점 또는 데이터가 모였을 때 | 요청이 들어오는 즉시 |
| 최적화 목표 | 대량 처리량과 자원 효율 | 낮은 지연시간과 가용성 |
| 결과 저장 | 파일, 데이터베이스, Data Warehouse | 요청한 클라이언트에 즉시 응답 |
| 예시 | 매일 새벽 고객 이탈 점수 계산 | 결제 순간 이상 거래 탐지 |
| 대표 실패 | 작업 일부 실패, 중복 처리 | 타임아웃, 순간 과부하 |

Batch와 Online 중 하나만 선택해야 하는 것은 아니다. 같은 모델을 정기적인 전체 고객 점수 계산에는 Batch로, 실시간 신규 요청에는 Online으로 제공할 수 있다.

### 1.3 배치 처리에서 중요한 개념

#### Scheduling

**Scheduling(스케줄링)**은 작업을 언제 실행할지 정하는 것이다. 예를 들어 매일 오전 2시에 학습 파이프라인을 실행한다.

#### Idempotency

**Idempotency(멱등성)**는 같은 작업을 여러 번 실행해도 결과가 한 번 실행한 것과 같아야 한다는 성질이다.

배치 작업이 중간에 실패해 다시 실행될 수 있으므로 중복 데이터나 중복 예측 결과가 생기지 않도록 설계해야 한다.

#### Backfill

**Backfill(백필)**은 과거 특정 기간의 데이터를 다시 처리하는 작업이다. 로직 수정이나 데이터 누락이 발견되었을 때 사용한다.

#### Checkpoint

**Checkpoint(체크포인트)**는 긴 작업의 진행 상태를 저장하는 지점이다. 실패 후 처음부터 다시 실행하지 않고 저장된 지점부터 복구할 수 있다.

### 1.4 배치 학습의 기본 흐름

```text
원천 데이터 수집
→ 데이터 검증
→ 전처리와 Feature 생성
→ 학습·검증 데이터 분리
→ 모델 학습
→ 모델 평가
→ 승인 기준 확인
→ Artifact Store 저장
→ Model Registry 등록
→ 배포 또는 기존 모델 유지
```

새 모델의 평가 점수가 기준에 미달하면 자동 배포하지 않아야 한다. 학습 완료와 배포 승인은 별개의 단계다.

### 이 장에서 기억할 것

- Batch Training은 모델을 주기적으로 다시 만드는 과정이다.
- Batch Serving은 많은 데이터를 모아 한 번에 예측하는 과정이다.
- 배치 시스템은 재실행을 전제로 멱등성, 체크포인트, 백필을 고려해야 한다.
- 새 모델이 만들어졌다고 자동으로 운영 배포되어야 하는 것은 아니다.

## 2. Pipeline Model Serving

> 원본 PDF 137~175쪽

### 2.1 파이프라인이 필요한 이유

실제 예측은 모델 하나를 호출하는 것으로 끝나지 않는 경우가 많다.

```text
원본 입력
→ 유효성 검사
→ 전처리
→ Feature 생성
→ 모델 추론
→ 후처리
→ 결과 저장 또는 응답
```

이처럼 여러 작업을 순서와 의존관계에 따라 연결한 구조를 **Pipeline(파이프라인)**이라고 한다.

각 단계는 앞 단계의 출력을 받아 다음 단계가 사용할 출력을 만든다. 따라서 단계 사이의 데이터 형식인 **Data Contract(데이터 계약)**가 명확해야 한다.

### 2.2 Workflow와 DAG

**Workflow(워크플로)**는 작업들이 어떤 순서와 조건으로 실행되는지를 정의한 전체 과정이다.

**DAG(Directed Acyclic Graph, 방향성 비순환 그래프)**는 작업 사이의 의존관계를 나타내는 구조다.

- Directed: 작업 진행 방향이 있다.
- Acyclic: 작업이 순환해 무한히 반복되지 않는다.
- Graph: 작업을 Node, 의존관계를 Edge로 표현한다.

```text
데이터 수집
   ├→ 품질 검사 ─┐
   └→ 통계 생성 ─┼→ 모델 학습 → 평가 → 등록
                 ┘
```

### 2.3 Orchestration과 Airflow

**Orchestration(오케스트레이션)**은 여러 작업의 실행 순서, 스케줄, 재시도, 상태를 중앙에서 관리하는 것이다.

**Apache Airflow**는 Python 코드로 DAG를 정의하고 작업을 스케줄링하는 Workflow Orchestrator다. 머신러닝 전용 도구는 아니지만 데이터와 모델 파이프라인에 널리 사용된다.

Airflow의 주요 개념:

| 용어 | 의미 |
|---|---|
| DAG | 실행할 작업과 의존관계의 정의 |
| Task | DAG 안의 개별 작업 |
| Operator | Task가 무엇을 실행할지 정의하는 템플릿 |
| Scheduler | 실행 시점을 판단하고 작업을 예약하는 구성 요소 |
| Executor | 예약된 작업을 실제로 실행하는 방식 |
| XCom | Task 사이에 소량의 메타데이터를 전달하는 기능 |

큰 모델 파일이나 데이터셋을 XCom으로 직접 전달하는 것은 적합하지 않다. 실제 파일은 Object Storage나 공유 저장소에 두고, XCom에는 경로나 식별자만 전달하는 편이 안전하다.

### 2.4 학습 파이프라인과 서빙 파이프라인

두 파이프라인은 목적이 다르다.

#### Training Pipeline

```text
데이터 준비
→ 학습
→ 평가
→ 모델 등록
```

새로운 모델 버전을 만드는 과정이다.

#### Serving Pipeline

```text
요청 입력
→ 전처리
→ 모델 1 추론
→ 모델 2 추론
→ 후처리
→ 응답
```

이미 학습된 모델을 사용해 예측 결과를 만드는 과정이다.

### 2.5 단계 분리의 장점

- 특정 단계만 교체하거나 다시 실행할 수 있다.
- 단계별 실행 시간과 오류를 관찰할 수 있다.
- CPU 작업과 GPU 작업을 다른 자원에서 실행할 수 있다.
- 여러 팀이 각 단계의 책임을 나눌 수 있다.

### 2.6 단계 분리의 비용

- 네트워크 호출과 직렬화 비용이 늘어난다.
- 부분 실패와 재시도 정책이 복잡해진다.
- 모델과 데이터 버전의 조합을 추적해야 한다.
- 전체 Latency는 각 단계 Latency의 합과 대기시간으로 결정된다.

### 2.7 Pipeline 설계 체크 포인트

- 각 단계의 입력·출력 Schema가 명확한가?
- 실패한 단계만 다시 실행할 수 있는가?
- 재시도해도 중복 결과가 생기지 않는가?
- 단계별 Timeout과 Retry 정책이 있는가?
- 모델, 데이터, 코드 버전을 함께 기록하는가?
- 개인정보나 민감정보가 단계 사이에 불필요하게 전달되지 않는가?

### 이 장에서 기억할 것

- Pipeline은 여러 작업을 의존관계에 따라 연결한 구조다.
- DAG는 작업 순서를 방향성 비순환 그래프로 표현한다.
- Airflow는 모델 자체를 실행하는 런타임이 아니라 작업을 조정하는 Orchestrator다.
- Training Pipeline과 Serving Pipeline은 목적과 운영 특성이 다르다.

## 3. Ensemble Model Serving Pattern

> 원본 PDF 176~187쪽

### 3.1 Ensemble의 목적

하나의 모델은 특정 데이터나 오류 유형에 약할 수 있다. 여러 모델의 예측을 결합하면 개별 모델의 편향과 분산을 줄이고 더 안정적인 결과를 얻을 수 있다.

이를 **Ensemble Model Serving(앙상블 모델 서빙)**이라고 한다.

```text
입력
├→ Model A ─┐
├→ Model B ─┼→ 결과 결합 → 최종 예측
└→ Model C ─┘
```

### 3.2 주요 결합 방식

#### Hard Voting

각 모델이 선택한 클래스를 투표하고 다수결로 결정한다.

#### Soft Voting

각 모델이 출력한 클래스별 확률을 평균하거나 가중 평균한다.

#### Weighted Ensemble

성능이나 신뢰도에 따라 모델별 가중치를 다르게 적용한다.

```text
최종 점수 = 0.5 × Model A + 0.3 × Model B + 0.2 × Model C
```

#### Stacking

여러 Base Model의 출력을 새로운 Meta Model의 입력으로 사용한다.

### 3.3 병렬 실행과 순차 실행

- 병렬 실행: 모델들을 동시에 호출해 전체 Latency를 줄일 수 있다. 자원 사용량은 커진다.
- 순차 실행: 앞 모델의 결과에 따라 다음 모델을 선택할 수 있다. 전체 Latency가 누적될 수 있다.

### 3.4 운영 시 고려 사항

- 한 모델이 Timeout이면 전체 요청을 실패시킬 것인가?
- 일부 모델만 성공해도 결과를 반환할 것인가?
- 모델별 버전과 가중치를 어떻게 기록할 것인가?
- 모델마다 전처리가 다르면 어디에서 관리할 것인가?
- 여러 모델을 호출해 증가한 비용과 Latency가 성능 향상에 비례하는가?

앙상블은 항상 더 좋은 선택이 아니다. 정확도 개선이 작고 운영 비용이 크게 늘어난다면 단일 모델이 더 적합할 수 있다.

### 이 장에서 기억할 것

- Ensemble은 여러 모델의 예측을 결합한다.
- Voting, Averaging, Weighted Ensemble, Stacking은 결합 방식이 다르다.
- 정확도뿐 아니라 Latency, 자원, 장애 처리 비용을 함께 평가해야 한다.

## 4. Business Logic Pattern

> 원본 PDF 188~208쪽

### 4.1 모델의 출력과 업무 결정은 다르다

모델은 보통 확률, 점수, 클래스 등을 출력한다. 실제 서비스는 그 출력에 정책과 규칙을 적용해 행동을 결정한다.

```text
모델 출력: 부정 사용 확률 0.82
        +
업무 규칙: VIP 고객, 거래 금액, 국가, 법적 제한
        ↓
최종 결정: 즉시 차단 / 추가 인증 / 승인
```

모델 출력과 최종 업무 결정을 분리하면 모델을 교체해도 정책을 유지할 수 있고, 정책 변경을 위해 모델을 다시 학습할 필요도 없다.

### 4.2 Rule-based Logic과 Model-based Decision

| 구분 | Rule-based Logic | Model-based Decision |
|---|---|---|
| 정의 | 사람이 명시한 조건 | 데이터에서 학습한 패턴 |
| 예 | 금액이 1억 원 이상이면 추가 승인 | 거래별 이상 확률 예측 |
| 장점 | 설명과 통제가 쉽다. | 복잡한 패턴을 학습할 수 있다. |
| 한계 | 규칙이 많아지면 관리가 어렵다. | 오판 가능성과 설명 문제가 있다. |

두 방식을 경쟁 관계로 볼 필요는 없다. 실제 시스템에서는 모델과 규칙을 함께 사용하는 경우가 많다.

### 4.3 Threshold

**Threshold(임계값)**는 모델 점수를 실제 행동으로 바꾸는 기준이다.

```text
위험 점수 < 0.5       → 승인
0.5 ≤ 위험 점수 < 0.8 → 추가 인증
위험 점수 ≥ 0.8       → 검토 또는 차단
```

임계값을 바꾸면 Precision과 Recall의 균형이 달라진다. 따라서 기술팀만 결정하지 않고 오탐과 미탐의 업무 비용을 고려해야 한다.

### 4.4 Routing

**Routing(라우팅)**은 입력 조건에 따라 다른 모델이나 처리 경로를 선택하는 것이다.

```text
언어 판별
├→ 한국어 → 한국어 모델
├→ 영어   → 영어 모델
└→ 기타   → 다국어 모델
```

라우팅 기준과 선택된 모델 버전을 로그와 트레이스에 기록해야 문제 발생 시 어떤 경로가 사용됐는지 알 수 있다.

### 4.5 Fallback

**Fallback(대체 경로)**은 주 모델이나 외부 서비스가 실패했을 때 사용할 예비 동작이다.

예:

- 신모델 실패 시 이전 안정 버전 사용
- LLM Timeout 시 미리 준비한 안내 메시지 반환
- 추천 모델 실패 시 인기 상품 목록 반환

Fallback은 오류를 숨기는 수단이 아니다. Fallback 발생률을 메트릭으로 기록하고 원인을 해결해야 한다.

### 4.6 Human-in-the-loop

**Human-in-the-loop**는 모델이 확신하기 어려운 사례나 영향이 큰 결정을 사람이 검토하도록 하는 구조다.

```text
높은 확신 → 자동 처리
낮은 확신 또는 고위험 → 사람의 검토
검토 결과 → 향후 학습 데이터로 활용
```

### 이 장에서 기억할 것

- 모델의 예측값과 최종 업무 결정은 분리해서 생각한다.
- Threshold, Routing, Fallback은 대표적인 Business Logic이다.
- 임계값은 모델 성능뿐 아니라 오탐·미탐의 업무 비용으로 결정한다.
- 고위험 의사결정에는 Human-in-the-loop가 필요할 수 있다.

## 5. KServe

> 원본 PDF 209~231쪽

### 5.1 KServe가 필요한 이유

FastAPI만으로도 모델 API를 만들 수 있다. 하지만 모델과 팀이 많아지면 다음 기능을 매번 직접 구현해야 한다.

- 컨테이너 배포
- 요청량에 따른 자동 확장
- Health Check
- 모델 파일 다운로드
- 버전 전환과 Canary 배포
- 표준화된 추론 API

**KServe**는 Kubernetes 위에서 이런 기능을 제공하는 Kubernetes-native Model Serving Platform이다.

### 5.2 먼저 알아야 할 Kubernetes 용어

#### Container

애플리케이션과 실행에 필요한 라이브러리를 하나의 격리된 패키지로 묶은 실행 단위다.

#### Pod

Kubernetes에서 배포되는 최소 실행 단위다. 하나 이상의 Container를 포함한다.

#### Deployment

Pod 복제본 수와 업데이트 방식을 관리한다.

#### Service

변할 수 있는 Pod 주소 앞에 안정적인 네트워크 접근점을 제공한다.

#### Custom Resource Definition

**CRD(Custom Resource Definition)**는 Kubernetes에 새로운 리소스 종류를 추가하는 방법이다. KServe는 `InferenceService` 같은 CRD를 제공한다.

#### Controller

Kubernetes 리소스의 현재 상태를 관찰하고 사용자가 선언한 원하는 상태가 되도록 실제 리소스를 생성·수정하는 제어 프로그램이다. 이 과정을 **Reconciliation(조정)**이라고 한다.

### 5.3 KServe 주요 구성 요소

| 구성 요소 | 계층 | 역할 |
|---|---|---|
| KServe Controller | Control Plane | KServe CRD를 관찰하고 Deployment, Service 등 실제 Kubernetes 리소스를 만든다. |
| ClusterServingRuntime | Control Plane | scikit-learn, Triton, vLLM 등 모델 형식별 기본 실행 이미지와 실행 방법을 정의한다. |
| InferenceService | Control Plane | 사용자가 선언하는 최상위 추론 서비스 리소스다. |
| Predictor | Data Plane | 모델을 로드하고 실제 추론을 수행한다. |
| Transformer | Data Plane | Predictor 호출 전후의 전처리와 후처리를 담당한다. |
| Explainer | Data Plane | SHAP 등으로 예측 이유를 생성하는 선택적 구성 요소다. |

**Control Plane**은 시스템의 원하는 상태를 결정하고 관리한다. **Data Plane**은 실제 요청과 데이터를 처리한다.

### 5.4 InferenceService와 ServingRuntime의 관계

사용자는 `InferenceService`에 어떤 모델을 어떤 형식으로 제공할지 선언한다. KServe는 적합한 `ServingRuntime`을 찾아 실제 Pod를 구성한다.

```text
InferenceService 작성
→ KServe Controller가 감지
→ 적합한 ServingRuntime 선택
→ 모델 저장소에서 모델 다운로드
→ Predictor Pod 시작
→ 네트워크 Endpoint 생성
```

### 5.5 모델 로딩

모델 파일은 Object Storage, Persistent Volume, Model Registry 등 외부 저장소에 있을 수 있다.

KServe의 **storage-initializer**는 모델 아티팩트를 내려받아 공유 Volume에 저장하고, Predictor Container가 그 Volume을 읽도록 구성한다.

### 5.6 Autoscaling

**Autoscaling(자동 확장)**은 요청량이나 자원 사용량에 따라 실행 인스턴스 수를 자동으로 조정하는 기능이다.

- Scale-out: 인스턴스 수를 늘린다.
- Scale-in: 인스턴스 수를 줄인다.
- Scale-to-zero: 요청이 없을 때 인스턴스를 0개까지 줄인다.

Scale-to-zero는 비용을 줄이지만 다음 요청에서 모델을 다시 로드해야 하므로 **Cold Start(콜드 스타트)** 지연이 발생할 수 있다.

### 5.7 Canary Deployment

**Canary Deployment(카나리 배포)**는 새 버전에 일부 트래픽만 보내 먼저 검증하는 방법이다.

```text
기존 모델 v1: 트래픽 90%
새 모델 v2:   트래픽 10%
```

새 버전의 오류율, Latency, 품질이 안정적이면 비율을 늘린다. 문제가 있으면 기존 버전으로 되돌린다.

### 5.8 KServe가 적합하지 않을 수 있는 경우

- 모델이 하나뿐이고 트래픽이 작다.
- Kubernetes 운영 기반이 없다.
- 단순한 내부 실험 API만 필요하다.
- 자동 확장과 버전 전환 기능보다 개발 단순성이 중요하다.

이런 경우 FastAPI나 BentoML 같은 더 단순한 방식이 적합할 수 있다.

### KServe 실습에서 확인할 것

- InferenceService가 정상 상태가 되는가?
- 모델 파일이 올바르게 로드되는가?
- Endpoint로 추론 요청을 보낼 수 있는가?
- Predictor, Transformer, Explainer의 역할을 구분할 수 있는가?
- 새 버전과 기존 버전의 트래픽 비율을 제어할 수 있는가?

## 6. vLLM

> 원본 PDF 232~251쪽

### 6.1 일반 모델 서빙과 LLM 서빙의 차이

일반적인 분류 모델은 한 번의 Forward Pass로 결과를 만든다. LLM은 Prompt를 처리한 뒤 다음 Token을 하나씩 반복 생성한다.

```text
Prompt 입력
→ Prefill
→ 첫 Token 생성
→ 이전 결과를 이용해 다음 Token 생성
→ 종료 조건까지 반복
```

여러 사용자의 요청이 동시에 들어오면 요청마다 길이와 생성 시간이 다르기 때문에 GPU를 효율적으로 공유하기 어렵다.

**vLLM**은 LLM 추론의 처리량과 메모리 효율을 높이기 위한 Serving Engine이다.

### 6.2 Token과 Tokenization

**Token(토큰)**은 LLM이 텍스트를 처리하는 기본 단위다. 단어 전체일 수도 있고 단어 일부나 기호일 수도 있다.

**Tokenizer**는 문자열을 Token ID의 배열로 변환하고, 생성된 Token ID를 다시 문자열로 복원한다.

### 6.3 Prefill과 Decode

#### Prefill

입력 Prompt 전체를 한 번에 처리해 각 위치에 대한 내부 상태와 KV Cache를 만든다. 계산량이 크고 병렬 연산 비중이 높다.

#### Decode

이전에 만든 KV Cache를 재사용해 다음 Token을 하나 생성한다. Token을 생성할 때마다 반복된다.

```text
Prompt → Prefill → KV Cache 생성
                    ↓
              Decode 반복
                    ↓
              생성 결과 출력
```

### 6.4 KV Cache

Transformer는 다음 Token을 만들 때 이전 Token들의 **Key**와 **Value** 계산 결과를 사용한다.

**KV Cache**는 이전 Token의 Key·Value를 저장해 같은 계산을 반복하지 않도록 한다. 생성 속도를 높이지만 GPU Memory를 많이 사용한다.

### 6.5 PagedAttention과 Paged KV Cache

요청마다 연속된 큰 메모리 공간을 미리 할당하면 실제 사용하지 않는 공간이 생기고, 요청 길이가 달라 메모리가 조각날 수 있다.

vLLM의 **PagedAttention**은 KV Cache를 고정 크기 Block으로 나눠 필요한 만큼 할당한다. 운영체제의 가상 메모리 Page와 비슷한 발상이다.

효과:

- KV Cache 메모리 낭비 감소
- 서로 다른 길이의 요청을 효율적으로 관리
- 같은 GPU에서 더 많은 요청 처리

### 6.6 Continuous Batching

전통적인 Static Batching은 Batch 안의 모든 요청이 끝날 때까지 다음 요청을 기다리게 할 수 있다.

**Continuous Batching(연속 배칭)**은 매 Decode Iteration마다 완료된 요청을 제거하고 대기 중인 새 요청을 즉시 Batch에 넣는다.

```text
Iteration 1: A, B, C 실행
Iteration 2: A 완료 → D 투입 → B, C, D 실행
Iteration 3: C 완료 → E 투입 → B, D, E 실행
```

GPU 유휴 시간을 줄여 전체 처리량을 높인다.

### 6.7 vLLM 주요 구성 요소

| 구성 요소 | 역할 |
|---|---|
| OpenAI API Server | HTTP 요청 검증, 응답과 Streaming 처리 |
| Tokenizer | 문자열과 Token ID 사이 변환 |
| Scheduler | 활성 요청과 대기 요청을 관리하고 실행 Batch 구성 |
| Paged KV Cache | KV Cache Block 할당·갱신·반환 |
| Compute Worker | GPU/CPU에서 Prefill과 Decode 연산 수행 |
| Output Processor | Token을 텍스트로 변환하고 응답 생성 |

### 6.8 OpenAI-compatible API

vLLM은 OpenAI API와 호환되는 Endpoint를 제공할 수 있다. 기존 OpenAI SDK를 사용하던 애플리케이션에서 `base_url`을 vLLM 서버로 바꿔 호출할 수 있다.

대표 Endpoint:

- `/v1/models`
- `/v1/completions`
- `/v1/chat/completions`

Chat Completions 요청의 주요 필드:

| 필드 | 의미 |
|---|---|
| `model` | 사용할 모델 이름 |
| `messages` | `system`, `user`, `assistant` 역할과 내용 |
| `max_tokens` | 생성할 최대 Token 수 |
| `temperature` | 출력의 무작위성 조절 |
| `top_p` | 누적 확률 기준 Sampling 범위 |
| `stop` | 생성을 중단할 문자열 또는 Token 조건 |
| `stream` | Server-Sent Events 방식으로 중간 결과를 받을지 여부 |

### 6.9 Streaming

LLM 응답은 길고 생성 시간이 오래 걸릴 수 있다. 모든 Token 생성이 끝난 후 한 번에 반환하면 사용자는 오랫동안 빈 화면을 보게 된다.

**Streaming**은 생성되는 Token을 여러 Chunk로 나누어 즉시 전달한다. OpenAI 호환 API에서는 일반적으로 **SSE(Server-Sent Events)**를 사용한다.

Streaming은 전체 계산 시간을 반드시 줄이는 것은 아니지만 **Time to First Token(TTFT)** 관점에서 사용자가 더 빠르게 응답을 느끼게 한다.

### 6.10 LLM 서빙 지표

- **TTFT(Time to First Token)**: 요청 후 첫 Token이 도착할 때까지의 시간
- **TPOT(Time per Output Token)**: 출력 Token 하나를 생성하는 데 걸리는 평균 시간
- **Tokens per Second**: 초당 처리하거나 생성한 Token 수
- **End-to-end Latency**: 요청부터 전체 응답 완료까지의 시간
- **Queue Time**: Scheduler 대기열에서 기다린 시간
- GPU Memory 사용량과 KV Cache 사용률

일반 API의 요청 수만 측정하면 Prompt 길이와 생성 길이 차이를 반영하기 어렵다. LLM은 Request와 Token 단위 지표를 함께 봐야 한다.

### vLLM 실습에서 확인할 것

- 모델이 정상적으로 GPU 또는 선택한 Device에 로드되는가?
- OpenAI-compatible Endpoint에 요청할 수 있는가?
- 비스트리밍과 스트리밍 응답의 구조를 구분할 수 있는가?
- `max_tokens`, `temperature`, `top_p`가 요청에 반영되는가?
- TTFT, 생성 속도, GPU Memory를 관찰할 수 있는가?

### 이 장에서 기억할 것

- LLM은 Prefill 후 Decode를 반복하며 Token을 생성한다.
- KV Cache는 이전 Token 계산을 재사용하지만 많은 GPU Memory를 사용한다.
- PagedAttention은 KV Cache를 Block 단위로 관리해 메모리 낭비를 줄인다.
- Continuous Batching은 완료된 요청을 빼고 새 요청을 즉시 넣어 처리량을 높인다.
- LLM 서빙은 Latency뿐 아니라 TTFT와 Token 처리량을 함께 측정한다.

## 7. 2일차 전체 연결

```text
많은 데이터를 주기적으로 처리
→ Batch Training / Batch Serving

여러 작업을 순서대로 연결
→ Pipeline / DAG / Airflow

여러 모델의 예측을 결합
→ Ensemble Model Serving

모델 출력에 정책과 예외 처리 적용
→ Business Logic

Kubernetes에서 표준화된 배포와 자동 확장
→ KServe

LLM의 GPU Memory와 Token 생성을 효율화
→ vLLM
```

2일차의 핵심은 도구 이름을 외우는 것이 아니다. **작업의 성격과 운영 요구에 따라 서빙 구조를 선택하는 능력**이 중요하다.
