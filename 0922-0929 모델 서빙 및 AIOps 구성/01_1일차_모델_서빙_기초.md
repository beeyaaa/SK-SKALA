# 1일차 - 모델 서빙의 기초

> 원본 범위: PDF 6~126쪽  
> 학습 흐름: **전체 그림 → 구체적인 모델 서빙 예시 → 핵심 개념과 패턴 → 다시 전체 그림**

---

## 0. 오늘 무엇을 배우는가

머신러닝 모델을 학습하면 보통 모델 객체나 모델 파일이 만들어진다. 하지만 파일이 존재하는 것만으로는 사용자가 모델을 이용할 수 없다. 다른 프로그램이 데이터를 보내고 예측 결과를 받을 수 있도록 모델을 실행 가능한 서비스로 만들어야 한다.

이 과정을 **Model Serving(모델 서빙)**이라고 한다.

```text
데이터 준비
→ 모델 학습
→ 모델 평가
→ 모델 저장
→ 모델 서빙
→ 모니터링과 지속적인 평가
```

오늘의 핵심 질문은 다음과 같다.

1. 학습된 모델은 어떻게 파일로 저장하는가?
2. 저장한 모델을 재학습 없이 어떻게 다시 실행하는가?
3. 다른 프로그램은 모델에 어떻게 예측을 요청하는가?
4. 배포한 모델이 계속 정상적으로 동작하는지는 어떻게 판단하는가?

---

## 1. Model Serving이란 무엇인가

> 원본 PDF 6~40쪽

### 1.1 Training과 Inference

**Training(학습)**은 데이터에서 규칙을 찾아 모델의 파라미터를 결정하는 과정이다.

**Inference(추론)**는 학습이 끝난 모델에 새로운 입력을 넣어 예측 결과를 얻는 과정이다.

```text
[Training]
학습 데이터 → 학습 알고리즘 → 학습된 모델

[Inference]
새로운 데이터 → 학습된 모델 → 예측 결과
```

예를 들어 Iris(붓꽃) 데이터로 품종 분류 모델을 만든다고 하자.

- 학습: 꽃받침과 꽃잎의 길이·너비를 이용해 품종 구분 규칙을 학습한다.
- 추론: 새로운 꽃의 측정값을 넣고 `setosa`, `versicolor`, `virginica` 중 하나를 예측한다.

모델 서빙은 두 번째 과정인 추론을 다른 사용자나 프로그램이 이용할 수 있게 만드는 일이다.

### 1.2 모델 파일만으로는 서비스가 되지 않는다

모델을 서비스하려면 여러 계층이 함께 필요하다.

```text
사용자 또는 애플리케이션
        ↓ 요청
Serving Framework
        ↓ 모델 호출
Model Runtime
        ↓ 파일 로드
Model Format
        ↓
예측 결과 반환
```

#### Model Format

**Model Format(모델 형식)**은 학습된 모델을 파일로 저장하는 규칙이다.

예:

- scikit-learn의 `pickle` 파일
- PyTorch의 TorchScript `.pt` 파일
- Keras의 `.keras` 파일
- 프레임워크 간 교환을 위한 `.onnx` 파일

#### Model Runtime

**Model Runtime(모델 런타임)**은 저장된 모델을 메모리에 불러와 실제 추론 연산을 수행하는 실행 엔진이다.

예를 들어 **ONNX**는 모델 파일 형식이고, **ONNX Runtime**은 그 파일을 실행하는 엔진이다. 파일 형식과 실행 프로그램을 구분해야 한다.

#### Serving Framework

**Serving Framework(서빙 프레임워크)**는 요청을 받고, 런타임을 통해 모델을 실행하고, 결과를 응답으로 돌려주는 계층이다.

- FastAPI: 개발자가 API 코드를 직접 작성한다.
- KServe: Kubernetes에서 모델 배포, 확장, 트래픽 전환을 관리한다.
- vLLM: Large Language Model(LLM)을 높은 처리량으로 서빙하는 데 특화되어 있다.

### 1.3 전체 ML 서비스 생명주기

#### Data Preparation

모델이 학습할 데이터를 준비하는 영역이다.

- **Data Collection(데이터 수집)**: 원천 데이터를 모은다.
- **Preprocessing(전처리)**: 결측치, 이상치, 형식 등을 정리한다.
- **Feature Engineering(피처 엔지니어링)**: 예측에 도움이 되는 입력 변수를 만든다.

여기서 **Feature(피처)**는 모델이 입력으로 사용하는 개별 변수다. Iris 예제에서는 꽃받침 길이, 꽃받침 너비, 꽃잎 길이, 꽃잎 너비가 피처다.

#### Model Build

- **Training / Fine-tuning**: 모델을 처음부터 학습하거나 기존 모델을 추가 학습한다.
- **Evaluation(평가)**: 정확도, 정밀도, 재현율 등으로 성능을 확인한다.
- **Pipeline**: 데이터 준비부터 평가까지의 여러 단계를 정해진 순서로 자동 실행한다.

#### Model Release

- **Artifact Store(아티팩트 저장소)**: 모델 파일, 그래프, 로그처럼 실행 결과로 생성된 파일을 보관한다.
- **Model Registry(모델 레지스트리)**: 모델의 버전, 상태, 평가 결과, 배포 이력을 관리한다.

`Artifact`는 작업의 결과로 만들어진 산출물을 뜻한다. 모델 파일도 아티팩트의 한 종류다. Artifact Store가 실제 파일을 보관한다면, Model Registry는 어떤 모델이 어떤 버전이고 어디에 배포됐는지를 관리한다.

#### Model Serving

사용자 요청을 받아 모델 추론 결과를 제공한다.

#### Monitoring

서비스가 배포된 후 상태를 관찰한다.

- **Metrics(메트릭)**: 요청 수, 오류율, 지연시간처럼 숫자로 집계하는 값
- **Logs(로그)**: 특정 시점에 발생한 사건의 상세 기록
- **Traces(트레이스)**: 하나의 요청이 여러 서비스를 통과한 경로와 소요시간
- **Quality / Drift**: 모델 품질 저하와 데이터 분포 변화를 확인하는 영역

### 1.4 배포 환경

| 환경 | 목적 |
|---|---|
| Local | 개발자의 컴퓨터에서 기능을 구현하고 시험한다. |
| Development(Dev) | 여러 개발자의 변경 사항을 통합해 검사한다. |
| Staging | 운영 환경과 비슷한 조건에서 최종 검증한다. |
| Production(Prod) | 실제 사용자가 접근하는 운영 환경이다. |

Staging은 단순한 추가 개발 서버가 아니다. 운영 배포 전에 운영과 최대한 같은 조건으로 확인하는 리허설 환경이다.

### 1.5 주요 서빙 도구의 위치

| 도구 | 성격 | 적합한 상황 | 주의점 |
|---|---|---|---|
| Flask / FastAPI | 범용 웹 프레임워크 | 단순한 모델 API를 빠르게 직접 만들 때 | 버전 관리, 자동 확장, 모니터링을 직접 구성해야 한다. |
| TensorFlow Serving | TensorFlow 전용 모델 서버 | TensorFlow 모델과 버전을 표준 방식으로 운영할 때 | 기본적으로 TensorFlow 모델 형식에 맞춰야 한다. |
| TorchServe | PyTorch 모델 서버 | PyTorch 모델을 REST/gRPC로 제공할 때 | 전처리·후처리를 위한 Handler 작성이 필요하다. |
| BentoML | 모델 패키징 및 서빙 프레임워크 | 여러 프레임워크의 모델을 일관된 방식으로 패키징할 때 | BentoML의 Service와 Runner 개념을 익혀야 한다. |
| KServe | Kubernetes-native 모델 서빙 플랫폼 | Kubernetes에서 여러 모델을 표준화해 운영할 때 | Kubernetes와 관련 구성 요소의 학습 비용이 크다. |
| Ray Serve | 분산 서빙 프레임워크 | 여러 모델과 CPU/GPU 작업을 DAG로 연결하고 독립 확장할 때 | Ray 클러스터 운영이 추가로 필요하다. |
| MLflow | MLOps 플랫폼 | 실험, 모델 버전, 배포 이력을 함께 관리할 때 | 서빙 전용 도구가 아니라 전체 수명주기 관리 도구다. |
| Kubeflow | Kubernetes-native ML 플랫폼 | 학습, 튜닝, 파이프라인, 서빙을 Kubernetes에서 관리할 때 | 서빙은 주로 KServe에 위임한다. |

### 1.6 ONNX가 필요한 이유

프레임워크마다 모델 객체와 저장 방식이 다르다. PyTorch에서 만든 모델을 PyTorch가 없는 환경에서 실행하거나, 여러 프레임워크의 모델을 하나의 런타임으로 실행하려면 공통 형식이 필요하다.

**ONNX(Open Neural Network Exchange)**는 모델의 연산 구조와 파라미터를 표현하는 개방형 교환 형식이다.

```text
PyTorch / TensorFlow / scikit-learn
              ↓ 변환
            ONNX
              ↓ 실행
        ONNX Runtime
```

ONNX를 사용한다고 모든 모델이 자동으로 완벽하게 호환되는 것은 아니다. 모델이 사용하는 연산이 ONNX의 연산 집합인 **Operator Set(opset)**에서 지원되는지, 변환 전후 출력이 일치하는지 검증해야 한다.

### 이 장에서 기억할 것

- 학습은 모델을 만드는 과정이고, 추론은 완성된 모델을 사용하는 과정이다.
- 모델 서빙은 추론 기능을 API나 서버 형태로 외부에 제공하는 것이다.
- Model Format, Model Runtime, Serving Framework는 서로 다른 계층이다.
- 모델 파일 보관은 Artifact Store, 버전과 상태 관리는 Model Registry의 역할이다.
- 배포 이후에는 시스템 상태뿐 아니라 모델 품질과 드리프트도 관찰해야 한다.

## 2. Model Serving Patterns

> 원본 PDF 41~68쪽

모든 서비스가 같은 방식으로 예측을 제공하지는 않는다. 응답이 필요한 시간, 데이터 양, 네트워크 상태, 모델 수에 따라 적절한 패턴이 달라진다.

### 2.1 서빙의 기본 원칙

#### Stateless

**Stateless(무상태)**는 서버가 이전 요청의 상태를 자기 메모리에 영구적으로 의존하지 않는 설계다.

서버 인스턴스 내부에 사용자 상태를 저장하면 인스턴스가 재시작되거나 여러 개로 늘어났을 때 상태가 서로 달라질 수 있다. 지속해야 하는 상태는 데이터베이스나 외부 저장소에 둔다.

#### Continuous Model Evaluation

모델은 배포 시점에 한 번 평가하고 끝나는 소프트웨어가 아니다. 실제 입력 데이터가 변하면 성능이 떨어질 수 있으므로 운영 중에도 계속 평가해야 한다.

#### Keyed Prediction

**Keyed Prediction**은 요청에 식별 키를 붙여 비동기·병렬 처리 후에도 원래 요청과 결과를 정확히 연결하는 방식이다.

```text
request_id=A → 예측 작업 ┐
request_id=B → 예측 작업 ├→ 완료 순서가 달라도 키로 결과 연결
request_id=C → 예측 작업 ┘
```

### 2.2 Batch Serving

**Batch Serving(배치 서빙)**은 많은 입력을 모아 일정한 시점에 한꺼번에 추론하는 방식이다.

예: 매일 새벽 전체 고객의 이탈 가능성을 계산해 데이터베이스에 저장한다.

장점:

- 대량 처리에 유리하다.
- GPU나 분산 자원을 효율적으로 사용할 수 있다.
- 사용자가 응답을 기다리지 않아도 되는 작업에 적합하다.

한계:

- 최신 입력에 즉시 반응하지 못한다.
- 작업 실패 시 재처리 범위와 중복 처리를 관리해야 한다.

### 2.3 Online Serving

**Online Serving(온라인 서빙)**은 요청이 들어올 때마다 즉시 추론 결과를 반환하는 방식이다.

예: 결제 요청이 들어오는 순간 이상 거래 여부를 판단한다.

주요 지표:

- **Latency(지연시간)**: 요청부터 응답까지 걸린 시간
- **Throughput(처리량)**: 초당 처리한 요청 수
- **Availability(가용성)**: 서비스를 정상적으로 사용할 수 있는 비율

### 2.4 Two-phase Prediction

두 단계의 모델을 차례로 사용한다.

예:

1. 가벼운 모델이 많은 후보를 빠르게 생성한다.
2. 무거운 모델이 소수 후보를 정밀하게 재정렬한다.

검색과 추천 시스템의 **Candidate Generation(후보 생성)**과 **Ranking(순위 결정)**이 대표적이다. 네트워크가 불안정한 엣지 환경에서는 기기 내부의 경량 모델과 서버의 정밀 모델을 나누는 방식으로도 사용할 수 있다.

### 2.5 Pipeline Serving

**Pipeline Serving(파이프라인 서빙)**은 하나의 요청을 여러 처리 단계나 모델에 순서대로 전달한다.

```text
이미지 입력
→ 이미지 전처리
→ 객체 탐지 모델
→ 탐지 결과 후처리
→ 설명 생성 모델
→ 최종 응답
```

단계를 분리하면 일부 모델만 교체하거나 단계별 병목을 찾기 쉽다. 반면 단계가 늘수록 전체 지연시간, 장애 지점, 데이터 형식 관리가 복잡해진다.

### 2.6 Ensemble Serving

**Ensemble(앙상블)**은 여러 모델의 예측을 결합해 최종 결과를 만드는 방식이다.

- Voting: 여러 모델의 다수결을 사용한다.
- Averaging: 확률이나 점수의 평균을 사용한다.
- Weighted Averaging: 모델별 가중치를 다르게 준다.
- Stacking: 여러 모델의 출력을 다른 모델의 입력으로 사용한다.

### 2.7 Business Logic Pattern

모델의 출력만으로 최종 의사결정을 내리지 않고 업무 규칙을 함께 적용한다.

```text
모델 위험 점수
+ 고객 등급
+ 법적 제한
+ 재고 상태
→ 최종 업무 결정
```

모델은 확률이나 점수를 예측하지만, 실제 서비스 결정에는 정책, 비용, 규정, 사용자 상태가 함께 필요하기 때문이다.

### 패턴 선택 기준

| 질문 | 적합한 방향 |
|---|---|
| 즉시 응답해야 하는가? | Online Serving |
| 대량 데이터를 주기적으로 처리하는가? | Batch Serving |
| 여러 단계가 순서대로 실행되는가? | Pipeline Serving |
| 여러 모델의 판단을 결합하는가? | Ensemble Serving |
| 모델 결과에 정책을 적용해야 하는가? | Business Logic Pattern |
| 빠른 1차 처리 후 정밀 판단이 필요한가? | Two-phase Prediction |

### 이 장에서 기억할 것

- 서빙 패턴은 도구 이름이 아니라 요청을 처리하는 구조다.
- 실시간 응답은 Online, 대량 주기 처리는 Batch가 기본이다.
- Pipeline은 단계의 연결, Ensemble은 여러 예측의 결합이다.
- 실제 서비스의 최종 결정에는 Business Logic이 자주 필요하다.

### 3.1 scikit-learn의 역할

**scikit-learn**은 Python에서 전통적인 머신러닝 알고리즘과 데이터 처리 기능을 제공하는 라이브러리다. 분류, 회귀, 군집화, 전처리, 모델 평가 등을 일관된 API로 제공한다.

대표적인 사용 흐름은 다음과 같다.

```python
model.fit(X_train, y_train)   # 학습
prediction = model.predict(X_test)  # 추론
```

### 3.2 Iris와 Random Forest

Iris 데이터는 150개 샘플과 4개 피처, 3개 품종으로 구성된 분류용 데이터셋이다.

**Random Forest(랜덤 포레스트)**는 여러 Decision Tree(결정 트리)를 학습한 뒤 그 결과를 결합하는 Ensemble 알고리즘이다. 하나의 트리에 과도하게 의존하는 문제를 줄일 수 있다.

### 3.3 pickle 직렬화

Python 객체는 실행 중 메모리에 존재한다. 프로세스가 종료되면 객체도 사라지므로 파일로 저장해야 한다.

- **Serialization(직렬화)**: 객체를 저장하거나 전송할 수 있는 바이트 형태로 변환한다.
- **Deserialization(역직렬화)**: 바이트 데이터를 다시 객체로 복원한다.

Python 표준 라이브러리인 `pickle`은 객체를 직렬화할 수 있다.

```python
with open("model.pkl", "wb") as file:
    pickle.dump(model, file)

with open("model.pkl", "rb") as file:
    model = pickle.load(file)
```

`pickle.load()`는 신뢰할 수 없는 파일에 사용하면 안 된다. 역직렬화 과정에서 임의 코드가 실행될 수 있기 때문이다.

### 3.4 FastAPI 서빙 구조

**FastAPI**는 Python의 ASGI 기반 웹 프레임워크다. 요청 데이터를 Pydantic 모델로 검증하고 JSON 응답을 만들기 쉽다.

```text
POST /predict
→ 입력값 검증
→ NumPy 배열 변환
→ model.predict 또는 predict_proba
→ JSON 응답
```

모델은 요청마다 파일에서 다시 읽지 않는다. 서버가 시작될 때 한 번 로드하고 모든 요청에서 재사용해야 한다.

FastAPI의 **lifespan**은 애플리케이션 시작과 종료 시 실행할 로직을 정의한다.

```text
서버 시작 → 모델 1회 로드 → 여러 요청 처리 → 서버 종료 → 리소스 정리
```

## 4. Application 내부 추론 - PyTorch

> 원본 PDF 78~88쪽

### 4.1 PyTorch 모델

**PyTorch**는 Tensor 연산, 자동 미분, 신경망 학습 기능을 제공하는 딥러닝 프레임워크다.

**Tensor(텐서)**는 숫자를 여러 차원으로 배열한 자료구조다. 신경망은 텐서를 입력받아 행렬 연산을 수행한다.

`nn.Module`을 상속해 모델 구조를 정의하고, `forward()`에 입력이 통과하는 계산 과정을 작성한다.

```text
입력 4개
→ Linear(4, 16) + ReLU
→ Linear(16, 8) + ReLU
→ Linear(8, 3)
→ 품종별 Logit 3개
```

**Logit(로짓)**은 Softmax를 적용하기 전의 원시 점수다. 가장 큰 로짓의 인덱스를 예측 클래스로 선택할 수 있다.

### 4.2 Eager Mode와 TorchScript

일반적인 PyTorch는 Python 코드를 실행하면서 연산을 즉시 수행하는 **Eager Mode**를 사용한다.

**TorchScript**는 PyTorch 모델의 계산 구조와 파라미터를 실행 가능한 중간 표현으로 저장하는 방식이다. 모델 클래스 정의가 없는 프로세스에서도 `torch.jit.load()`로 불러올 수 있다.

```text
PyTorch nn.Module
→ torch.jit.script(model)
→ TorchScript 모델
→ iris_model.pt
```

`torch.jit.script()`는 Python의 `forward()` 코드를 분석해 제어 흐름을 포함한 그래프를 만든다. `torch.jit.trace()`는 예시 입력을 실제로 통과시키며 실행된 연산 경로를 기록한다는 점이 다르다.

### 4.3 학습과 서빙의 전처리 일치

신경망 실습에서는 `StandardScaler`를 사용한다.

```text
표준화된 값 = (원본 값 - 학습 데이터 평균) / 학습 데이터 표준편차
```

서빙 환경에서도 학습할 때 계산한 평균과 표준편차를 그대로 사용해야 한다. 요청 데이터로 평균과 표준편차를 새로 계산하면 모델이 학습한 입력 분포와 달라진다.

따라서 모델 파일뿐 아니라 전처리 파라미터도 함께 버전 관리해야 한다.

### PyTorch 실습에서 확인할 것

- Eager Mode와 TorchScript의 테스트 정확도가 같은가?
- 복원 스크립트에 원래 모델 클래스 정의가 없는가?
- 서버가 `iris_model.pt`와 전처리 파라미터를 시작 시 한 번만 로드하는가?
- 워커 수를 늘렸을 때 처리량과 지연시간이 어떻게 변하는가?

> 참고: 최신 PyTorch에서 TorchScript 관련 deprecation 경고가 표시될 수 있다. 경고는 기술의 현재 권장 방향이 바뀌고 있음을 뜻하며, 실습의 저장·복원 개념 자체와는 구분해서 이해한다.

## 6. Continuous Model Evaluation

> 원본 PDF 100~126쪽

### 6.1 왜 배포 후 평가가 필요한가

테스트 데이터에서 정확했던 모델도 운영 환경에서는 성능이 떨어질 수 있다.

- 실제 입력 데이터가 학습 데이터와 다를 수 있다.
- 시간이 지나면서 사용자 행동과 환경이 변할 수 있다.
- 데이터 수집 방식이나 스키마가 바뀔 수 있다.
- 정답 데이터가 늦게 도착할 수 있다.

따라서 모델 평가는 배포 전 한 번으로 끝나지 않는다. 운영 중 입력, 예측, 실제 결과를 지속해서 관찰해야 한다.

### 6.2 Data Drift와 Concept Drift

#### Data Drift

**Data Drift(데이터 드리프트)**는 입력 데이터의 분포가 학습 시점과 달라지는 현상이다.

예: 학습 당시 고객 연령 분포와 현재 고객 연령 분포가 달라졌다.

#### Concept Drift

**Concept Drift(개념 드리프트)**는 입력과 정답 사이의 관계가 달라지는 현상이다.

예: 과거에는 특정 구매 패턴이 이탈을 의미했지만, 정책 변경 후 같은 패턴이 더 이상 이탈을 의미하지 않는다.

입력 분포가 같아도 Concept Drift가 발생할 수 있으므로, 피처 분포만 보는 것으로는 충분하지 않다.

### 6.3 PSI

**PSI(Population Stability Index)**는 기준 데이터와 현재 데이터의 구간별 비율 차이를 측정해 분포 변화를 요약하는 지표다.

강의자료의 해석 기준:

| PSI | 해석 |
|---:|---|
| `< 0.1` | 안정 |
| `0.1 ~ 0.25` | 약한 드리프트 - 주의 필요 |
| `> 0.25` | 강한 드리프트 - 원인 분석과 조치 필요 |

PSI 하나만으로 모델 성능 저하를 확정할 수는 없다. 입력 분포가 변했다는 신호로 사용하고, 성능 지표와 데이터 품질을 함께 확인해야 한다.

### 6.4 모델 품질 지표

정답을 확보할 수 있다면 문제 유형에 맞는 품질 지표를 추적한다.

- 분류: Accuracy, Precision, Recall, F1 Score, ROC-AUC
- 회귀: MAE, MSE, RMSE
- 확률 예측: Log Loss, Calibration

전체 평균만 보면 특정 집단의 성능 저하를 놓칠 수 있으므로 지역, 사용자 유형, 입력 구간 등 의미 있는 Segment별로도 확인한다.

### 6.5 시스템 지표

모델 품질과 서비스 품질은 별개다. 예측이 정확해도 서버가 느리거나 자주 실패하면 좋은 서비스가 아니다.

- 요청 수와 초당 요청 수
- 오류율
- 평균, p50, p95, p99 Latency
- CPU, Memory, GPU 사용량
- 모델 로딩 성공 여부

**p95 Latency**는 전체 요청 중 95%가 이 시간 안에 완료되었다는 뜻이다. 평균만으로는 일부 매우 느린 요청을 파악하기 어려우므로 Percentile을 함께 본다.

### 6.6 HTTP 상태 코드

| 코드 | 의미 | 모델 API 예시 |
|---:|---|---|
| 400 Bad Request | 요청 형식이나 값이 잘못됨 | 모델이 요구하는 피처 수가 맞지 않음 |
| 401 Unauthorized | 유효한 인증 정보가 없음 | API 토큰 누락 |
| 403 Forbidden | 인증됐지만 권한이 없음 | 일반 사용자가 관리자 API 호출 |
| 404 Not Found | 요청한 경로나 버전이 없음 | 배포되지 않은 모델 버전 요청 |
| 422 Unprocessable Entity | 구조는 맞지만 값 검증에 실패 | 숫자 필드에 문자열 입력 |
| 429 Too Many Requests | 요청 한도 초과 | Rate Limit 초과 |
| 500 Internal Server Error | 서버 내부의 예기치 못한 오류 | 전처리나 추론 코드 예외 |
| 502 Bad Gateway | 게이트웨이가 잘못된 백엔드 응답을 받음 | 모델 서버 프로세스 장애 |
| 503 Service Unavailable | 서버가 일시적으로 처리 불가 | 배포 중이거나 과부하 상태 |
| 504 Gateway Timeout | 제한 시간 안에 백엔드 응답이 없음 | 대용량 추론이 타임아웃 초과 |

클라이언트 입력 오류를 모두 500으로 반환하면 운영자가 서버 장애와 입력 오류를 구분하기 어렵다. 입력 검증과 예외 처리를 통해 적절한 상태 코드를 반환해야 한다.

### 6.7 평가에서 조치까지

```text
입력·예측·정답 수집
→ 데이터 품질 검사
→ 드리프트와 성능 계산
→ 기준 초과 여부 판단
→ 알림과 원인 분석
→ 재학습·롤백·트래픽 제한 등 조치
```

모니터링은 그래프를 보는 것으로 끝나지 않는다. 어떤 조건에서 누구에게 알리고 어떤 조치를 할지까지 정의해야 운영 체계가 된다.

### 이 장에서 기억할 것

- 모델은 배포 후에도 입력 분포와 예측 품질이 변할 수 있다.
- Data Drift와 Concept Drift는 다른 현상이다.
- PSI는 분포 변화 신호이지 모델 성능 자체의 증명은 아니다.
- 모델 품질 지표와 시스템 운영 지표를 함께 관찰해야 한다.
- 지표에는 임계값, 알림, 담당자, 대응 절차가 연결되어야 한다.
