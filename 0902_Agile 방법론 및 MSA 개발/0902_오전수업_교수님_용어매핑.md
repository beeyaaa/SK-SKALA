## 3. MSA 설계 용어

| 용어 | 교수님이 설명한 뜻 | 이번 실습에 적용되는 방식 | 발언 시각 |
|---|---|---|---|
| Monolith | 분할되지 않은 하나의 덩어리다. 하나의 업무라면 Monolith가 나쁜 것이 아니며 하나의 단위로 가는 것이 맞을 수 있다. | MSA를 정답으로 전제하지 않고, 실제로 독립 가능한 업무인지 먼저 판단한다. | 07:25 |
| MSA | 역할과 업무에 따라 서비스를 나누고 API·이벤트 계약으로 연결해 사용하는 구조다. 특정 서비스를 중단해도 다른 독립 서비스는 계속 동작할 수 있다. | User, Course, Enrollment, Payment, Recommend가 별도 서비스·컨테이너로 실행된다. | 01:13, 02:36, 07:25 |
| 서비스 독립성 | 한 서비스를 죽였을 때 무관한 다른 서비스가 계속 동작하는 성질이다. | Payment가 중단되어도 로그인·상품 등록·조회처럼 Payment와 무관한 부분은 동작하는지 관찰할 수 있다. | 01:13 |
| Bounded Context | 서비스를 나누는 업무·도메인 경계다. 교수님은 데이터 소유권과 변경 단위를 핵심 기준으로 설명했다. | Course 데이터는 Course Service, Enrollment 데이터는 Enrollment Service가 소유하도록 책임을 구분한다. | 07:25, 15:39 |
| 업무 단위 분할 | 데이터는 업무의 결과로 생기므로, 마이크로서비스는 일반적으로 데이터 생성·처리 그룹을 기준으로 나눈다. | 등록·조회·수정·삭제가 함께 일어나는 업무와 데이터를 하나의 책임 경계로 본다. | 07:25, 41:56 |
| 데이터 소유권 | 어떤 서비스가 특정 데이터를 만들고 변경할 책임을 갖는지를 뜻한다. | 다른 서비스가 직접 테이블을 수정하기보다 소유 서비스의 API를 통해 요청한다. | 07:25, 15:39, 41:56 |
| 변경 빈도·배포 단위 | 함께 자주 변경되는 업무와 코드는 같은 서비스 경계에 있어야 유지보수가 쉽다. 한 기능 수정에 다른 서비스 내부를 알아야 한다면 경계가 잘못됐을 수 있다. | 팀 도메인 변경이 Course에만 해당하면 Course Service만 수정·재배포할 수 있어야 한다. | 07:25, 08:40 |
| 나누지 말아야 할 것 | 동일 데이터를 함께 수정하는 트랜잭션을 잘못 분리하면 데이터 일관성과 유지보수가 위험해진다. | 같은 데이터의 입력·수정·삭제와 승진 처리처럼 함께 보장돼야 하는 로직은 무리하게 서비스로 쪼개지 않는다. | 02:36, 15:39, 41:56 |
| 트랜잭션 격리 | DBMS가 제공하는 DB 수준 격리와 업무 수준에서 설계해야 하는 격리를 구분해야 한다. | Enrollment 생성과 이후 Payment 실패·이벤트 처리 같은 업무 경계를 별도로 고려한다. | 20:04, 41:56 |
| API 계약 | 서비스 내부 구현 전체를 아는 대신 Method, URL, Request, Response라는 계약을 기준으로 연결하는 방식이다. | Swagger에서 계약을 확인하고 프론트엔드와 서비스 간 호출을 팀 시나리오에 맞게 연결한다. | 00:00, 02:36, 34:07, 49:06 |
| SOLID·SRP | 역할과 책임에 따라 클래스를 분리하는 Java/Spring 원칙이며 MSA의 서비스 분할에도 같은 사고방식이 적용된다. | 한 서비스와 클래스가 지나치게 많은 책임을 갖지 않도록 한다. | 10:56, 18:55 |
| MSA 적합 영역 | 사용자 변화에 맞춰 기능이 자주 변경되고 빌드·배포가 빈번한 영역에 적합하다. MSA는 만능이 아니다. | 추천처럼 사용자 반응에 따라 자주 바뀌는 AI 기능은 독립 서비스로 교체·배포하기 좋다. | 12:05, 13:13 |
| 장애 시 대체값 | 개인화 추천 서비스에 장애가 나도 전체 서비스가 멈추지 않도록 일반 추천 같은 대체 결과를 제공할 수 있다. | 개인화 Recommend 실패 시 인기 항목 등 기본 추천으로 대체하는 아이디어다. | 14:29 |

| Docker Compose | 여러 컨테이너의 실행 방법과 관계를 하나의 설정으로 관리하는 도구 | 10개 서비스의 포트, 환경변수, 실행 순서, 네트워크를 관리한다 | `docker compose up`으로 전체 서비스를 실행했다 |
| Eureka | 실행 중인 서비스의 이름과 위치를 등록하고 다른 서비스가 찾도록 하는 Service Discovery | API Gateway와 각 마이크로서비스가 Eureka에 등록된다 | `localhost:8761`에서 7개 애플리케이션이 UP인 것을 확인했다 |
| API Gateway | 외부 요청이 각 마이크로서비스로 들어가기 전에 거치는 단일 진입점 | 프론트엔드 요청을 User, Course, Enrollment 등의 서비스로 전달한다 | 프론트엔드가 개별 포트 대신 8080번 Gateway를 호출한다 |
| REST API | URL과 HTTP Method를 이용하여 서비스가 요청과 응답을 주고받는 방식 | 프론트엔드의 목록 조회·신청과 서비스 간 결제 요청에 사용된다 | Swagger에서 API 경로와 요청·응답 형식을 확인했다 |
| Swagger | REST API의 사용 방법을 확인하고 직접 호출할 수 있는 문서 화면 | 서비스별 API의 Method, URL, Request, Response를 확인한다 | 8081~8084의 Swagger UI에 접속했다 |
| Kafka | 한 서비스가 발생시킨 이벤트를 다른 서비스가 비동기로 전달받게 하는 메시지 브로커 | 결제 완료와 수강 활성화 이벤트를 전달한다 | Kafka 컨테이너가 실행되고 이벤트 토픽이 설정된 것을 확인했다 |
| Producer | Kafka에 이벤트를 발행하는 주체 | Payment Service가 `payment.completed` 이벤트를 발행한다 | 결제 서비스 로그에서 이벤트 발행 코드를 확인했다 |
| Consumer | Kafka 이벤트를 구독하여 처리하는 주체 | Enrollment Service가 결제 완료 이벤트를 받아 상태를 ACTIVE로 바꾼다 | Enrollment의 Kafka Consumer 구조를 확인했다 |
| JWT | 로그인한 사용자의 신원과 권한 정보를 담은 서명된 토큰 | 로그인 이후 API 요청의 Authorization 헤더에 포함된다 | 브라우저의 sessionStorage에 토큰이 저장되는 구조를 확인했다 |
| OAuth2 | 사용자의 인증과 토큰 발급 절차를 표준화한 인증 방식 | Auth Server가 로그인 후 Authorization Code를 발급하고 이를 Access Token으로 교환한다 | 로그인 후 `/callback`으로 돌아오는 흐름을 확인했다 |
| 동기 통신 | 요청을 보낸 서비스가 상대 서비스의 응답을 기다리는 통신 | Enrollment Service가 Course 존재 여부와 Payment 결과를 REST로 확인한다 | 수강신청 중 Payment Service를 직접 호출하는 코드를 확인했다 |
| 비동기 통신 | 이벤트를 발행한 서비스가 다른 서비스의 즉각적인 응답을 기다리지 않는 통신 | 결제 완료 후 Kafka 이벤트로 Enrollment 상태를 변경한다 | REST 호출과 Kafka 이벤트의 사용 목적이 다르다는 것을 이해했다 |
