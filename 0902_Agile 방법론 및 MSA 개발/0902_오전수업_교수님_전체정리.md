# 1. 오전 수업의 핵심 메시지

교수님이 오전 수업에서 반복해서 강조한 내용은 다음과 같다.

1. 요구사항을 많이 쓰는 것이 중요한 게 아니라 **사용자에게 정말 필요한 가치가 무엇인지 근거를 갖고 Backlog로 도출**해야 한다.
2. Sprint 1에는 모든 기능이 아니라 **MVP로 먼저 검증할 핵심 흐름**을 넣어야 한다.
3. MSA는 서비스를 무조건 잘게 쪼개는 것이 아니라 **업무·데이터 소유권·변경 단위가 독립적인 부분만 분리**해야 한다.
4. 이번 실습은 인프라를 새로 구축하는 것이 아니라 **완성된 서비스의 API 계약을 이해하고 팀 아이디어에 맞게 연결·수정하는 경험**이다.
5. Eureka, Kafka, Auth Server, API Gateway 같은 인프라는 역할을 이해하고 사용하되 **내부 구현을 파고들거나 수정하지 않는다.**
6. 수업 중 전체 빌드를 하면 대량의 라이브러리 다운로드가 발생하므로 **제공된 Docker Image를 로드하고 `--no-build`로 실행**한다.
7. 개인 서브노트는 용어 사전이 아니라 **이해관계자 가치 → AI 솔루션 → 아키텍처 → Sprint → API 계약 → 실행 증빙 → 트러블슈팅**의 논리로 작성한다.
8. 조별 결과물은 화려한 신규 개발보다 **정해진 범위 안에서 필요한 부분을 정확하게 수정하고 협업하는 과정**이 중요하다.

# 2. 교수님 발언 시간순 상세 정리

## 00:00~01:12 - User Story, Backlog, MVP와 API 계약

- 녹음은 API 계약 관계에 대한 설명 도중부터 시작한다.
- User Story와 Backlog를 만들 때 요구사항을 많이 넣을 필요는 없다.
- 가장 먼저 물어야 할 것은 “사용자에게 필요한 것이 무엇인가?”이다.
- Backlog는 그 질문에 대한 답으로 명확하게 나와야 한다.
- 어떤 근거로 특정 요구사항이 중요하다고 판단했는지 설명해야 한다.
- 그중 무엇을 MVP로 선택해 Sprint 1에서 먼저 하겠다는 팀의 이야기가 들어가야 한다.
- 오후 실습에서 각자의 PC에 온라인 교육 플랫폼을 실행할 예정이다.
- 플랫폼을 실행하면 API 명세를 확인할 수 있는 링크가 제공된다.
- API 화면에서 회원가입·로그인, Course 등록, Enrollment, Payment 등 각 마이크로서비스의 기능을 확인할 수 있다.
- 교수님은 온라인 교육 용어를 쇼핑몰에 비유했다.
  - Course 등록은 상품 등록에 대응할 수 있다.
  - Enrollment는 상품을 선택하거나 장바구니·주문에 넣는 행위로 볼 수 있다.
  - Payment는 이후 결제 처리에 대응한다.

## 01:13~02:10 - 서비스 독립성과 오늘의 Sprint

- 각 기능은 별도 마이크로서비스로 실행된다.
- 특정 서비스 컨테이너를 중지해도 관련 없는 다른 서비스까지 모두 중단되지는 않는다.
- 예를 들어 Payment Service가 중단돼도 로그인이나 상품 등록·조회 등 무관한 기능은 계속 동작할 수 있다.
- 이런 독립성이 MSA로 분리한 결과임을 직접 확인할 수 있다.
- 실습도 Scrum처럼 진행해보라고 안내했다.
- 오늘 Backlog를 도출하고 기획한 다음 Sprint 1을 실행할 예정이다.

## 02:11~03:50 - 실습의 목적과 MSA 개발의 범위

- 백엔드를 실제 동작하는 시나리오로 연결해 포트폴리오로 활용할 수 있게 하는 것이 목표다.
- 제공한 완성형 템플릿을 학생들을 위한 “선물”이라고 표현했다.
- 오후에는 Sprint Backlog에 무엇을 넣을지 정리한다.
- 템플릿을 직접 실행해 MSA 서비스 간 계약 관계를 확인하고 연결한다.
- MSA 기반 개발의 본질은 서비스를 적절히 나누고 연결해 사용하는 것이다.
- 가장 위험한 실수는 **나누지 말아야 할 것을 나누는 것**이다.
- 이번 과정은 전문 MSA 인프라 개발자 양성과정이 아니라 AI 서비스 엔지니어 과정이다.
- 따라서 모든 내부 구현을 처음부터 만드는 대신 API 계약을 보고 서비스를 연결하는 수준에 집중한다.

## 03:51~06:11 - Agile 적용 조건, 이해관계자 가치, 리더의 역할

- Agile이 실패하는 이유 중 하나는 조직이 지속적으로 변하는 이해관계자 요구와 가치를 인정하지 않는 것이다.
- Agile은 모든 업무에 적합한 방법론이 아니다.
- 반도체 공정처럼 수율을 위해 온도·순서·타이밍이 엄격하게 맞물리는 고정 공정을 함부로 분할하면 안 된다는 사례를 들었다.
- Agile은 사용자의 가치가 계속 변하고 그 변화를 수용해야 하는 업무에 적용하는 것이 적합하다.
- 학생들은 단순 지시자가 아니라 리더의 관점으로 기술과 현장을 이해해야 한다.
- 리더는 기술을 알고 이해관계자 가치에 맞게 방향을 잡을 수 있어야 한다.
- 모든 것을 직접 개발하라는 뜻은 아니지만 개발 경험은 필요하다.
- 개발 경험이 있어야 다른 엔지니어·개발자의 결과물을 검증할 수 있다.
- AI에게 일을 맡긴 후 그 결과를 검증하고 다른 시스템과 연결하는 데도 개발 경험이 필요하다.
- 실습 예제에서 인증·사용자 관리와 도메인 서비스가 분리돼 있다.
- Eureka, Kafka 등은 인프라이므로 직접 구현 대상이 아니다.

## 06:12~07:24 - 가이드 문서와 오늘·내일 연결

- 실습용 온라인 교육 플랫폼에는 수강신청 업무가 포함돼 있다.
- 소스 코드와 마이크로서비스 이미지가 함께 제공된다.
- 가이드 2는 제공된 코드가 어떻게 설계됐는지 이해하는 문서다.
- 가이드 1은 수업 운영·실행 절차를 확인하는 문서다.
- 필요한 내용은 수업 중간에 발췌해 설명할 예정이다.
- 오늘과 내일 실습이 연결되므로 먼저 전체 절차와 MSA 개념을 설명했다.
- 실제 사례를 이용해 어떤 경우에 마이크로서비스를 사용하는지 설명할 예정이라고 했다.

## 07:25~08:39 - Monolith와 MSA 분할 기준

- Monolith는 하나로 된 덩어리, 즉 분할되지 않은 상태를 뜻한다.
- Monolith가 본질적으로 나쁜 것은 아니다.
- 하나의 업무로 이루어진 시스템이면 하나의 단위로 유지하는 것이 맞을 수 있다.
- MSA에서 중요한 것은 서비스를 어떤 기준으로 나눌 것인지다.
- Bounded Context, 즉 도메인 경계는 업무의 경계를 의미한다.
- 구체적인 분할 기준으로 데이터 소유권을 강조했다.
- 데이터는 업무 수행의 결과로 생성된다.
- 따라서 업무 단위, 더 구체적으로는 데이터를 생성하고 처리하는 단위로 서비스를 나눈다.
- 변경이 발생하면 해당 서비스를 다시 빌드하고 배포해야 한다.
- 함께 변경되는 업무와 행위는 같은 변경·배포 단위로 묶여야 한다.

## 08:40~10:55 - 변경 단위, Docker Compose, Kubernetes와 비용

- 한 업무를 변경하려는데 다른 서비스 내부까지 알아야 한다면 유지보수가 어려워진다.
- 변경 빈도와 변경 범위가 서비스 경계를 정하는 기준이 된다.
- 변경이 자주 발생하는 기능은 독립 배포가 가능한 MSA가 잘 맞는다.
- MSA는 여러 서비스를 실행하고 서로 연결해야 하므로 인프라 복잡성이 증가한다.
- 이번 실습에서는 컨테이너로 서비스를 실행하고 Docker Compose로 연결한다.
- 교수님은 서비스가 매우 많아지면 Compose만으로 각각을 관리하기 어렵다고 설명했다.
- 규모가 커지면 Kubernetes 같은 오케스트레이션 기술로 자동화할 수 있다.
- Kubernetes는 서비스 중단 가능성을 줄이기 위해 복제 인스턴스를 사용할 수 있다.
- 고가용성을 높이는 대신 더 많은 인프라 비용이 든다.
- 많은 서비스를 안정적으로 운영하는 가치가 비용보다 중요할 때 Kubernetes를 선택할 수 있다.
- 현재 실습은 서비스 수가 적으므로 Compose를 사용하는 중간 단계로 이해하면 된다.
- 현재 Compose 구성을 이해하면 향후 Kubernetes 환경으로 확장하는 기반이 된다.
- 작은 규모에서 Kubernetes부터 적용하면 운영 부담과 비용이 클 수 있다.
- 학생들은 지금 인프라 기술의 내부 구현보다 그것이 무엇을 위한 것인지 이해하면 된다.

## 10:56~12:04 - SOLID와 단일 책임

- Java·Spring Boot에서 배운 SOLID 원칙을 다시 연결했다.
- 특히 SRP는 Single Responsibility Principle, 단일 책임 원칙이다.
- 역할과 책임을 기준으로 클래스를 분리하는 사고방식은 마이크로서비스 분할에도 공통으로 적용된다.
- 비즈니스 요구가 명확히 분리된다면 각 책임을 독립적으로 구현하고 변경할 수 있다.

## 12:05~13:12 - MSA와 Cloud Native, IaaS

- 마이크로서비스는 클라우드와 궁합이 좋다.
- 클라우드는 MSA를 적용하기 좋은 자연스러운 기반, 즉 Cloud Native Architecture 관점으로 설명할 수 있다.
- 과거에는 서버, OS, 볼륨, 스토리지 등을 직접 설치·연결해야 했다.
- IaaS에서는 이런 인프라 자원을 서비스 형태로 빠르게 준비할 수 있다.
- 수업에서는 주로 개념 수준으로 이해하면 된다.

## 13:13~14:28 - PaaS, CSP, AI와 클라우드, MSA 적합성

- PaaS는 인프라뿐 아니라 DB와 개발에 필요한 다양한 서비스를 제공해 개발자가 연결과 활용에 집중하는 형태라고 설명했다.
- 대표적인 퍼블릭 클라우드 제공업체로 AWS, Microsoft Azure, Google Cloud Platform을 언급했다.
- 이러한 업체를 Cloud Service Provider라고 부른다.
- AI 서비스도 클라우드와 궁합이 좋다.
- 모델을 학습할 때 GPU를 사용하고 필요하지 않을 때 반환할 수 있다는 예시를 들었다.
- MSA는 만능이 아니며 적합한 영역이 따로 있다.
- 자주 빌드·배포해야 하거나 사용자 변화에 맞춰 자주 수정되는 서비스에 적합하다.
- 변화가 적고 강하게 결합된 전통적 백엔드 업무에는 항상 적합한 것은 아니다.

## 14:29~15:38 - Netflix와 장애 대체 전략

- Netflix가 DVD 우편 대여 사업에서 온라인 스트리밍 서비스로 전환한 사례를 들었다.
- AWS 인프라를 활용하면서 온라인 서비스 중심으로 변화했다.
- 사용자의 연령·성별·클릭·시청 순서 같은 데이터를 기반으로 개인화 추천 서비스를 구성할 수 있다.
- 개인화 추천 기능은 사용자 요구에 따라 자주 바뀔 수 있다.
- 개인화 추천 서비스에 장애가 발생해도 전체 시스템을 중지시키지 않고 일반적인 추천 결과를 대체 제공할 수 있다.
- 이런 방식으로 여러 독립 서비스가 동시에 협력하는 구조를 설명했다.

## 15:39~16:48 - 데이터와 Bounded Context 심화

- 큰 회사는 서비스가 매우 세분돼 내부 직원도 전체 서비스 수를 정확히 알기 어려울 정도라고 설명했다.
- Bounded Context의 핵심 기준을 다시 데이터라고 강조했다.
- 데이터를 입력하고 단순 조회만 한다면 비교적 쉽게 분리할 수 있다.
- 입력뿐 아니라 수정·삭제가 발생한다면 그 변경 단위까지 고려해야 한다.
- 같은 인사 데이터를 이용해 승진처럼 업데이트가 필요한 업무를 서로 무리하게 분리하면 안 된다는 취지의 예를 들었다.
- 클라우드 특성을 활용할 수 있도록 애플리케이션을 분리하는 단계가 Cloud Native·MSA와 연결된다.

## 16:49~17:46 - 12-Factor와 학습 범위

- 단순히 Monolith 컨테이너를 클라우드에 올리는 단계와 클라우드 특성을 활용하도록 분리·설계한 단계를 구분했다.
- 클라우드에 적합한 애플리케이션 구성 원칙으로 12-Factor를 자료에 넣었다.
- 그러나 12-Factor 전체는 별도의 클라우드·MSA 강의가 될 수 있는 범위다.
- 이번 과정에서는 전부 외우거나 구현하지 않아도 된다.
- MSA 자체는 AI와 다른 전문 분야지만, 독립 변경·배포 특성이 AI 서비스에 잘 맞기 때문에 필요한 부분만 공부한다.
- 향후 관련 업무에서 다시 접하게 될 참고 개념이라고 했다.

## 17:47~18:54 - API Gateway, BFF, Auth, Config, Service Discovery

- 실습 아키텍처에는 API Gateway가 있다.
- 학생들은 Gateway 내부보다 그 뒤에 연결된 도메인 마이크로서비스 업무에 집중하면 된다.
- BFF는 Backend for Frontend의 약자다.
- 웹·모바일 등 다양한 채널의 요구에 대응하기 위해 별도 백엔드 계층을 둘 수 있다.
- 현재 실습에는 BFF를 적용하지 않았다.
- 마이크로서비스 요청은 API Gateway에서 라우팅된다.
- 인증 서버도 별도 서비스로 분리돼 있다.
- Config Server를 별도로 둘 수도 있지만 현재 구성에는 넣지 않았다.
- API Gateway, Service Discovery, Auth Server 등의 인프라는 역할과 책임을 기준으로 분리된 것이다.
- Spring 구조는 클래스와 계층을 역할·책임에 따라 나누기 쉬운 형태라고 설명했다.

## 18:55~21:05 - 서비스 통신, Kafka, 모니터링, 트랜잭션 격리

- Java에서 클래스를 역할과 책임으로 나누는 것과 서비스 분할 사고를 연결했다.
- MSA 상세 구현보다 전체 서비스 흐름을 이해하면 된다고 재차 강조했다.
- Kafka와 Eureka, Producer·Consumer의 내부 설정은 인프라에 가까우므로 사용 중심으로 접근한다.
- 서비스 간 통신이 많아지면 장애를 처리하는 별도 계층도 필요해진다.
- 서비스 수가 늘면 각 서비스를 모니터링해야 한다.
- 규모가 커지면 Kubernetes로 연결·관리·모니터링을 자동화하는 것이 유리할 수 있다.
- MSA의 주의사항으로 트랜잭션 격리를 언급했다.
- DB 트랜잭션 격리는 대부분 DBMS가 처리하지만 업무 수준의 트랜잭션 경계는 애플리케이션 설계가 필요하다.
- 실제 튜닝 현장에서 겪은 사례를 교재에 넣었으므로 참고하라고 안내했다.

- 실행 컨테이너에는 전체 소스 대신 JAR 중심으로 들어간다.
- 이런 분리 방식은 실행 Image를 단순화하고 소스 노출을 줄이는 효과가 있다.

# 7. 교수님이 명확히 하지 말라고 한 것

- 요구사항을 근거 없이 많이 Backlog에 넣지 않는다.

# 9. 전사상 불확실하거나 수업상 단순화된 부분

다음 내용은 원문 음성이 불명확하거나 교수님이 직관적 설명을 위해 단순화한 것으로 보인다.

- 녹음 첫 문장은 중간부터 시작해 앞 문맥이 없다.
- “100개가 넘으면 Kubernetes”는 정확한 기술 도입 기준이라기보다 규모가 커지면 Compose 수동 관리가 어려워진다는 취지다.
- “Kubernetes는 최소 두 개가 뜬다”, “비용이 두 배”는 고가용성과 복제 비용을 설명하기 위한 단순화다.
- “입력·조회만 하면 분리할 수 있고 수정·삭제가 있으면 분리하면 안 된다”는 절대 규칙이 아니라 데이터 소유권과 트랜잭션 경계를 고려하라는 설명으로 이해해야 한다.
- 전사의 “KPI로 컨테이너”는 문맥상 규칙 기반 추천 모델을 컨테이너로 제공했다는 의미로 보인다.
- 전사의 “API 투기”는 API Gateway 또는 API routing 문맥으로 보인다.
- 전사의 “스크린 구드/스크린 코트”는 Spring Cloud 문맥으로 보이나 정확한 음성 확인이 필요하다.
- “로컬 파일을 추가로 등록했다”는 교수님 발언과 달리 실제 ZIP에는 `docker-compose.local.yml`이 없었다.

이 불확실한 표현은 제출 문서에서 그대로 인용하기보다 가이드와 실제 코드에서 확인한 정확한 용어를 사용한다.
